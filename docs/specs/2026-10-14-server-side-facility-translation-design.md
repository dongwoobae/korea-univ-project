# 시설 번역을 서버로 옮기는 설계

**작성일:** 2026-10-14

## 문제

시설을 저장하면 번역은 관리자 브라우저가 이어서 진행했다.

```
브라우저: 시설 저장(translation_status='pending') → /api/translate → 브라우저가 번역 여섯 칸과 상태를 저장
```

두 번째 저장 전에 탭을 닫거나 다른 화면으로 가면 행이 `pending`으로 남는다. 2026-10-14 기준으로 운영 DB에 `pending`인 시설이 3건 있다. `pending`은 "번역 필요"로 집계되므로 사라지지는 않지만, 관리자가 다시 재번역해야 한다.

## 결정

### 번역과 저장을 서버 라우트 하나에서 한다

`POST /api/translate-facility { facilityId }` (관리자 전용)

1. 서버가 DB에서 그 시설의 원문(`name`·`description`·`floor_info`)을 읽는다. 브라우저가 보낸 글자를 믿지 않는다.
2. Google로 번역한다. 요청 형식은 `/api/translate`와 같은 `src/lib/server/googleTranslate.ts`를 쓴다.
3. 번역 여섯 칸과 `translation_status`를 서비스 키로 저장한다. 번역에 실패하면 `failed`만 저장한다.
4. 저장했으면 `/api/facilities`를 재검증한다.

관리자 화면은 지금처럼 응답을 기다렸다가 결과를 토스트로 보여 준다.

### 관리자가 떠나도 끝까지 처리한다

작업 promise를 `after()`에 넘긴다. Vercel에서는 `waitUntil`로 연결되어, 응답이 끝나거나 끊겨도 그 promise가 끝날 때까지 함수가 살아 있다.

### 원문이 그대로일 때만 쓴다

번역을 저장할 때 읽었던 원문 세 칸이 DB에서 그대로인 조건을 함께 건다(`eq`, 값이 없으면 `is null`). 조건이 맞지 않으면 PostgREST는 0행을 돌려주고, 이 라우트는 아무것도 쓰지 않은 채 `superseded`로 끝난다. 원문을 바꾼 저장이 자기 번역을 따로 돌리기 때문이다.

`updated_at`으로 잠그지 않는 이유가 있다. 설치 여부 토글이나 영상 자막 저장도 `updated_at`을 바꾼다. 그러면 원문과 상관없는 저장 때문에 번역이 버려지는데, 그 저장은 번역을 다시 돌리지 않는다.

### 응답

| 상황                       | DB                     | 응답                           |
| -------------------------- | ---------------------- | ------------------------------ |
| 번역·저장 성공             | 여섯 칸 + `translated` | 200 `{ status: "translated" }` |
| 그 사이 원문이 바뀜        | 쓰지 않음              | 200 `{ status: "superseded" }` |
| 번역 실패(키 없음 포함)    | `failed`               | 502                            |
| 저장 실패                  | 그대로(`pending` 등)   | 500                            |
| 없는 시설 / uuid가 아닌 ID | —                      | 404                            |

### 부르는 곳

시설 저장(`saveFacility` — 건물 상세의 `FacilityFormModal`과 독립 시설 상세 패널이 쓴다), 개별 재번역(`FacilityTranslationControl`, 독립 시설 상세 패널의 `재번역`), 일괄 재번역(`BulkRetranslateButton`), 제보 승인(`FacilityRequestReviewModal`)이 `translateFacility(facilityId)`로 이 라우트를 부른다.

재검증은 서버가 한다. 그래서 개별·일괄 재번역이 하던 재검증 호출은 지운다. 2026-08-04 설계의 "일괄은 재검증을 마지막에 한 번"을 이 문서가 대신한다. 시설 저장과 제보 승인은 저장 자체를 반영하려고 재검증 호출을 남긴다.

명소의 "자동번역 채우기", 건물 사진 캡션, 시설 영상 자막은 지금처럼 `/api/translate`를 쓴다. 명소는 저장 전에 결과를 보고 고치는 기능이다. 캡션은 번역이 실패해도 원문은 저장하는 흐름이다.

## 고려했지만 고르지 않은 방법

- **202를 바로 돌려주고 서버가 뒤에서 처리.** 저장 직후 실패를 알 수 없고, `pending`이 "번역 중"인지 "버려짐"인지 구분되지 않는다.
- **Supabase 트리거와 Edge Function.** 완전히 분리되지만, 배포할 곳과 구글 키를 둘 곳이 하나씩 늘어난다. 학교에 넘길 때 바꿀 곳이 두 군데가 된다.
- **시설 저장까지 서버로 옮기기.** 아래 남는 틈까지 없애지만, 시설 폼과 승인 흐름 전체를 다시 짜야 한다.
- **`updated_at` 잠금.** 위 "원문이 그대로일 때만 쓴다"에서 설명한 이유.

## 남는 틈

시설을 저장한 뒤 번역 요청을 보내기 전에 탭이 닫히면 행이 `pending`으로 남는다. 이 행은 "번역 필요"로 집계되어 일괄 재번역 대상에 그대로 보인다.
