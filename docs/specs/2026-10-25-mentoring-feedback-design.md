## 3. 건물 사진 순서 (8, PR ①-1·①-2)

### 3.1 지금

- `building_photos`에는 순서 칸이 없다(`id, building_id, url, created_at, caption, caption_en, caption_zh`).
- 공개 상세(`SidePanel.tsx`)와 관리자(`BuildingPhotoManager.tsx`) 둘 다 `.order("created_at")`로 읽는다. 그래서 처음 올린 사진이 늘 맨 앞이다.
- 업로드(`/api/upload-building-photo`)·삭제(`/api/delete-building-photo`)·캡션 저장은 누르는 즉시 저장된다. 페이지 전체의 "저장" 버튼과 묶이지 않는다.
- 시설 사진(`facility_photos`)에는 이미 `sort_order`가 있다. 이름은 그것을 따른다.

### 3.2 동작 (PR ①-2)

- **[사용자]** 관리자 건물 편집 화면의 사진 칸에서 각 썸네일에 ◀ ▶ 버튼이 있다. ◀는 바로 왼쪽 사진과 자리를 바꾸고 ▶는 바로 오른쪽 사진과 바꾼다.
- 맨 앞 사진의 ◀, 맨 끝 사진의 ▶는 비활성이다. 사진이 하나면 둘 다 비활성이다.
- **[판단]** 업로드·삭제와 같게 누르는 즉시 저장한다. 저장 중에는 그 건물의 화살표를 모두 잠가 연속 클릭이 엇갈리지 않게 한다. 실패하면 화면 순서를 되돌리고 오류 토스트를 띄운다.
- **[판단]** 업로드와 맞바꾸기는 서로를 잠근다. 올리는 동안 화살표를, 맞바꾸기 저장 중에는 "사진 추가"와 "실패한 사진 다시 시도"를
  잠근다. 업로드가 끝나며 목록을 다시 읽어, 저장 중인 맞바꾸기 앞의 순서로 화면을 덮을 수 있다.
- 공개 상세는 같은 순서로 보인다(첫 사진이 맨 앞).
- 새로 올린 사진은 맨 뒤에 붙는다. 기존 사진의 처음 순서는 올린 순서(`created_at`, 같으면 `id`)다.
- **[판단]** 끌어서 옮기기(드래그)는 이번에 만들지 않는다. 화살표는 휴대폰·키보드에서 그대로 쓸 수 있다. 사용자는 둘 다 괜찮다고 했다.
- 버튼에는 사진을 구분하는 접근 가능한 이름을 단다: "사진 N 앞으로 옮기기"·"사진 N 뒤로 옮기기"(N은 지금 화면 순서, 1부터).
  **[판단]** 숫자마다 뒤 조사(을/를)가 달라 조사 없는 꼴로 둔다.
- **[판단]** 저장 중 잠금은 `aria-disabled`로 건다. `disabled`로 잠그면 누른 버튼이 키보드 초점을 잃는다. 맨 앞·맨 끝이라 누를 수
  없는 화살표만 `disabled`다.
- **[판단]** 옮긴 뒤 초점은 옮긴 사진의 같은 방향 화살표로 간다. 끝에 닿아 그 화살표가 꺼지면 같은 사진의 반대쪽으로 간다 —
  키보드로 같은 사진을 이어서 옮길 수 있게.
- **[판단]** 성공 토스트는 띄우지 않는다. 화면 순서가 바로 바뀌고, 캡션 저장도 성공 토스트가 없다.

### 3.3 데이터 (PR ①-1)

마이그레이션 하나로 아래를 넣는다. 이 PR은 앱 코드를 바꾸지 않는다(타입 파일 제외). 넣은 뒤에도 지금 코드가 그대로 돌아야 한다.

- `building_photos.sort_order integer`를 더하고, 건물별로 `created_at, id` 순 번호(0부터)로 채운 뒤 `not null`로 바꾼다. 채우는
  동안에는 활동 기록 트리거를 끈다 — 운영 사진 수만큼 "건물 사진 수정" 줄이 쌓이지 않게.
- **새 행의 번호는 DB가 매긴다.** `sort_order` 없이 들어오는 행(지금 업로드 라우트가 그렇다)은 그 건물의 마지막 번호 + 1을
  받는다(사진이 없으면 0). 그래서 업로드 라우트는 ①-1에서도 ①-2에서도 바꾸지 않는다. 같은 건물에 두 장이 동시에 들어와도
  번호가 겹치지 않아야 한다.
- 같은 건물 안에서 번호가 겹치지 않음을 DB가 보장한다(`(building_id, sort_order)` 유일 제약). 맞바꾸기가 중간 상태에서 이 제약에
  걸리지 않게 짠다.
- 모든 새 행(번호를 직접 준 행 포함)과 맞바꾸기는 **같은 건물 단위 잠금**을 잡는다. 그래서 두 장이 동시에 들어오거나, 올리는 중에
  맞바꾸거나, 두 관리자가 동시에 화살표를 눌러도 번호가 겹치거나 덮이지 않는다. 지우기 라우트는 이 잠금을 잡지 않으므로, 맞바꾸기는
  두 행을 행 잠금으로 잡아 그사이 지워지지 않게 한다.
- **자리 바꾸기 함수**: 사진 두 장의 id를 **화면 순서대로**(앞·뒤) 받아 두 번호를 한 트랜잭션에서 맞바꾼다. 아래면 아무것도 바꾸지
  않고 오류를 낸다.
  - 두 사진이 같은 건물이 아니거나 하나라도 없다.
  - 앞 사진이 지금 순서에서 뒤 사진의 바로 앞이 아니다 — 사이에 다른 사진이 있거나 앞뒤가 뒤집혔다(다른 관리자가 그사이 순서를
    바꿨다). 방향까지 보는 이유: 두 관리자가 오래된 화면에서 같은 쌍을 누르면 두 번째 요청이 첫 번째를 몰래 되돌린다. 화면은 이
    오류를 받으면 다시 불러온다.
  - 두 사진이 보이지만 고칠 권한이 없다(RLS가 막았다).
- 함수는 호출자 권한(`security invoker`)으로 돈다. 관리자 화면의 브라우저 Supabase 클라이언트가 부르고(캡션 저장과 같은 길),
  기존 관리자 목록 쓰기 정책(`20261020000000_restrict_admin_writes.sql`의 `admin write`)이 그대로 걸린다. 실행 권한은
  `authenticated`에만 준다(`anon`·`public`, Supabase 기본 권한으로 따라오는 `service_role`도 뺀다). 서비스 키로 RLS를 건너뛰는
  업로드 라우트(`supabaseAdmin`)는 이 함수를 쓰지 않는다.
- 로컬·CI의 빈 DB에서도 돌아야 한다. 기존 DB 테스트의 사진 `insert`(`admin_write_policies.test.sql`,
  `activity_log_triggers.test.sql`)는 `sort_order` 없이 넣으므로 DB가 번호를 매겨 그대로 통과해야 한다.
- DB 테스트(`supabase/tests/`)에 더한다: 새 행 번호(빈 건물 0, 다음은 마지막 + 1), 맞바꾸기, 이웃이 아닐 때·앞뒤가 뒤집혔을 때·다른 건물일 때
  오류, 관리자 목록에 없는 계정의 맞바꾸기 거부, `anon` 실행 거부, 유일 제약. 채우기는 마이그레이션 때 한 번 도는 일이고 DB 테스트의
  DB는 그때 비어 있어 거기서 볼 수 없다. 운영에 적용된 뒤 공개 읽기로 건물마다 `sort_order` 순서가 `created_at, id` 순서와 같은지
  확인한다.
- `supabase/database.types.ts`를 함께 갱신한다. 마이그레이션 규칙은 `docs/database-migrations.md`.
- 활동 기록: `building_photos`의 `update`도 트리거로 남는다. 맞바꾸기 한 번에 "건물 사진 수정" 두 줄이 남고, 바뀐 칸은 기존
  `COLUMN_LABELS`의 `sort_order` → "순서"로 읽힌다. 따로 손대지 않는다.

### 3.4 화면 (PR ①-2)

- 공개 상세(`SidePanel.tsx`)와 관리자 사진 칸(`BuildingPhotoManager.tsx`)은 `sort_order`로 정렬해 읽는다. 같은 번호가 있을 수
  없지만 순서가 늘 같도록 `id`를 두 번째 기준으로 둔다. 그 밖에 `building_photos`를 순서대로 보여 주는 곳이 있으면 같이 바꾼다.
- 화살표는 3.3의 맞바꾸기 함수를 부른다. 인자는 화면 순서대로 — ◀는 (왼쪽 사진, 누른 사진), ▶는 (누른 사진, 오른쪽 사진).
- "이웃이 아님"(`PT409`)이나 "사진 없음"(`P0002`, 다른 관리자가 지웠다) 오류면 사진 목록을 다시 불러오고, 순서가 바뀌어 다시
  불러왔다는 토스트를 띄운다. 그 밖의 실패는 화면 순서를 되돌리고 오류 토스트.
- **[판단]** 다시 불러오기가 실패하면 서버 순서를 모르니 누르기 전 화면으로 되돌리고 오류 토스트를 띄운다. 사진 칸의 목록 다시
  읽기는 실패하면 지금 목록과 입력 중인 설명을 그대로 둔다(업로드·삭제 뒤 다시 읽기도 같다).
- **[판단]** 되돌린 실패는 활동 기록에 실패로 보고한다(작업 키 `building_photos.update`, 대상은 누른 사진, HTTP 상태 포함).
  브라우저 Supabase 쓰기 실패를 보고하는 관문은 `rpc/`를 건너뛰기 때문이다(`docs/specs/2026-10-19-activity-log-design.md` 4.3).
  `PT409`·`P0002`는 다른 관리자가 먼저 바꾼 경합이라 보고하지 않는다.
- E2E 목 백엔드(`e2e/support/mockBackend.ts`)가 `sort_order` 정렬과 맞바꾸기 RPC를 흉내 내야 한다.

## 4. 시설 종류 (9·10, PR ②)

### 4.1 지금

### 4.2 바꿀 것

- 새 마이그레이션 하나로:
  - `restroom`을 넣거나 고친다(`code`가 기본 키 — `insert … on conflict (code) do update`). `label`은 `장애인용 화장실`.
    새로 넣을 때(빈 DB)의 영어·중국어는 운영 값 그대로 `Accessible Restroom`·`无障碍卫生间`이고, 이미 있으면 `label`만 바꾼다.
  - **[판단]** 시설 이름(`building_facilities.name`)이 정확히 `장애인 화장실`인 행도 `장애인용 화장실`로 바꾼다. 화면은 시설 이름이
    있으면 종류 이름보다 그것을 먼저 쓰기 때문이다(`f.name ?? f.facility_types?.label`). 2026-10-25 운영 화장실 시설 40곳 중
    35곳은 이름이 비어 종류 이름을 쓰고, 2곳이 정확히 `장애인 화장실`, 3곳은 이미 "장애인용 화장실"이 들어간 이름이다. 영어·중국어
    이름과 번역 상태는 건드리지 않는다(뜻이 같다). 대기 중인 등록 요청은 관리자가 검토하며 고치므로 건드리지 않는다.
  - `student_lounge`를 같은 방식으로 넣거나 고친다(세 언어 이름 모두 아래 값으로 맞춘다).
  - 로컬·CI의 빈 DB에서도 돈다. 나머지 운영 종류(`ramp` 등)를 씨앗으로 채우는 일은 하지 않는다.
- **[판단]** 새 종류 값: 코드 `student_lounge`, 영어 `Lounge for Students with Disabilities`, 중국어 `残障学生休息室`.
- **[판단]** 아이콘은 lucide `Sofa`. 마커 SVG와 JSX 아이콘 짝 검사(`iconography.test.ts`)를 통과해야 한다.
- **[사용자]** 색은 청록 `#0F766E`(흰 아이콘 대비 5.47:1). 2026-10-26 처음 정한 갈색 `#7A5230`은 색상이 경사로 주황 `#B25617`과
  같은 계열이라 바꿨다. 이 색은 `FALLBACK_PALETTE`에도 있어 거기서 뺀다 — 모르는 종류의 칩이 목록 위치에 따라 같은 색을 받지
  않게. 알려진 종류 색이 `FALLBACK_PALETTE`와 겹치지 않음을 단위 테스트로 지킨다. 알려진 종류이므로 마커와 필터 칩이 같은 색을 쓴다.
- **[사용자]** 종류 목록의 순서를 저장 순서에 맡기지 않는다. 지금 화면들은 `facility_types`를 정렬 없이 읽어 행이 저장된 순서대로
  보이고, `restroom` 행을 고치면 Postgres가 고친 행을 새로 써 화장실 칩이 뒤로 밀릴 수 있다.
  - `facility_types.sort_order`를 `generated by default as identity`로 더하고, 기존 행은 2026-10-26 운영 화면 순서(`restroom` 1 ·
    `ramp` 2 · `parking` 3 · `elevator` 4 · `automatic_door` 5)로 채운다. 채우는 동안 활동 기록 트리거를 끈다(3.3과 같은 이유).
  - 번호 없이 들어오는 행(`student_lounge`, ②-2b 관리 화면이 더하는 종류)은 다음 번호를 받아 맨 뒤에 붙는다.

## 5. 건물 이름 강조 (2, PR ③)

### 5.1 지금 (`src/components/map/Map.tsx`)

- 건물 이름은 폴리곤에 붙은 영구 툴팁(`.ku-building-label`)이다. 확대가 데스크톱 17, 모바일 18 이상일 때만 보이고, 불투명도 0.58로 흐리다.
- 데스크톱에서 그보다 덜 확대했을 때는 마우스를 올리면 폴리곤이 강조되고 커서를 따라다니는 이름표(`.ku-map-tooltip`)가 뜬다.
- 이름이 보이는 확대에서는 `mouseover`가 일부러 아무것도 하지 않는다.
- 모바일은 건물을 누르면 상세 패널이 열리고 그 폴리곤이 강조된다.

### 5.2 동작

- **[사용자]** 이름이 보이는 확대에서 건물에 마우스를 올리면 **그 건물 이름만** 진해지고(흐림 없음), 굵어진다. 마우스를 빼면 돌아간다.
  처음 정한 "살짝 커진다"는 2026-10-27 사용자가 뺐다 — 글자 크기는 그대로다.
- **[판단]** 선택된 건물(웹에서 클릭, 모바일에서 터치해 상세가 열린 동안)의 이름도 같은 모양으로 강조한다. 모바일에는 마우스 올리기가 없어서 이것이 "터치되면 강조"다. 상세를 닫으면 돌아간다.
- **[사용자]** 선택된 건물의 이름은 **확대와 상관없이** 보인다. 이름이 숨는 확대(데스크톱 17 미만, 모바일 18 미만 — 모바일은 16에서
  열린다)에서도 그 한 건물 이름만 띄워 강조한다. 다른 건물 이름은 지금처럼 숨는다.
- **[판단]** 모바일에서 누른 건물의 이름이 상세 시트(아래 `min(62vh, 620px)`)에 가리면, 확대는 그대로 두고 지도를 옮겨 시트 위로
  보이는 자리에 오게 한다. 이미 보이면 옮기지 않는다. 옮길 자리는 지도 위에서 시트 위까지의 세로 가운데다. 지도 경계
  (`src/lib/mapBounds.ts`) 끝에 붙은 건물은 확대를 바꾸지 않고는 더 옮길 수 없어 가린 채 남을 수 있다 — 받아들인다. 검색·즐겨찾기로 고른
  건물은 `fitBounds`가 화면 가운데에 두는 다른 흐름이라 이 규칙에 넣지 않았다(2026-10-27).
- **[판단]** 웹에서 이름이 숨는 확대일 때, 선택된 건물에 마우스를 올리면 이미 이름이 떠 있으므로 커서 이름표를 띄우지 않는다.
  다른 건물은 지금처럼 커서 이름표가 뜬다. 폴리곤을 눌러 선택한 순간에도 떠 있던 커서 이름표를 닫는다.
- **[판단]** 덜 확대했을 때의 커서 이름표와 폴리곤 강조는 그대로 둔다. 이름이 보이는 확대에서 폴리곤 색은 바꾸지 않는다.
- **[판단]** 마우스를 올린 건물과 선택된 건물이 다르면 둘 다 강조한다. 선택이 풀리거나(상세 닫기·다른 건물 선택), 언어가 바뀌어
  이름이 다시 그려지거나, 확대가 바뀌어도 강조는 지금 상태(올림·선택)와 맞아야 한다 — 남거나 빠지지 않게. 지하철역을 고르면 앞서
  고른 건물의 폴리곤 강조도 푼다. 상세를 닫는 0.28초 사이에 다른 건물을 고르면 그 선택을 지우지 않는다. 둘 다 2026-10-27 전에는 어긋나
  있었다(역 선택 뒤 건물 강조가 남고, 닫는 사이 고른 건물의 상세가 사라졌다).
- 이름의 가운데가 건물 가운데에서 움직이지 않아야 한다. 굵어지면 너비가 달라지므로 툴팁 자리를 다시 계산한다(`tooltip.update()`).
  Leaflet은 툴팁 바깥 요소의 `transform`으로 자리를 잡으므로 거기에 `transform`을 걸지 않는다. 굵기는 강조 상태만 따르고 확대를 따르지
  않는다 — 마우스를 올린 채 확대 경계를 넘을 때 너비가 바뀌면 자리를 다시 잴 때가 없다.
- 다크 모드(⑤)와 글자 크기(⑥)가 들어온 뒤에도 강조가 맞게 보여야 한다. 그 확인은 ⑤·⑥ PR의 몫이다.

### 6.4 함께 지킬 것

- 필터 상태, 검색 결과, 즐겨찾기, 목록의 내용과 동작은 바꾸지 않는다. 바꾸는 것은 담는 그릇과 여닫는 방법이다.
- **열린 패널은 상태 하나로 다룬다.** 지금은 검색 결과·즐겨찾기·모바일 필터·목록이 각자 열림 상태를 갖는다(`Map.tsx`의
  `showFavorites`·`mobileFilterOpen`·`browseOpen`, `SearchControl` 안의 결과 열림). 이것을 `search | filter | favorites | browse | null`
  (⑤부터 `view`) 하나로 모은다. **[판단]** 전이:

  | 일                                        | 결과                                                                        |
  | ----------------------------------------- | --------------------------------------------------------------------------- |
  | 다른 버튼을 누른다                        | 앞 패널이 닫히고 그 패널이 열린다                                           |
  | 열린 패널의 버튼을 다시 누른다            | 닫힌다                                                                      |
  | 검색 결과·즐겨찾기·목록에서 항목을 고른다 | 패널이 닫히고 지금처럼 그 자리로 간다(건물이면 상세가 열린다)               |
  | 지도를 누른다(빈 곳이든 건물이든)         | 패널이 닫힌다. 건물이면 지금처럼 상세도 열린다                              |
  | 필터 안에서 체크·칩을 바꾼다              | 열린 채로 둔다                                                              |
  | Esc                                       | 열린 패널이 있으면 그것만 닫고 버튼으로 초점을 돌린다. 없으면 지금 Esc 동작 |
  | 768px 경계를 넘는다(창 크기·회전)         | 열린 패널을 닫는다. 웹의 접힘 저장 값은 그대로 둔다                         |
  | 모바일에서 건물 상세가 열린다             | 패널을 닫고 가로 줄을 숨긴다                                                |

- 언어 목록(`LanguageSwitcher`)은 이 상태에 넣지 않는다. 지금처럼 따로 열고 닫는다.
- 접근성: 버튼은 Tab으로 닿고, 패널을 여는 버튼에는 `aria-expanded`와 `aria-controls`, 열린 버튼은 눈에도 구분된다. 패널을 열면
  초점이 패널 안 첫 조작(검색은 입력창)으로 가고, 닫으면 연 버튼으로 돌아온다. **[판단]** 모바일의 아래에서 올라오는 패널은
  비모달이다(초점 가두기·배경 막기 없음). 지금 모바일 필터·목록도 그렇다.
- 터치 대상은 최소 44px.
- 모바일 검색: 입력창에 초점이 가서 화상 키보드가 올라와도 결과 목록이 키보드나 가로 줄에 가리지 않아야 한다.
- 지금 공개 지도 E2E(`e2e/public-map*.spec.ts`)의 상당수가 검색 상자·필터 버튼·목록 버튼 자리에 기댄다. 동작이 그대로인 시나리오는 새 자리로 옮겨 계속 통과시키고, 없어진 버튼을 가리키는 단언은 새 동작을 단언하도록 고친다.
- **모바일 확인은 PR마다 한다.** ④·⑤·⑥은 각자 바꾼 화면을 360·390·430px 세로와 가로 모드 하나에서 E2E로 확인하고(겹침·잘림·
  터치 크기), 모바일 검색은 키보드가 열린 높이(낮은 뷰포트)에서도 본다. ⑤·⑥은 자기가 더한 모드·글자 크기에서도 본다.
  ⑦(9장)은 그 위에서 하는 탐색 점검이다.

- 버튼 자리: ④의 아이콘 줄(웹) 맨 아래·가로 줄(모바일) 오른쪽 끝. **[사용자]** 웹 펼친 모습에서는 오른쪽 아래 지도 버튼 열에 둔다.
  세부는 `docs/specs/2026-10-28-dark-mode-design.md` 1장.
- 바뀌는 범위는 화면 색과 지도 바탕 타일·지도 위 색 모두. 바꾸면 새로 고침 없이 바로 바뀐다.
- **[판단]** 다크로 저장해 둔 사람이 들어올 때 밝은 화면이 번쩍이지 않게, 저장 값을 첫 그리기 전에 적용한다. 계약:
  - `<head>`의 작은 인라인 스크립트 하나가 `ku_theme`(⑥부터 `ku_font_scale`도)를 읽어 검증하고 `<html>`의 `data-theme`
    (`data-font-scale`) 속성으로 건다. `localStorage` 예외·모르는 값은 기본값(2장).
  - 서버는 이 속성을 렌더하지 않는다. `<html>`에 `suppressHydrationWarning`을 달아 그 속성 차이로 hydration 경고가 나지 않게 한다.
  - React 쪽 상태의 처음 값은 `localStorage`를 다시 읽지 않고 `<html>`에 걸린 속성에서 가져온다.
  - 모드를 드는 곳은 하나이고, 바꾸면 `<html>` 속성·`localStorage`·지도 타일과 지도 위 색을 쓰는 모든 곳이 새로 고침 없이 같이
    바뀐다. `usePrefersDarkMode()`를 쓰던 곳은 이 값을 읽는다. Context 대신 모듈 저장소로 한 이유는 세부 설계 2.1.
  - 다크 색 토큰은 `@media` 대신 `[data-theme="dark"]` 선택자로 건다.
  - 지도 로딩 자리(`MapWrapper.tsx`)도 테마 토큰 색을 쓴다.

### 7.3 관리자 화면

- **[사용자]** 관리자 화면도 같은 규칙이다. 기기 설정을 따르지 않고, 저장 값이 없으면 밝게 연다. 저장 값은 공개 지도와 같은
  `ku_theme`이라 한쪽에서 바꾸면 다른 쪽도 그 모드로 열린다.
- **[사용자]** 관리자 화면의 **지도는 늘 밝다**(타일·지도 위 색 모두). 다크 모드는 지도 밖 — 헤더·패널·드로어·모달·표 — 에만 걸린다.
- **[판단]** 관리자 헤더에 같은 다크모드 토글을 둔다. "다크는 버튼으로만 들어간다"는 규칙을 관리자 화면 안에서도 지키려면 버튼이
  관리자 안에 있어야 한다.
- 관리자만 쓰는 지도 다섯(7.1)은 테마를 읽지 않고 밝게 고정한다. `FacilityMap.tsx`는 쓰는 쪽이 정한다 — 공개 등록 요청 모달은
  테마를 따르고, 관리자 시설 폼·제보함 드로어는 밝게 고정한다(예: prop 하나).
- 다 바꾼 뒤 `usePrefersDarkMode()`를 쓰는 곳이 없으면 지운다.
- `e2e/admin-dark.spec.ts`는 기기 다크(`emulateMedia`) 대신 `ku_theme = "dark"`를 저장한 상태에서 같은 대비 검사를 한다. 기기가
  다크여도 저장 값이 없으면 관리자 화면이 밝게 열리는지도 단언한다. 지도는 지금처럼 검사에서 뺀다.

## 8. 글자 크기 (3, PR ⑥)

### 8.1 동작

- **[사용자]** 크게 · 보통 · 작게 세 단계. 처음은 보통.
- **[사용자]** 화면 글자 전체 — 패널·목록·버튼·검색·건물 상세·등록 요청과 피드백 모달 — 와 **지도 위 건물 이름·명소 이름까지** 같은 비율로 바뀐다.
  - **[사용자]** 2026-10-28 메뉴 줄(웹 접힌 줄·모바일 아래 줄)의 버튼 이름은 그대로 둔다. 칸이 좁아 크게에서 넘친다. 나머지 그대로인 글자는
    `docs/specs/2026-10-28-font-scale-design.md` 2.2.
- **[사용자]** 2026-10-28 고르는 자리는 오른쪽 아래 지도 버튼 열의 `가−`·`가＋` 두 버튼이다(ycc 웹사이트 설교 요약 화면과 같은 꼴).
  처음에는 ⑤의 보기 패널에 더하기로 했으나 ⑤가 패널 없는 토글이 됐다(7.2). 세부는 위 문서 1장. 값은 `ku_font_scale`에 남고 첫
  그리기 전에 적용한다(7.2와 같은 방식).
- **[판단]** 비율은 작게 0.9, 크게 1.2(위 문서 2.3).
- **[판단]** 공개 지도에만 적용한다. 관리자 화면에는 이 설정이 없다.
- 아이콘·마커 크기는 바꾸지 않는다. 글자만이다.

### 8.2 구현 참고

- 공개 지도 CSS(`map-ui.css` 약 1,700줄)와 컴포넌트 인라인 스타일은 대부분 `px` 글자 크기다. 한 곳의 배율로 다 같이 움직이게 바꾸는 방법(`rem` 전환, CSS 변수 곱 등)은 구현자가 고른다. 관리자 화면 글자에 번지면 안 된다.
- 배율이 닿아야 하는데 `.ku-map-shell` 안에서 이어받지 못하는 곳이 있다. 각각 처리하고 각각 확인한다.
  - `document.body`로 띄우는 공개 모달: 등록 요청(`FacilityRequestModal.tsx`), 피드백(`FeedbackButton.tsx`). 띄우는 뿌리에 공개
    화면 표시를 달아 배율 규칙이 닿게 한다.
  - 명소 이름: `LandmarkMarkers.tsx`가 `L.divIcon` HTML 문자열에 `10.5px`를 박고 아이콘을 캐시한다. 글자 크기를 CSS 클래스·변수로
    빼거나, 배율을 캐시 키에 넣어 다시 만든다.
  - 건물 이름: 툴팁 글자. 배율이 바뀌면 자리를 다시 계산한다(5.2와 같은 이유).
  - 시설 마커·팝업의 글자(`FacilityMarkers.tsx`의 인라인 `px`).
- E2E로 확인할 대상: 검색·필터·즐겨찾기·목록 패널, 건물 상세, 등록 요청·피드백 모달, 건물 이름·명소 이름, 시설 팝업.
