# 계단 표시 설계

2026-11-06

## 이 문서의 목적

경사도 선이 끊긴 자리에 계단을 그려, 지도를 보는 사람이 그 자리가 무엇인지 알게 하는 설계다.

요청(2026-11-06 발주자 피드백): 경사도 데이터에 끊긴 구간이 있는데 지도를 보는 쪽에서는 그게 무엇인지 모른다. 그 구간을
회색으로, 경사도 선과 같은 모양으로 그리고 싶다.

끊긴 자리는 관리자가 경사로를 그리다 계단을 만나면 그 앞에서 멈춘 곳이다. 지금 목적은 보이게 하는 것이지만 이 데이터는
후속 경로 탐색([`accessible-routing.md`](../future-development/accessible-routing.md))의 입력이 된다. 그래서 저장하는 값은
판단("통행 불가")이 아니라 사실("계단")이고(2장), 계단의 모양은 OpenStreetMap(OSM)에 이미 그려진 계단을 후보로 받아
관리자가 확정한다(5·6장).

### 대체하는 기존 문서

대체 표시(머리 배너와 표)는 **그 절의 코드를 바꾸는 구현 커밋**에서 단다. 표시가 코드보다 먼저 들어가면 문서가 아직 없는
화면을 가리킨다(2026-10-14·2026-10-19 설계의 같은 규칙).

## 2. 이름 — 계단이지 "통행 불가"가 아니다

### 2.1 사실과 판단을 나눈다

- **저장하는 것은 사실이다.** 구간 유형(계단·경사로)과 실측 경사다. 경로 탐색 문서의 `walkway_edges` 초안도 구간 유형에
  계단을 둔다.
- **지나갈 수 있는지는 계산하는 값이다.** 구간 유형 + 경사 + 이동 수단으로 정해진다. 경로 탐색 문서의 "목표 사용자 여정"이
  적듯 수동·전동 휠체어는 오를 수 있는 경사와 넘을 수 있는 턱 높이가 달라 같은 길도 판정이 갈린다.
- 계단은 수동·전동 휠체어 모두 지나가지 못해 지금은 "계단 = 통행 불가"가 겹친다. 가파른 경사로는 이동 수단에 따라 갈리고,
  공개 지도에서는 이미 구간 색(빨강 구간)이 그 정보를 맡는다. 이름에 "불가"를 박으면 경사 쪽과 어긋난다.
- 경로 탐색이 생기면 "고른 조건에서 못 가는 구간"은 그 결과를 지도 위에 덧그리는 별도 층이다. 수동 휠체어를 고르면 빨강
  경사로도 그 층에 들어간다. 이 문서의 회색 점선은 그 층이 아니라 사실 층이다.

기각한 이름:

- **휠체어 불가 경로** — 위의 이유. 가파른 경사로도 불가인데 같은 이름을 못 쓴다.
- **경사 없는 경로** — 없는 것이 무엇인지 말하지 않는다. 피드백은 "그 구간이 무엇인지 모른다"였다.
- **주의 구간·통행 제한 구간** — 같은 이유로 "무엇인지 모른다"가 다시 생긴다.

### 2.2 회색은 계단에만

조사하지 않은 빈칸은 비워 둔다. 경로 탐색에서 "모름"과 "못 감"은 다르게 다룬다 — 모름은 경고하고 못 감은 피한다. 계단을
그려 넣고 나면 남은 빈칸이 "아직 조사하지 않은 곳"이라는 뜻을 갖는다.

### 2.3 단 수는 받지 않는다

- 경로 탐색 문서가 다루는 이동 수단은 수동·전동 휠체어다. 휠체어에게는 계단 단 수와 무관하게 막히므로 경로 계산에 쓰이지
  않는다.
- 이동 수단마다 갈리는 것은 넘을 수 있는 턱의 **높이(cm)**이고 단 수가 아니다. 낮은 턱이 필요해지면 `턱` 종류를 높이 칸과
  함께 새로 만든다(11장).
- 우회로처럼 남길 말은 설명(`note`)에 적는다.

## 3. 실측 — OSM과 우리 경로 (2026-11-06)

Overpass API로 지도 표시 범위(`KU_BOUNDS`)의 `highway` 전체와 OSM `고려대학교 서울캠퍼스` 영역(way `26253960`)의 보행
그래프를 받고, 운영 공개 API(`/api/slopes`)의 경사도 경로와 대조했다. 거리는 캠퍼스 위도의 평면 근사다.

| 항목                                                  | 값                                             |
| ----------------------------------------------------- | ---------------------------------------------- |
| OSM 캠퍼스 영역의 길(보행로·서비스 도로 등)           | 648개 way, 노드 2,467개                        |
| 그중 한 덩어리로 이어진 노드                          | 98.8% (덩어리 5개)                             |
| OSM 캠퍼스 영역의 계단(`highway=steps`) · 횡단보도    | 71개 way · 51개 way                            |
| 계단 중 단 수(`step_count`)·휠체어(`wheelchair`) 태그 | 0개 · 0개 (`incline` 8개, 오르내림 방향뿐)     |
| 엘리베이터 · 턱(`kerb`) · 건물 출입구 노드            | 0 · 0 · 23                                     |
| 운영 경사도 경로 · 꼭짓점                             | 55개 · 156개                                   |
| 꼭짓점에서 가장 가까운 OSM 길(차로 포함)까지          | 중앙값 0.8m, 90% 2.6m, 최대 24.9m. 5m 안 152개 |
| 경로 끝점 110개 중 OSM 계단까지 5m · 10m · 20m 안     | 15개 · 22개 · 40개                             |
| 끝점 10m 안에 걸린 서로 다른 계단 way                 | 15개, 모두 OSM 캠퍼스 영역 안                  |

읽는 법:

- 우리 경로는 배경 지도의 길을 따라 그려졌다. 그래서 OSM 계단이 경로 끝과 잘 맞물린다. 예: `우당교양관 앞`의 시작점과
  `한투스퀘어 앞 경로`의 끝점이 같은 계단 way에, `정후 폭풍의 언덕`과 `국제관-타이거플라자 앞 경로`의 끝점이 같은 계단
  way에 붙어 있다.
- 끝점 근처 계단은 **후보**일 뿐이다. `중앙광장 본관 계단 옆 경사로`처럼 계단 옆을 지나는 경사로도 10m 안에 걸린다(6.3의
  토글). OSM에 빠졌거나 지금은 없는 계단도 있을 수 있다(6.4의 손 그리기).
- OSM이 주는 것은 길 모양·연결·계단과 횡단보도 유형이다. 경사와 통과 여부의 근거는 여전히 현장 실측이다. 경로 탐색 문서의
  "보행로는 기준선, 실측 경사는 속성"과 같은 분업이다.

## 4. 데이터

### 4.1 컬럼

`slope_segments`에 세 컬럼을 더한다.

```sql
alter table public.slope_segments
  add column kind text not null default 'slope'
    check (kind in ('slope', 'stairs')),
  add column osm_way_id bigint,
  add column note text,
  add constraint slope_segments_osm_way_id_stairs_only
    check (osm_way_id is null or kind = 'stairs');

create unique index slope_segments_osm_way_id_key
  on public.slope_segments (osm_way_id)
  where osm_way_id is not null;
```

- 기존 행은 기본값으로 모두 `slope`가 된다.
- `osm_way_id`가 있으면 OSM 후보로 확정한 계단, 없으면 손으로 그린 계단이다. 출처 칸을 따로 두지 않는다.
- 같은 OSM 계단은 한 번만 확정된다(고유 인덱스). 동시 확정은 6.7.
- `note`는 화면에서 계단에만 받는다. 컬럼은 종류를 가리지 않는다 — 경사로에 설명이 필요해지면 화면만 연다.
- 쓰기 권한은 지금의 관리자 쓰기 정책 그대로다.
- `supabase/database.types.ts`를 같은 커밋에서 갱신한다.

### 4.2 계단 행의 `segments` — 좌표만

```ts
/** kind = 'stairs' 행의 segments */
export type StairsPoints = [
  SlopeRouteStart,
  SlopeRouteStart,
  ...SlopeRouteStart[],
];
```

- 경사·거리를 싣지 않는다. 길이는 읽을 때 꼭짓점으로 잰다.
- 읽기 함수 `readStairsPoints(raw)`를 따로 둔다. 배열이고 두 점 이상이며 모든 원소가 좌표면 통과, 아니면 `null`(형식 오류).
  좌표 밖의 키는 무시한다.
- `readRoutePoints`는 경사로 전용으로 그대로 둔다. 경사값이 깨진 행을 통째로 버리는 규칙(그 함수의 주석)도 그대로다.
- **위험: 지금 `readRoutePoints`를 모든 행에 부르는 곳이 있다** — 공개 지도 `SlopeLayer`, 편집 지도 `SlopeRouteMap`의 다른
  경로, 목록 요약 `summarizeSlopeRoute`. 계단 행이 그대로 가면 경사가 없어 `null`이 되어 목록에는 형식 오류로, 지도에서는
  사라진다. 세 곳 모두 `kind`로 먼저 나눈다.

### 4.3 조회

- 공개 API(`/api/slopes`)의 select에 `kind`·`note`를 더한다. `osm_way_id`는 공개 지도가 쓰지 않아 받지 않는다.
  `SlopeLayer`의 `SlopeRoute`(`Pick`)도 같이 넓힌다.
- 편집 지도의 다른 경로 조회(`select("id, segments")`)에 `kind`를 더한다.
- 관리자 목록은 지금처럼 `select("*")`다.

### 4.4 활동 기록

컬럼 이름표만 더한다 — `kind` 종류, `note` 설명, `osm_way_id` OSM 번호. 경로 형상(`segments`)을 점 개수로 요약하는 트리거는
계단 행에도 그대로 맞는다. `kind` 값(`slope`·`stairs`)을 한국어로 보일지는 12장.

### 4.5 기각한 대안

- **별도 테이블(`stairs`).** RLS·API·편집기·활동 기록 트리거·이름표를 하나씩 더 만든다. 두 종류는 "관리자가 그린 선 +
  이름"이라는 모양이 같다.
- **경사로 안에서 구간마다 유형을 달기(경사 `null` 허용).** 경로 안 연결이 저절로 보장되는 장점이 있다. 그러나 경로 탐색
  문서에서 `slope_segments`는 그래프가 아니라 실측 기록이자 이전 출처이고, 연결은 보행로 그래프가 다시 정한다. 그 장점에
  비해 `readRoutePoints`의 "깨진 행은 통째로 버린다" 규칙이 무너지고 요약·프로파일 막대·검증이 모두 `null`을 다뤄야 한다.
  지금 끊긴 자리가 두 행 사이라는 점도 같다 — 어차피 행을 합치는 기능이 새로 필요하다.

## 5. OSM 계단 스냅숏

### 5.1 스크립트

- `src/scripts/fetchOsmStairs.ts`. `syncBuildings.ts`처럼 Node 24로 바로 실행한다(`npm run fetch-osm-stairs`).
- 같은 Overpass 서버(`syncBuildings.ts`의 주소)를 쓴다.
- Overpass 응답을 스냅숏으로 바꾸는 일(캠퍼스 경계로 거르기 포함)은 `src/lib/osmStairs.ts`의 순수 함수로 두고 vitest로 본다.
  스크립트는 받아서 그 함수에 넘기고 파일을 쓰기만 한다.
- 조회가 실패하거나 응답이 깨졌으면 기존 파일을 덮지 않고 0이 아닌 코드로 끝낸다.

### 5.2 범위

`public/campus-boundaries.geojson`의 캠퍼스 다각형 안에 꼭짓점이 하나라도 있는 `highway=steps` way 전부다. 2026-11-06에
71개(인문사회계 44 · 녹지캠퍼스 16 · 자연계 11 · 의료원 0).

경로 끝점 근처만 거르지 않는다. 경로가 새로 그려지면 후보가 달라지므로 거르기는 화면이 한다(6.1).

### 5.3 파일 — `public/osm-stairs.geojson`

```json
{
  "type": "FeatureCollection",
  "attribution": "© OpenStreetMap contributors",
  "license": "ODbL-1.0",
  "fetchedAt": "2026-11-06T00:00:00Z",
  "features": [
    {
      "type": "Feature",
      "properties": { "osmWayId": 394382780, "name": null },
      "geometry": {
        "type": "LineString",
        "coordinates": [
          [127.0, 37.5],
          [127.0, 37.5]
        ]
      }
    }
  ]
}
```

- 좌표 순서는 GeoJSON 그대로 `[lng, lat]`다. 확정할 때 `{lat, lng}`로 바꾼다.
- `campus-boundaries.geojson`과 같은 자리라 관리자 화면이 후보를 켤 때만 받는다. 앱 번들에 들어가지 않는다.
- `public/`과 `*.geojson`은 prettier 검사 밖이다(`.prettierignore`). 스크립트가 고정된 들여쓰기로 써서 갱신 diff를 읽을 수
  있게 한다.

### 5.4 갱신

스크립트를 다시 돌리고 바뀐 파일을 커밋한다. 확정한 계단은 좌표를 자기 행에 복사해 두므로 OSM에서 그 way가 지워지거나
바뀌어도 그대로다. 사라진 way를 알리는 일은 하지 않는다(11장).

### 5.5 라이선스 (ODbL)

법률 자문이 아니다. ODbL 1.0 원문 4.4~4.6절과 OSM 재단의 Substantial·Horizontal Map Layers 가이드라인을 읽고 적는다.

- **출처 표시**: 공개 지도에 이미 OpenStreetMap 표기가 있다(`src/lib/mapTiles.ts`의 `CARTO_ATTRIBUTION`).
- **동일조건(4.4·4.6)**: OSM에서 가져와 손본 데이터 묶음(Derivative Database)이나 그것으로 만든 결과물을 외부에 보이면,
  그 묶음은 ODbL로만 내놓을 수 있고 받는 사람에게 기계가 읽는 사본(전체, 또는 원본에서 바꾼 부분과 방법)을 제공해야 한다.
  조직 내부 사용은 해당하지 않는다(4.5). 앱 코드와 OSM에서 온 것이 없는 데이터 종류(우리 경사 실측)는 대상이 아니다.
- **실질적 추출 문턱**: 가이드라인은 한 번 추출한 100개 미만을 비실질적으로 보고, 같은 프로젝트의 반복 추출은 합쳐서 센다.
  이 프로젝트는 계단 전에 이미 OSM에서 이름 있는 건물을 가져온다 — `syncBuildings.ts`가 OSM way 번호를 건물 id로,
  `name`·`name:en`을 이름으로 넣는다. 그 스크립트의 조회 범위에 2026-11-06 이름 있는 건물이 107개다. 그래서 계단 71개를
  더하기 전부터 100개를 넘는다. 100개를 넘는다고 바로 실질적이 되지는 않는다(가이드라인의 기준은 "마을 지도는 괜찮고 도시
  지도는 안 된다") — 다만 "문턱 아래라 신경 쓰지 않아도 된다"고 할 수는 없다.
- 이 상태는 계단 작업이 만든 것이 아니라 건물 가져오기에서 이미 있다. 이 설계는 OSM 유래 데이터(건물 id·이름, 계단 좌표)를
  여기 적어 두는 데서 멈추고, 공개 방식(내려받기 제공 등)은 발주자 확인 사항으로 남긴다(13장).

## 6. 관리자 화면 — 경사도 작업 화면

### 6.1 후보 보기

- 목록 패널에 `OSM 계단 후보` 토글을 둔다. 기본 꺼짐, 상태는 URL에 남기지 않는다.
- 켜면 스냅숏을 받아, 이미 확정된 `osm_way_id`를 뺀 후보를 지도에 옅은 회색 점선으로 깐다. 스냅숏을 못 받으면 토글 옆에
  오류 문구를 보이고 토글을 끈다.
- 후보를 누르면 `?osm={wayId}`로 후보 확정 패널(6.2)을 연다. 스냅숏에 없거나 이미 확정된 번호로 들어오면 없는 `?id=`와
  같은 규칙(URL에서 지우고 경고 토스트)이다.

### 6.2 후보 확정 패널

- 입력: 이름(기본값은 OSM `name`, 없으면 `계단`, 필수), 설명(선택).
- 끝 잇기 토글(6.3)과 미리보기.
- `계단으로 확정` → `kind='stairs'`, `osm_way_id`, 좌표(끝 잇기 반영)로 insert. 성공하면 그 계단의 보기(`?id=`)로 간다.
- 저장 중 잠금·실패 시 초안 유지·이탈 경고는 경사로 편집 패널과 같은 규칙이다.

### 6.3 끝 잇기

계단 선의 첫 꼭짓점과 끝 꼭짓점 각각에 대해, 10m 안에서 가장 가까운 **경사로 행의 끝점**(시작점·끝점)을 찾는다. 찾으면
패널에 그 끝의 토글 `{경로 이름} 끝에 잇기 ({거리}m)`를 보인다. 기본 켜짐이다.

- 켜면 계단 선의 그 끝 꼭짓점을 경사로 끝점 좌표로 **바꾼다**. 덧붙이지 않는다.
- 두 끝이 같은 경사로 끝점을 고르면 가까운 쪽만 잇는다.
- 고치는 것은 새 계단 행뿐이다. 경사로 행은 건드리지 않는다.
- 10m는 3장의 실측에서 왔다(끝점 22개가 계단 10m 안).
- 토글은 계단 옆을 지나는 경사로가 걸리는 경우(3장) 때문에 둔다.

기각:

- **잇는 선을 덧붙이기.** 경사로 끝과 OSM 계단 끝 사이 몇 m가 계단 점선으로 그려져, 계단이 아닌 길을 계단으로 보인다.
  관리자는 "계단 앞까지" 그렸으므로 경사로 끝점이 실제 계단 시작에 가깝고, OSM 계단 끝은 근사다 — 계단 끝을 옮기는 쪽이
  현장에 더 가깝다.
- **경사로 끝점을 계단 쪽으로 옮기기.** 실측한 구간 길이(`distance`)가 바뀐다.
- **잇지 않기.** 몇 m의 빈틈이 지도에 남는다. 경로 탐색 문서가 계단 시작·종료점을 노드로 두는데, 그 점이 경사로 끝과
  어긋난다.

### 6.4 손으로 그리기

- 목록 패널의 `＋ 경로 그리기` 옆에 `＋ 계단 그리기`(`?new=stairs`). 기존 도구 바(`SlopeEditToolbar`)를 그대로 쓴다.
- 패널: 이름(필수, 빈칸으로 시작)·설명·끝 잇기 토글(6.3, 선이 있을 때)·`취소`·`저장`. 단위 선택과 구간 카드는 없다.
- 검증: 이름, 두 점 이상, 길이 0인 구간 없음. 경사 입력 검증은 없다.

### 6.5 목록

- 칩: `전체 · 경사로 · 계단`(`kind` 기준). 경사도 수집 정책의 칩이 생기므로 목록 패널이 칩 줄을 그린다 —
  2026-10-19 설계 5장의 "칩 줄을 그리지 않는다"를 대체한다. 형식 오류 행도 `kind`로 칩에 든다.
- 머리 문구: `경사로와 계단 · 총 {n}개`. 지금 문구("구간별 경사를 기록한 보행 경로")는 계단에 맞지 않는다.
- 계단 행: 이름 + 요약 줄 `계단 · {길이}m · {수정일}`. 프로파일 막대는 그리지 않는다. 형식 오류면 지금처럼 `형식 오류` 배지.
- 목록 범례(`LEGEND`)에 계단 견본 한 줄을 더한다.

### 6.6 보기·편집

- 보기 패널: 이름·설명·출처(`OSM {번호}` 또는 `직접 그림`)·길이, `계단 편집`. 삭제는 경사로와 같은 인라인 확인이다.
- 편집 패널은 6.4와 같다.
- 끝 잇기는 이미 경사로 끝점에 붙은 끝(0.01m 미만)을 제안하지 않는다. 그래서 이어 둔 기존 계단을 열면 토글이 보이지 않고,
  꼭짓점을 옮기면 다시 계산한다. 잇지 않은 끝이 있는 기존 계단은 토글이 처음부터 보이되 꺼져 있다 — 관리자가 일부러 끈
  끝일 수 있다.
- `osm_way_id`는 편집해도 남는다 — 모양을 고쳐도 그 계단에서 왔다는 사실은 그대로다.

### 6.7 동시 확정

두 관리자가 같은 후보를 확정하면 뒤 요청이 고유 인덱스에 걸린다(PostgreSQL `23505`). 그때 `이미 확정된 계단이에요`를
보이고 목록을 다시 받아 후보에서 뺀다. 수정의 `updated_at` 조건은 경사로와 같다.

### 6.8 지도

- 작업 화면 지도·편집 지도의 다른 경로 층에서 계단은 공개 지도와 같은 회색 점선(7.1)이다. 굵기·흐려짐 규칙은 경사로 선과
  같다.
- 모바일은 2026-10-14 설계 6.6의 보기·편집 규칙을 그대로 따른다. 후보 확정 패널은 보기 패널과 같은 자리다.

## 7. 공개 지도

### 7.1 선

- 색 `#78716C`(중간 회색) 하나, 굵기 5(경사로와 같다), 점선. 관리자가 구간 색으로 회색을 골라도 점선이라 갈린다.
- 점선은 길이 0의 대시와 둥근 끝(`lineCap: "round"`)으로 만든 점이다. 시작값 `dashArray: "0 14"`.
- **외곽선도 같은 점선 무늬다.** 굵기는 2026-10-19 설계 4.1대로 선 굵기 + 3. 같은 무늬라 점마다 테두리가 생긴다. 외곽선
  점끼리 붙지 않아야 한다 — 간격이 외곽선 굵기보다 넉넉해야 한다(12장).
  - 기각: 실선 외곽선. 어두운 실선 위의 점이 되어 이어진 길로 읽힌다.
- 상수(`STAIRS_LINE_COLOR`, `STAIRS_DASH`)는 `src/lib/stairs.ts` 한 곳에 두고 공개 지도·작업 화면·편집 지도가 같이 쓴다.

### 7.2 순서

외곽선 전부 → 계단 → 경사로. 2026-10-19 설계 4.1의 "외곽선을 전부 먼저"를 그대로 따르고, 이어 붙인 계단 끝이 경사로
끝 밑으로 들어간다.

### 7.3 팝업

굵은 `계단`, 그 아래 이름, 설명이 있으면 설명. 지금 경사 팝업처럼 한국어만이다.

### 7.4 범례

- `SlopeBandsLegend`의 구간 막대 오른쪽에 간격을 두고 점선 견본 칸 하나. 2026-10-19 설계 4.2의 "늘 보이는 것은 막대와
  경계 눈금뿐"을 대체한다.
- 막대 안의 칸으로 넣지 않는다 — 막대는 관리자가 2~6개로 고치는 구간 설정이고 칸 사이에 경계 눈금이 붙는다.
- `<button type="button">`, 접근 이름 `계단`, `경사도 범례` 묶음 안. 툴팁 `계단 — 휠체어로 지나갈 수 없어요`. 툴팁 규칙(누르면
  열림·Esc·한 번에 하나·툴팁을 눌러도 닫힘)은 구간 칸과 같다.
- 컴포넌트 속성 `showStairs`. 지도 위 범례(`SlopeLegend`)는 켜고, 범례 편집 모달의 미리보기는 끈다 — 모달은 구간을 고치는
  곳이라 고칠 수 없는 칸이 섞이면 헷갈린다.
- 범례 폭이 늘어난다. 데스크톱·모바일·글자 크기 150%에서 눈금과 버튼이 겹치지 않는지 기존 시험으로 다시 본다(10.2).

### 7.5 필터

경사도 필터 하나로 경사로와 계단이 같이 켜지고 꺼진다. 필터 이름은 그대로다.

## 12. 구현 시 확인할 것

- 길이 0 대시 + 둥근 끝이 Chrome·Safari·Firefox에서 점으로 그려지는지, 외곽선 점과 선 점이 같은 자리에 맞는지, `"0 14"`에서
  외곽선 점끼리 붙지 않는지(밝은·어두운 지도, 위성).
- 2026-11-08 — 점선은 점 위만 눌려, 공개 지도는 보이지 않는 굵은 선(`stairsHitStyle`)이 누르기와 팝업을 받고 보이는 점선은
  `interactive: false`다. Chromium(Playwright, 배율 1·2)에서 둥근 점으로 그려지고 외곽선 점이 각 점 둘레에 얇은 테두리로 맞물리며
  `"0 14"`에서 외곽선 점끼리 붙지 않는다. 이어 붙인 계단 끝은 경사로 선 끝 밑으로 들어간다. Safari·Firefox와 실제 타일(밝은·어두운
  지도, 위성) 위의 모양은 확인 전.
- 편집 지도는 경사로를 그린 뒤 꼭짓점 개수를 고정한다(2026-08-30 설계 5.4.1 — 구간마다 경사가 있어서). 계단에는 그 이유가
  없다. 계단 편집에서 고정을 풀지, 그대로 쓸지.
- 2026-11-08 — 계단은 고정을 푼다(`STAIRS_EDIT_OPTIONS`). 구간마다 값이 없어 꼭짓점을 더하고 지워도 어긋날 것이 없다.
- `kind` 값을 활동 기록에서 `경사로`·`계단`으로 보일 값 이름표가 있는지(`activityLabels.ts`).
- `syncBuildings.ts`의 Overpass 서버가 지금도 응답하는지. 안 되면 스냅숏 스크립트만 다른 공개 서버로.
- `AGENTS.md` 지시대로 라우트 핸들러를 고치기 전 `node_modules/next/dist/docs/`의 해당 가이드를 읽는다.
