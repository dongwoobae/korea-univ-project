# 경사도 구간 범례 설계

2026-10-19

## 이 문서의 목적

공개 지도의 경사 색을 연속 그라데이션에서 **구간마다 한 색**으로 바꾸고, 구간의 개수·경계·색·이름·설명을 관리자
경사도 화면에서 고칠 수 있게 하는 설계다. 관리자 화면의 판정 3색도 같은 구간 색으로 통일한다.

요청(2026-10-19 발주자 피드백): 경사도 범례를 4구간으로 나누고 그라데이션을 빼 명확한 색으로 나눈다. 구간 개수와
구간별 경사도, 색은 관리자 경사도 페이지에서 수정할 수 있게 한다.

## 2. 구간 설정

### 2.1 저장 형식

```json
{
  "bands": [
    {
      "name": "보도 기준 이내",
      "upperPercent": 5.555555555555555,
      "color": "#8BC34A",
      "description": "보도 기준 1/18 이하"
    },
    {
      "name": "완화 범위",
      "upperPercent": 8.333333333333332,
      "color": "#FFD600",
      "description": "완화 한도 1/12 이하"
    },
    {
      "name": "특례 범위",
      "upperPercent": 12.5,
      "color": "#FF9800",
      "description": "경사로 특례 한도 1/8 이하"
    },
    {
      "name": "초과",
      "upperPercent": null,
      "color": "#E53935",
      "description": ""
    }
  ]
}
```

- 낮은 구간부터 적는다. **마지막 구간의 상한은 `null`**("그 위 전부")이다. 어떤 값도 반드시 한 구간에 든다.
- **상한은 %로, 반올림하지 않고** 저장한다. 법 기준이 비율이고, 색·경고 비교가 이미 %에서 `값 ≤ 경계 + 1e-9`로
  이뤄진다(2026-10-06 설계 2.2). 도로 입력해도 `degToPercent` 결과를 그대로 저장한다.
- 행이 없거나 형식이 깨졌으면 코드의 기본값(`DEFAULT_SLOPE_BANDS`)으로 그린다. 그래서 **마이그레이션이 없다** —
  첫 저장이 upsert로 행을 만든다. 배포 순서 문제도 없다.
- 읽기는 기존 RLS(anon·authenticated 모두 select 허용, `20260529000000_add_app_settings.sql`) 그대로다. 쓰기 정책이
  없어 service role만 쓸 수 있으므로 API 라우트를 거친다(6.3).

### 2.2 기본 구간

2026-10-19 운영 `slope_segments`를 anon 키로 조회했다 — 39행, 구간 62개, 1.92~18.35%. 10-06·10-08 조회와 같다.

| 안       | 경계              | 구간 수 (낮은 쪽부터) | 거리 m                |
| -------- | ----------------- | --------------------- | --------------------- |
| **택함** | 1/18 · 1/12 · 1/8 | 11 / 11 / 16 / 24     | 441 / 510 / 734 / 959 |
| 기각     | 1/12 · 1/8 · 15%  | 22 / 16 / 16 / 8      | 951 / 734 / 683 / 276 |

경계 셋이 모두 법 조항(2026-10-06 설계 4.1)에 근거가 있다. 기각안은 분포가 고르지만 15%는 근거가 없다.

기본 설명은 지금 범례 아래 기준선 세 줄의 문구를 옮겼다. 각 기준선이 그 구간의 상한이다. 마지막 구간에 대응하는
기존 문구가 없어 설명을 비운다. "법적 기준"이라고 쓰지 않는 규칙(2026-10-06 설계 4장)은 그대로다.

기본 상한은 비율 상수(`WALKWAY_RATIO * 100` 등)로 적는다. `5.56` 같은 리터럴을 쓰지 않는다(2026-10-06 설계 3.1).

### 2.3 기본 색과 그 한계

색 계열은 연두·노랑·주황·빨강으로 정했고(2026-10-19 동우), 후보 셋 중 흔한 신호등 색을 골랐다. 측정은 2026-10-06·10-14
설계와 같은 방법이다(OKLab ΔE×100, Machado 2009 심도 1.0, 밝은 바탕 `#F2F2F0`, 어두운 바탕 `#2B2B2B` 가정).

| 쌍          | 정상 | 제1색맹 | 제2색맹 |
| ----------- | ---: | ------: | ------: |
| 연두 – 노랑 | 16.9 |     9.7 |    15.2 |
| 노랑 – 주황 | 14.9 |    15.4 |    11.3 |
| 주황 – 빨강 | 20.5 |    22.5 |    16.7 |
| 연두 – 주황 | 18.5 | **6.2** | **5.3** |
| 연두 – 빨강 | 32.7 |    28.2 |    13.3 |
| 노랑 – 빨강 | 35.3 |    37.8 |    27.9 |

- 이웃 구간끼리는 색각 이상에서도 기준 8을 넘는다. **한 칸 건넌 연두와 주황이 색약 시야에서 갈리지 않는다.**
- 대비: 밝은 지도에서 연두 1.87·노랑 1.26·주황 1.92, 어두운 지도에서 빨강 3.35. 노랑은 외곽선(4.1) 없이는 밝은
  지도에서 거의 보이지 않는다.
- 보완: 외곽선, 팝업 수치(`경사 17.6% (10.0°)`), 범례 툴팁의 이름. 색은 관리자가 바꿀 수 있다.

기각한 기본 색:

- **`#75CC1D`·`#FCE67A`·`#D0792A`·`#9B1F1B`.** 모든 쌍 색각 이상 최소 9.7로 기준을 넘는다. 노랑이 옅은 크림색,
  주황이 갈색 쪽이라 요청한 네 색으로 덜 읽힌다.
- **`#77D312`·`#FCEF83`·`#D0792A`·`#9E1901`.** 최소 11.6. 위와 같은 이유이고 노랑이 더 옅다.

연두·노랑·주황·빨강은 색약 시야에서 모두 노랑~갈색 계열이라 밝기 차이로만 갈린다. 기준을 넘기려면 노랑을
옅게, 빨강을 어둡게 밀어야 했다.

### 2.4 검증 — `validateSlopeBands`

관리자 폼(6.1)과 API(6.3)가 같은 함수를 쓴다. 통과하면 정규화한 값을, 아니면 오류 문구 목록을 돌려준다.

| 항목 | 규칙                                                                                             |
| ---- | ------------------------------------------------------------------------------------------------ |
| 개수 | 2~6                                                                                              |
| 이름 | 앞뒤 공백을 떼고 1~20자                                                                          |
| 설명 | 앞뒤 공백을 떼고 0~200자. 비어도 된다                                                            |
| 색   | `#RRGGBB`. 대문자로 정규화                                                                       |
| 상한 | 마지막을 뺀 모든 구간이 유한수, `0 < 상한 ≤ 100`(%), 앞 구간보다 0.01%p 이상 큼. 마지막은 `null` |

- 상한 100%는 입력 범위 상한 45°(`MAX_SLOPE_DEG`)와 같다.
- **최소 간격 0.01%p**: 앞 구간보다 크기만 하면 되게 두면, 간격이 판정 허용오차(`1e-9`, 2.5)보다 좁은 두 상한에서
  뒤 구간의 정확한 상한이 앞 구간으로 판정된다. 눈금은 소수 둘째 자리까지 보이므로(4.2) 그보다 좁은 간격은 화면에서도
  구분되지 않는다. 비교는 `상한 − 앞 상한 ≥ 0.01 − 1e-9`다 — 부동소수로 `5.01 − 5`는 `0.009999999999999787`이라
  허용오차 없이 비교하면 사람이 친 `5.01`이 거부된다.
- 이 검증은 % 값을 받는다. 도로 친 값은 폼이 % 로 바꾸기 **전에** 도 범위로 검사한다(6.2).
- 6은 데스크톱 막대 폭 약 200px(4.2)에서 경계 눈금이 약 33px 간격이 되는 수다. 눈금 글자(`12.5%`)가 겹치지 않는지는
  구현에서 확인한다(11장). 겹치면 상한 개수를 줄인다.

`readSlopeBands(value)`는 DB 값을 같은 검증에 넣는다. 실패하면 **기본값 전체로** 대체하고 콘솔에 경고를 남긴다.
일부 구간만 살리면 경계가 끊기거나 마지막 구간이 상한을 갖게 된다.

### 2.5 판정 — `slopeBandIndexFromDeg(bands, deg)`

저장값(도)의 절댓값을 %로 바꿔 `percent ≤ upperPercent + 1e-9`인 첫 구간을 고른다. 상한이 `null`인 마지막
구간에서 멈춘다. 경계값은 그 구간에 든다. 도를 받는다는 것을 이름에 적는다(2026-10-06 설계 3.1).

### 2.6 기각한 대안

- **전용 테이블 `slope_bands`(구간당 한 행).** 구간 수를 바꾸는 저장이 행 추가·삭제·수정을 한 번에 해야 해 원자적으로
  하려면 RPC가 필요하다. "상한 오름차순"은 행 사이 조건이라 DB 제약으로 걸 수 없어 결국 2.4의 앱 검증이 필요하다.
- **`/api/slopes` 응답에 설정을 합친다.** 요청 하나가 준다. 응답이 배열에서 객체로 바뀌어 공개 지도·목 백엔드가 모두
  바뀌는데, 경사도 레이어는 기본으로 꺼져 있어 줄어드는 요청의 이득이 작다.
- **상한을 도로 저장한다.** 측정기가 도를 내고 저장 경사도 도다. 그러나 기본 경계가 비율이라 도로 저장하면
  `atan` 결과를 담게 되고, 비교는 어차피 %에서 한다.

## 3. 불러오기와 공유 — `useSlopeBands()`

구간 설정은 모듈 수준 저장소 하나에 두고 `useSyncExternalStore`로 읽는다(`src/lib/slopeBandsStore.ts`).

- 스냅샷은 `{ bands, status }`다. `status`는 `loading`(응답 전) · `ready` · `error`.
- 처음 구독할 때 `app_settings`에서 `slope_bands` 행을 한 번 읽는다. **`getSetting`을 쓰지 않는다** — 그 함수는 조회
  오류와 행 없음을 같은 fallback으로 돌려줘(`settings.ts`의 `getSetting`) 둘을 가를 수 없다.
  - 행 없음 → `ready`, 기본값. 값이 깨짐 → `ready`, 기본값(2.4의 `readSlopeBands`). 조회 오류 → `error`, 기본값.
  - 화면은 세 상태 모두 `bands`로 그린다. 공개 지도는 상태를 보지 않는다. 실패는 콘솔에 남기고 다시 시도하지 않는다.
- 서버 스냅샷은 `{ 기본값, loading }` 상수 하나다. 첫 렌더가 서버와 같아 hydration이 어긋나지 않는다.
- 관리자가 저장하면 `setSlopeBands(bands)`로 갱신하고 `ready`로 둔다. 열린 화면 전체가 그 자리에서 새 색으로 바뀐다.
- **저장소에 값이 한 번 쓰이면 그 전에 떠난 첫 읽기 응답은 버린다.** 첫 읽기가 늦게 오면 저장한 값을 옛 값으로
  되돌린다.
- **편집은 `ready`일 때만 연다(6.1).** `error` 상태에서 열면 초안이 기본값에서 시작해, 저장하는 순간 DB의 실제 설정을
  기본값 기반으로 덮어쓴다. `loading`에서 열면 같은 일이 응답 전에 생긴다.
- 공개 지도와 관리자 화면이 같은 훅을 쓴다. 지도·패널·카드로 props를 내려보내지 않는다.

기각: **경로 요약에 구간을 박아 둔다.** 지금 `summarizeSlopeRoute`는 조회 때 판정(`grade`)을 계산해 둔다. 구간도
그렇게 하면 범례를 저장한 뒤 목록을 다시 받기 전까지 옛 색이 남는다. 요약은 도(`slope`)만 들고, 구간은 그릴 때
현재 설정으로 고른다(5장).

다른 브라우저 탭에 열린 화면은 새로 고칠 때까지 옛 설정이다. 자주 바꾸지 않는 값이라 받아들인다.

## 4. 공개 지도

### 4.1 선 색과 외곽선

- 선 하나는 그 구간의 색 한 가지다. 굵기 5, 불투명도 0.85, 팝업은 그대로다.
- **모든 선 밑에 외곽선을 깐다** — 굵기는 **그 선의 굵기 + 3**(공개 지도 5 → 8), `interactive: false`, 클래스
  `ku-slope-casing`. 선마다 굵기가 다르다(관리자 작업 화면 5·선택 7, 편집 미리보기 9, 다른 경로 4) — 고정 굵기로 두면
  미리보기 선보다 외곽선이 가늘어 테두리가 되지 않는다. 불투명도는 그 선이 흐려질 때 같은 비율로 같이 흐려진다.
  - 어두운 거리 지도 위에서는 `#FFFFFF`(불투명도 0.6), 그 밖(밝은 거리 지도·위성)에서는 `#1C1917`(0.5).
  - **외곽선을 전부 먼저 그리고 선을 그 위에 그린다.** 구간마다 외곽선·선을 번갈아 그리면 다음 구간의 외곽선이 앞
    구간 선의 끝을 덮는다.
  - 관리자가 고르는 색은 아무 색이나 될 수 있어 색마다 대비를 맞출 방법이 없다. 외곽선은 색과 무관하게 선을
    바탕에서 떼어 낸다.
- 기각: **pane SVG에 CSS `drop-shadow`.** 코드가 한 줄이지만 지도 크기 SVG에 필터를 걸면 이동·확대 때마다 다시
  래스터화한다. 이 저장소는 노트북에서 SVG 지도가 버벅이는 문제를 이미 겪었다(`d9e0a20`의 드래그 끝 밀림과 그 뒤
  2026-10-06 재제보).

### 4.2 범례 막대와 툴팁 — `SlopeBandsLegend`

- 구간마다 같은 폭의 칸을 이은 막대다. 칸 너비를 %에 비례시키지 않는다 — 마지막 구간에 끝이 없다.
- 크기는 대충 확인할 정도로 작게 — 막대 높이 약 8px, 데스크톱 폭 약 200px, 눈금 글자 10px. 정확한 값은 구현에서
  `map-ui.css`에 둔다.
- **늘 보이는 것은 막대와 칸 사이 경계 눈금(`5.56%` 위, `3.18°` 아래)뿐이다.** 제목·구간 이름·기준선 줄은 두지 않는다.
  눈금은 지금 범례처럼 소수 둘째 자리까지 끝 0을 떼고 보인다.
- **툴팁**: 칸 위로 마우스를 올리거나 칸을 탭·클릭하면 그 칸의 이름(굵게)과 설명이 뜬다. 설명이 비어 있으면 이름만.
  - 마우스가 칸을 떠나면 닫힌다. 탭으로 연 툴팁은 같은 칸을 다시 탭하거나 다른 곳을 누르면 닫힌다.
  - 한 번에 하나만 열린다.
- 같은 컴포넌트를 관리자 모달의 미리보기(6.1)가 초안을 넣어 쓴다. 그래서 컴포넌트는 저장소를 직접 읽지 않고 구간을
  props로 받는다. 지도 위 범례(`SlopeLegend`)가 저장소에서 읽어 넘긴다.

### 4.3 위치

`FilterPanel` 안에서 빼서 지도 위에 띄운다. **경사도 필터가 켜져 있으면 늘 보이고, 끄면 사라진다.** 지금은
범례가 필터 패널 안에 있어 모바일에서 패널을 접으면 같이 사라진다.

- **데스크톱**: 오른쪽 아래, 지도 버튼 열(`.ku-map-actions`) 왼쪽에 바닥을 맞춘다. 버튼 열과 범례를 가로로 놓는 한
  컨테이너에 둬, 건물 패널이 열릴 때 버튼 열이 비키는 이동(`data-panel-open`)을 그대로 따른다. 버튼 열 폭이 언어에
  따라 달라도 따로 숫자를 맞추지 않는다. 지금 `.ku-map-actions`는 세로 열(`flex-direction: column`)이라 범례를 그
  안에 넣으면 버튼 위로 쌓인다 — 바깥에 가로 컨테이너를 하나 둔다.
- **모바일**: 둘러보기 트리거(`.ku-map-browse`) 위, 버튼 열 왼쪽 폭. 바닥 위치는 `.ku-map-browse`의 `bottom`에 묶인
  값이라 그 옆에 주석으로 묶는다. 바텀시트나 필터 오버레이가 열리면 버튼 열과 같은 규칙(`data-panel-open`,
  `data-overlay-open`)으로 숨긴다.

### 4.4 접근성

- 칸은 `<button type="button">`이다. 접근 이름은 `{이름}, {범위}`다. 범위는 첫 구간 `5.56% 이하 (3.18°)`, 가운데
  `5.56–8.33% (3.18–4.76°)`, 마지막 `12.5% 초과 (7.13°~)` 꼴이다(지금 범례의 숨김 목록과 같은 꼴).
- 열린 툴팁은 `role="tooltip"`이고 칸이 `aria-describedby`로 가리킨다. 키보드 포커스가 들어오면 열리고 나가면
  닫히며, Esc로 닫힌다.
- 막대 묶음은 `role="group"`, 이름 `경사도 범례`. 지금의 화면 낭독용 숨김 목록은 칸 버튼이 같은 내용을 읽어
  지운다.
- 범례는 지금처럼 한국어만이다. 이름·설명이 관리자 입력값이라 번역은 범위 밖(10장)이다.

## 6. 범례 편집

자주 쓰지 않을 기능이라(2026-10-19 동우) 최소로 만든다. 동시 편집 검사, 변경 이력, 닫을 때 확인은 두지 않는다.

### 6.1 진입과 모달 — `SlopeBandsModal`

- 진입은 경사도 작업 화면의 `범례 편집` 버튼 하나다. 다른 탭에는 없다. 목록 패널(`WorkspaceListPanel`)은 이 버튼을
  선택 props(`legendAction`)로 받는다. 시설·명소 탭은 넘기지 않아 화면이 그대로다.
  - 데스크톱: 목록 패널 맨 아래 범례 옆.
  - 모바일: 바텀시트 맨 아래 고정 줄. 지금 모바일 분기는 범례를 그리지 않고(시설 탭이 넘기는 범례도 마찬가지),
    이번에도 범례 목록은 더하지 않는다 — 버튼만이다. 시트 머리줄은 이미 제목·개수·정렬·`＋ 추가`로 차 있다.
  - 저장소가 `ready`가 아니면 버튼이 비활성이다(3장). `error`면 버튼의 `title`과 접근 설명이 `범례 설정을 읽지 못해
편집할 수 없어요. 새로 고친 뒤 다시 시도해 주세요`다.
- 모달은 `FeedbackEmailModal`과 같은 꼴이다(`useModalFocus`, 세션 토큰으로 API 호출). 화면 가운데에 뜨고, 폭 90%·최대
  560px, 높이 최대 90vh에 본문이 스크롤된다. 데스크톱·모바일 같다. 좁은 폭에서는 구간 행이 두 줄(`색 · 이름 · ✕` /
  `상한 · 설명`)로 접힌다.
- 맨 위: 미리보기 — `SlopeBandsLegend`(4.2)에 초안을 넣는다. 툴팁도 공개 지도와 같이 확인된다.
  - **툴팁이 열려 있는 동안 모달의 Esc 닫기를 끈다**(`useModalFocus`의 `closeOnEscape`). 그 훅은 document 캡처
    단계에서 Esc를 받아 전파를 멈추고 모달을 닫아, 툴팁을 닫으려던 Esc가 초안째 모달을 닫는다. 범례 컴포넌트가 툴팁
    열림을 콜백(`onTooltipOpenChange`)으로 알리고, 모달은 `closeOnEscape: !saving && !tooltipOpen`을 넘긴다.
- 단위 선택 `도(°) / 퍼센트(%)`. 경로 편집 패널과 같은 기억값(`useSlopeRouteDraft`의 `ku_slope_input_unit`)을 쓴다.
- 구간 행 — 낮은 구간부터, 한 줄에 `색 · 이름 · 상한 · 설명 · ✕`.
  - 색: 브라우저 색 선택기(`<input type="color">`)와 hex 입력란.
  - 상한: 마지막 행은 입력란 대신 `그 위 전부`. 입력란 옆에 다른 단위 환산값(편집 패널의 구간 카드와 같은 꼴).
  - ✕: 구간이 2개면 비활성. 마지막 행을 지우면 바로 앞 행이 새 마지막이 되어 상한을 잃는다.
- `구간 추가`: 마지막 구간 바로 앞에 이름·상한이 빈 행을 넣는다. 6개면 비활성. 색은 앞 구간의 색이다.
- `기본값으로`: 초안을 `DEFAULT_SLOPE_BANDS`로 채운다. 저장해야 반영된다.
- 검증 문구(2.4)는 저장 버튼 위에 목록으로. 통과하지 못하면 `저장` 비활성.
- 저장 성공: `setSlopeBands`(3장), 토스트 `범례를 저장했어요`, 모달 닫힘. 실패: 모달에 오류 문구, 초안 유지.

### 6.2 손대지 않은 상한은 정확한 값 그대로

입력란에는 `5.56`·`8.33`이 보이지만 기본 상한은 `WALKWAY_RATIO * 100`(5.5555…)·`RELAXED_RATIO * 100`(8.3333…)이다.
**화면 문자열을 다시 읽어 저장하면 경계가 반올림한 쪽으로 움직인다**(2026-10-06 설계 2.2의 표와 같은 실패).

- 1/12는 `8.33`으로 내려가, 정확히 1/12인 구간(8.3333…%)이 다음 칸으로 밀린다.
- 1/18은 `5.56`으로 올라가, 원래 둘째 칸이던 5.5556~5.56% 구간이 첫 칸으로 들어온다.

그래서:

- 초안은 구간마다 `upperPercent`(숫자)와 입력 문자열을 따로 든다. 숫자는 **그 칸을 사용자가 고쳤을 때만** 문자열을
  읽어 바꾼다.
- 단위를 바꾸면 숫자는 그대로 두고 문자열만 새 단위로 다시 쓴다(2026-10-06 설계 3.3과 같은 규칙).
- % 입력은 친 그대로, ° 입력은 `degToPercent` 결과를 반올림하지 않고 숫자로 든다.
- **도로 친 값은 바꾸기 전에 `0 < 값 ≤ 45`로 검사한다.** `tan`은 주기 함수라 `190°`가 약 17.6%로 바뀌어 2.4의 %
  검사를 통과한다(2026-10-06 설계 3.2와 같은 실패). % 로 친 값은 `0 < 값 ≤ 100`. 범위 밖이면 그 칸 아래에 문구를 두고
  숫자를 바꾸지 않으며 `저장`이 비활성이다.
- 행을 추가·삭제해도 다른 행의 숫자와 문자열은 그대로다. `기본값으로`는 숫자를 기본값 상수로, 문자열을 지금 단위로
  다시 쓴다.

### 6.3 API — `POST /api/settings/slope-bands`

- `requireAdmin`(`src/lib/requireAdmin.ts`) → `validateSlopeBands` → `supabaseAdmin()`(`src/lib/server/supabaseAdmin.ts`)으로
  `app_settings` upsert(`key: "slope_bands"`, `updated_at` 갱신) → `{ ok, value }`. 다른 관리자 API 라우트와 같은 짝이다.
- 검증 실패는 400과 첫 오류 문구. 폼이 같은 검증을 먼저 하므로 정상 경로에서는 나오지 않는다.
- `requireAdmin`은 로그인만 보고 역할을 보지 않는다 — `docs/TODO_list/auth/require-admin-role-check.md`. 이 라우트도
  같은 문턱이고, 그 TODO를 풀면 같이 좁혀진다.
- 피드백 메일 라우트(`/api/settings/feedback-emails`)는 자기 안의 `verifyAdmin`을 쓴다. 이 변경에서는 손대지 않는다.
- `revalidatePath`는 부르지 않는다. 공개 지도는 클라이언트에서 설정을 읽는다.
- 동시 편집 검사는 하지 않는다. 나중에 저장한 쪽이 이긴다.
- `feat/activity-log`(2026-10-19 작성 중)의 감사 로그 설계 5.5가 설정 키를 한글 이름으로 바꾼다. 그쪽이 병합되면
  `slope_bands` → `경사도 범례`를 더한다. 이 브랜치는 그 문서에 손대지 않는다 — 아직 그 브랜치에서도 커밋 전이다.

## 9. 테스트 계획

### 9.1 vitest

- `validateSlopeBands`: 구간 1·7개 거부, 2·6개 통과. 상한이 같거나 역순이면 거부. 앞 상한 `5`에 `5.009` 거부,
  `5.01` 통과(최소 간격). `0`·`100.01` 거부, `100` 통과.
  마지막 구간에 상한이 있거나 중간 구간에 없으면 거부. 이름이 공백뿐이거나 21자면 거부. 설명 201자 거부.
  색 `#FFF`·`red` 거부, `#ffd600`은 `#FFD600`으로 정규화.
- `readSlopeBands`: `null`, 배열 아닌 `bands`, 검증 실패 값은 기본값.
- `slopeBandIndexFromDeg`: 기본값에서 각 경계(포함)와 그 바로 위, `0`, 음수 도(절댓값), `45`(마지막).
  % 입력 왕복 — `WALKWAY_RATIO*100`·`RELAXED_RATIO*100`·`RAMP_EXCEPTION_RATIO*100`을 `percentToDeg`로 바꿔 넣으면
  그 경계의 구간이다(2026-10-06 설계 8.2와 같은 실패를 고정).
- `readableTextOn`: 기본 4색 각각.
- 저장소(`slopeBandsStore`): 행 없음 → `ready`·기본값, 조회 오류 → `error`·기본값, 깨진 값 → `ready`·기본값.
  첫 읽기 응답 전에 `setSlopeBands`를 부르고 그 뒤 응답을 풀면 저장한 값이 남는다. 모듈 상태는 테스트마다 모듈을
  다시 불러 비운다(`vi.resetModules`).
- 상한 입력 해석(모달 초안 함수): ° `190`·`45.01`·`0` 거부, `45` 통과. % `100.01`·`0` 거부. 손대지 않은 행은
  단위를 몇 번 바꿔도 숫자가 그대로(`Object.is`).
- `slopeScale.test.ts`: 연속 색·판정 색 테스트를 지운다. 경고 테스트는 그대로.
- `slopeWorkspace.test.ts`: 판정 수·배지 tone·칩 개수 테스트를 지우고, 배지는 형식 오류만 남는지 본다.

### 9.3 Playwright — 새로

공개 지도:

- 경사도를 끄면 범례가 없고, 켜면 지도 위에 뜬다. 필터 패널을 접어도(모바일) 남는다.
- 눈금 `5.56%`·`3.18°`·`8.33%`·`4.76°`·`12.5%`·`7.13°`가 보이고 구간 이름은 보이지 않는다.
- 칸에 마우스를 올리면 이름·설명 툴팁이 뜨고, 마우스가 떠나면 사라진다. 마지막 칸은 이름만. 탭으로 열고 다시 탭해
  닫는다. 포커스로 열고 Esc로 닫는다.
- 데스크톱: 범례 상자가 지도 버튼 열과 겹치지 않는다(경계 상자 비교). 건물 패널을 열면 같이 비킨다.
- 모바일: 범례가 둘러보기 트리거와 겹치지 않는다. 바텀시트를 열면 숨는다.
- 목 백엔드에 3구간 `slope_bands`를 넣으면 선 색과 눈금이 그 값을 따른다. 깨진 값을 넣으면 기본값이다.
- 선 밑에 `ku-slope-casing` 외곽선이 있고 클릭은 선이 받는다(팝업이 뜬다).

관리자:

- 칩 줄이 없다. 보기 패널 구간 표의 `범례` 열.
- `범례 편집` → 상한 하나를 바꿔 저장 → 목 백엔드가 받은 본문 → 작업 화면 선 색이 다시 조회하지 않고 바뀐다.
- 모바일 폭에서 바텀시트 맨 아래 `범례 편집`으로 같은 모달이 열린다.
- **아무것도 고치지 않고 저장하면 상한이 기본값 상수(`WALKWAY_RATIO * 100`·`RELAXED_RATIO * 100`·`RAMP_EXCEPTION_RATIO * 100`)와
  같은 값으로 간다**(6.2). 기대값을 `100/12`로 적지 않는다 — `(1/12)*100`은 `8.333333333333332`, `100/12`는
  `8.333333333333334`다.
- 단위를 °로 바꿔도 손대지 않은 상한이 그대로 간다. ° 단위에서 `190`을 치면 문구가 뜨고 `저장`이 비활성이다.
- 미리보기 칸에 포커스해 툴팁을 열고 Esc → 툴팁만 닫히고 모달과 초안은 남는다. 한 번 더 Esc → 모달이 닫힌다.
- 목 백엔드의 `app_settings` 조회가 실패하면 `범례 편집`이 비활성이다.
- 상한을 역순으로 넣으면 검증 문구가 뜨고 `저장`이 비활성이다.
- 2개일 때 ✕ 비활성, 6개일 때 `구간 추가` 비활성.
- `기본값으로` → 저장 본문이 기본값.
- 번호 원: 기본 빨강 구간 카드의 글자색이 흰색.
- `e2e/admin-dark.spec.ts`가 하드코딩한 밝은 색을 검사하는 화면에 모달을 더한다 — 모달이 테마 토큰을 써야 통과한다.

## 11. 구현 시 확인할 것

- Leaflet의 `interactive: false` 경로는 `leaflet-interactive` 클래스가 없고 클릭이 아래로 지나간다. 외곽선이 선보다
  굵어 선 바깥 1.5px에서 클릭이 지도로 가는 것은 지금과 같다(선 굵기는 그대로).
- react-leaflet에서 외곽선을 선보다 먼저 마운트해도, 구간 설정이 바뀌어 선만 다시 그려질 때 순서가 유지되는지 —
  SVG 렌더러는 레이어를 추가 순서대로 붙인다. 순서가 깨지면 외곽선과 선을 별도 pane으로 나눈다.
- `useSyncExternalStore`의 서버 스냅샷과 첫 클라이언트 스냅샷이 같은 객체인지(기본값 상수) — 다르면 hydration 경고.
- 목록 패널의 칩 줄 생략이 시설·명소 탭에 영향이 없는지 — 두 탭은 칩이 있다.
- 6구간일 때 데스크톱·모바일 막대 폭에서 경계 눈금 글자가 겹치지 않는지(2.4).
- `AGENTS.md` 지시대로 라우트 핸들러를 쓰기 전 `node_modules/next/dist/docs/`의 해당 가이드를 읽는다.
