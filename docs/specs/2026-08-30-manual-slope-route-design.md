# 경사도 경로 수기 입력 설계

2026-08-30

## 이 문서의 목적

관리자가 지도에 경로를 직접 그리고 구간별 경사도를 손으로 입력하는 기능의 설계다.
동시에 기존 GPX 기반 경사도 파이프라인을 폐기하는 전환 계획이기도 하다.

이 문서는 **문서 하나만 읽고 검토할 수 있도록** 쓴다. 현행 동작, 폐기를 결정하게
만든 실제 데이터, 대안 비교를 설계보다 먼저 놓는다.

---

## 1. 프로젝트 배경

`ku-barrier-free-map`은 고려대학교 캠퍼스의 접근성 시설(엘리베이터, 경사로, 장애인
화장실, 점자블록 등)을 모아 보여주는 웹 지도다.

- Next.js 16 App Router / React 19
- Supabase (PostgREST + RLS). 프론트가 `@supabase/supabase-js`로 직접 읽고 쓰며,
  일부는 `/api/*` 라우트 핸들러를 경유한다
- Leaflet + react-leaflet (공개 지도), Leaflet + `@geoman-io/leaflet-geoman-free`
  (관리자 기하 편집)
- 화면은 크게 둘이다. 공개 지도 `/` 와 관리자 `/admin/*`
- 테스트는 vitest와 Playwright 두 층이다
  - vitest는 `environment: "node"`다. **DOM이 없어 컴포넌트 테스트를 못 한다.**
    현재 모든 단위 테스트가 `src/lib/*.test.ts` 형태의 순수 로직 테스트인 이유다
  - Playwright는 `e2e/support/mockBackend.ts`가 `page.route`로 Supabase와 `/api/*`를
    네트워크 레벨에서 흉내 낸다. 실제 서버 없이 도는 in-memory 목이고 `slopes`
    상태를 이미 들고 있다

경사도는 공개 지도의 필터 토글 하나로 켜고 끄는 오버레이다. 기본값은 꺼짐이다.

## 2. 현행 경사도 파이프라인

### 2.1 데이터베이스

```
slope_segments
  id         uuid
  name       text          -- 경로 이름
  gpx_file   text          -- 업로드한 파일명
  segments   jsonb         -- 포인트 배열
  created_at timestamptz
  updated_at timestamptz
```

RLS는 `anon, authenticated` SELECT 허용, `authenticated` 전체 쓰기 허용이다
(`supabase/migrations/20260612163920_fix_slope_rls.sql`).

`segments`의 원소 타입은 `src/types/domain.ts`에 있다.

```ts
export interface SlopePoint {
  lat: number;
  lng: number;
  ele: number | null;
}
```

### 2.2 등록 — `src/app/admin/dashboard/slopes/page.tsx`

관리자가 GPX 파일을 고르면 브라우저에서 `DOMParser`로 파싱한다. `trkpt`의
`lat`/`lon` 속성과 자식 `ele`를 읽어 셋 중 하나라도 `NaN`이면 버린다. 살아남은
포인트가 2개 미만이면 업로드를 거부한다.

**경사도는 이 시점에 계산하지 않는다.** 원시 좌표만 그대로 `segments`에 넣는다.
파일명(확장자 제외)이 곧 경로 이름이 된다.

같은 파일에 `buildGpx()` / `downloadGpx()`가 있어 저장된 포인트로 GPX를 재구성해
내려받을 수 있다. 고도를 `ele` 엘리먼트로 문자열 보간해 만든다.

### 2.3 조회 — `src/app/api/slopes/route.ts`

```ts
supabase.from("slope_segments").select("id, name, segments");
```

`gpx_file`은 가져오지 않는다.

### 2.4 표시 — `src/components/map/SlopeLayer.tsx`

경사도 계산이 전부 여기서, 렌더링할 때마다 일어난다.

1. `medianFilter(points, half = 2)` — 각 포인트의 고도를 앞뒤 2개씩 총 5개의
   중앙값으로 치환한다
2. `processRawPoints()` — 포인트를 순회하며 haversine 거리를 누적하다가 **10m를
   넘으면** 한 구간을 끊는다. 마지막 포인트는 5m만 넘어도 끊는다.
   구간 경사는 `(고도차 / 누적거리) * 100`이다.
   **마지막 남은 거리가 5m에 못 미치면 구간을 새로 만들지 않고 직전 구간의
   끝 좌표만 마지막 포인트로 늘린다.** `distance`와 `slope`는 다시 계산하지 않아서,
   지도에 그려진 선의 실제 길이와 팝업에 뜨는 거리·경사가 어긋난다
3. 절댓값이 **30%를 넘으면 0으로 대체한다** (노이즈로 간주)
4. 구간마다 `Polyline`을 그리고 `slopeColor()`로 색을 정한다. 팝업에 경사와
   구간 거리를 띄운다

이 컴포넌트에는 포맷 자동 감지 분기가 있다.

```ts
const segs: MetricPoint[] =
  raw[1]?.slope !== undefined
    ? (raw as MetricPoint[]) // 구버전: 저장된 값을 그대로 그린다
    : processRawPoints(raw); // 신버전: 원시 좌표에서 계산한다
```

과거에는 경사도를 계산해서 저장했고 지금은 원시 좌표만 저장한다. 그 두 세대를
같이 읽으려고 남겨둔 호환 분기다. **이 설계는 이 분기를 적극적으로 활용한다.**

색상 기준은 `src/lib/theme.ts`의 `slopeColor()`다. 1% 이하 회색, 2% 이하 노랑,
5% 이하 주황, 8.33% 이하 진주황, 12% 이하 적갈, 초과는 암적색이다. 8.33%는
건축법상 경사로 기준 1/12이다.

### 3.1 물리적으로 불가능한 고도

`2026-06-08_18-42_월`은 경로 총길이가 202m인데 고도 범위가 28.4~83.8m다. 고도차
55m를 202m 만에 오르면 평균 27% 경사다. 걸어서 다니는 캠퍼스 보행로일 수 없다.

`안암병원_r_d센터_삼거리`는 전체 고도차(10.6m)만 보면 그럴듯하지만 점 사이
경사의 최댓값이 **282.3%**다. 총량은 맞고 점 단위 신호는 잡음이라는 뜻이다.
스마트폰 GPS 고도의 전형적인 실패 양상이다.

### 3.2 더 위험한 문제 — 조용히 0%가 된 구간

최종 표시 137개 중 **31개(23%)가 0.0%, 즉 회색 평지로 그려진다.** 30% 클램프에
걸려 0이 된 것은 5개뿐이고 나머지는 median 필터와 10m 누적 과정에서 고도차가
상쇄된 결과다.

`안암병원_정문_경사`가 대표적이다. 34개 포인트를 찍었지만 경로 길이가 42m뿐이라
10m 구간이 4개밖에 나오지 않고, 그중 하나가 0.0%다. 병원 정문 경사로가 평지로
표시된다.

**배리어프리 지도에서 경사로를 평지로 표시하는 것은 튀는 값보다 위험하다.**
휠체어 이용자가 이 정보를 보고 경로를 고르기 때문이다.

### 3.3 짧은 경사로를 원리적으로 담을 수 없다

10m 누적 임계값 때문에 10m가 안 되는 램프는 구간이 하나도 만들어지지 않거나,
만들어져도 GPS 고도 오차(수 m)가 실제 고도차(수십 cm)보다 커서 값이 무의미하다.
건물 진입 램프가 정확히 이 범주다.

### 3.4 부수적인 문제

- 이름이 `2026-06-08_18-42_월`인 행이 둘 있다. 파일명을 그대로 경로 이름으로
  쓰는 구조라서 어느 길인지 알 수 없다
- `_clean` 접미사가 붙은 행이 둘 있다. 이미 사람이 손본 흔적인데도
  `R_D센터_앞_clean`에는 25.0%, 28.2% 같은 값이 남아 있다. 수동 정제로는
  해결되지 않는다는 증거다

### 3.5 기존 설계 문서와의 관계

`docs/future-development/accessible-routing.md`는 이미 같은 결론에 도달해 있다.
"GPX는 길 자체가 아니라 경사도를 측정한 원본 자료로 취급해야 한다", "지도에
표시되는 선에는 관리자가 검수한 보행로 중심선을 사용한다"고 적혀 있다.

이 설계는 그 방향의 축소판이다. 다만 그 문서가 전제하는 `walkway_nodes` /
`walkway_edges` 정식 그래프는 5단계짜리 별도 과제이므로 **이번 범위에 넣지
않는다.** 이번에 만드는 데이터는 나중에 그 모델로 옮겨질 대상이다.

## 4. 결정 사항

### 4.1 GPX를 폐기하고 현장 실측 수기 입력으로 전환한다

관리자가 현장에서 경사계나 스마트폰 수평 앱으로 잰 값을 직접 입력한다. GPS 고도에
의존하지 않으므로 3장의 문제가 원인 단계에서 사라진다. 짧은 램프에서 특히 잘
맞는다.

기존 10개 행은 **기능이 완성된 뒤 일괄 삭제한다.** 그 전까지는 그대로 둔다.
따라서 v1 기간 동안 GPX 행과 수기 행이 한 테이블에 공존한다.

### 4.2 저장 포맷은 기존 "구버전" 포맷을 재사용한다

검토한 대안은 셋이다.

**A. 기존 구버전 포맷 재사용 (채택)**

포인트에 `slope`와 `distance`를 실어 저장한다. 2.4절의 감지 분기가 이미 이 모양을
읽을 줄 안다. 마이그레이션이 없고 `SlopeLayer` 변경이 없다. GPX를 폐기하는 순간
이 포맷이 자동으로 유일한 포맷이 되므로 정리가 공짜로 따라온다.

**B. `slope_routes` 신규 테이블**

꼭짓점과 구간을 정규화한다. 의미는 가장 명확하지만 마이그레이션, API 신설, 지도
레이어 이중화가 붙는다. GPX 폐기 후에도 테이블이 둘 남거나 한 번 더 옮겨야 한다.
구간이 1~4개인 데이터에서 정규화의 이점이 비용을 넘지 못한다.

**C. `segments` jsonb 스키마 재정의**

`{ vertices, slopes }` 객체로 바꾼다. 의미는 살지만 폐기 전까지 `SlopeLayer`가
포맷 3종을 알아야 한다.

### 4.3 경사도는 꼭짓점 사이 구간마다 하나씩 입력한다

경로 전체에 값 하나를 받는 방식은 짧은 램프에는 맞지만 경사가 변하는 길에 쓸 수
없다. 데이터 모델은 어차피 구간별이므로 나중에 확장할 필요가 없고, 짧은 램프는
꼭짓점 2개를 찍고 값 하나만 넣으면 되므로 두 경우가 모두 덮인다.

### 4.4 주 대상은 짧은 경사로다

건물 진입 램프, 계단 옆 경사로, 병원 정문처럼 길이가 10m에서 50m 사이인 구간이다.
경로당 꼭짓점 2개에서 5개, 구간 1개에서 4개를 상정한다.

409m짜리 경로에 꼭짓점 30개를 찍으면 경사도를 30번 실측해서 30번 입력해야 한다.
현장에서 불가능하므로 긴 보행로는 이번 대상이 아니다. 이 전제 때문에 "모든 구간에
같은 값 일괄 적용" 같은 장치를 넣지 않는다.

### 4.5 `ele`는 v1에서 `null`, 2단계에서 폐기한다

수기 입력은 고도를 쓰지 않는다. 그렇다고 지금 바로 필드를 빼면 `SlopePoint`의
`ele: number | null`을 `ele?: number | null`로 완화해야 하고, 그러면 **아직 살아
있는 GPX 행에 대한 타입 보증이 같이 풀린다.** `processRawPoints`가 `pt.ele ?? 0`으로
읽기 때문에 고도가 없어도 조용히 0으로 계산된다. 3.2절에서 확인한 "0%로 뭉개짐"
버그와 정확히 같은 부류다.

그래서 v1에서는 `ele: null`을 명시해 타입을 그대로 두고, GPX가 사라지는 2단계에서
타입과 함께 완전히 없앤다.

## 5. 설계

### 5.1 데이터 모델

마이그레이션이 없다. `slope_segments` 스키마를 그대로 쓴다.

꼭짓점 3개짜리 램프는 이렇게 저장된다.

```jsonc
{
  "name": "안암병원 정문 경사로",
  "gpx_file": null,
  "segments": [
    { "lat": 37.5861, "lng": 127.0268, "ele": null },
    {
      "lat": 37.5862,
      "lng": 127.0269,
      "ele": null,
      "slope": 7.2,
      "distance": 12.4,
    },
    {
      "lat": 37.5863,
      "lng": 127.0271,
      "ele": null,
      "slope": 4.5,
      "distance": 8.0,
    },
  ],
}
```

- 첫 포인트에는 `slope`와 `distance`가 없다. 구간은 앞 포인트에서 이 포인트까지를
  뜻하므로 시작점에는 구간이 없다. `SlopeLayer`가 `segs.slice(1)`로 순회하는 것과
  맞는다
- `slope`는 관리자 실측값이다. 음수는 받지 않는다(0은 허용한다). `SlopeLayer`가
  `Math.abs()`로 표시하고, 경로는 양방향 통행이라 오르막/내리막 구분에 의미가 없다
- `distance`는 꼭짓점 좌표에서 haversine으로 계산한다. 입력받지 않는다
- `gpx_file`이 `null`인 것이 수기 경로의 판별자다

**관리자가 실제로 타이핑하는 것은 경로 이름 하나와 구간마다 숫자 하나가 전부다.**
좌표는 지도 클릭에서, 거리는 좌표에서 나온다.

2.4절의 감지 분기가 `raw[1]?.slope !== undefined`를 보므로 두 번째 포인트에
`slope`가 있으면 구버전 경로로 인식된다. 값이 `0`이어도 `0 !== undefined`라
정상 동작한다.

### 5.2 파일 구성

vitest가 node 환경이라 컴포넌트를 테스트할 수 없다. 그래서 **테스트 가능한 경계와
파일 경계를 일치시킨다.** 판단이 필요한 로직은 전부 순수 함수로 빼고 컴포넌트는
얇게 유지한다.

| 파일                                        | 상태 | 책임                                                  |
| ------------------------------------------- | ---- | ----------------------------------------------------- |

#### 5.2.1 인증은 페이지가 직접 확인한다

**`/admin/slopes/*`는 `/admin/dashboard/layout.tsx` 바깥이라 그 레이아웃의 인증

페이지 안에서 같은 검사를 따로 한다.

신규 두 페이지도 `buildings/new`와 같은 방식으로 **페이지 안에서 인증을 확인하고
비로그인이면 `/admin`으로 리다이렉트한다.** 빠뜨리면 비로그인 사용자에게 편집
UI가 그대로 노출된다. `slope_segments`는 `anon` SELECT가 열려 있어 기존 경로
데이터까지 함께 보인다.

#### 5.2.2 저장 포맷 타입

현재 `SlopePoint`에는 `slope`와 `distance`가 없다. `SlopeLayer`가 파일 안에서
`StoredPoint` / `MetricPoint`를 따로 선언해 쓰고 있다. 편집기와 수정 페이지가
저장된 경사값을 읽어야 하므로 그 타입이 `domain.ts`에 있어야 한다. 없으면 지역
중복 타입이나 캐스팅으로 때우게 된다.

**union으로 만들지 않는다.** `{ lat, lng, ele }`와 `{ lat, lng, ele, slope }`의
union은 `point.slope` 접근이 컴파일되지 않는다. 측정형 쪽에 그 속성이 없기
때문이다. 두 세대를 구분하는 것은 타입이 아니라 `slope`의 존재 여부이므로,
**선택 속성 하나짜리 인터페이스**가 정확한 모델이다.

```ts
export interface SlopePoint {
  lat: number;
  lng: number;
  /** GPX 측정 원본에만 있다. 수기 경로는 null (2단계에서 제거) */
  ele: number | null;
  /** 수기 경로의 구간 값. 첫 포인트에는 없다 */
  slope?: number;
  distance?: number;
}
```

`SlopeLayer`가 파일 안에 들고 있는 `StoredPoint`는 정확히 이 모양이다. 지역
타입을 지우고 이 타입을 쓴다. `SlopeSegment`는 이미 `segments: SlopePoint[]`이므로
연결이 그대로 유지된다.

2단계에서 GPX가 사라지면 `ele`를 없애고, 첫 포인트를 제외하면 `slope`·`distance`가
항상 있으므로 선택 속성 표기도 정리한다.

### 5.3 상태 모델과 불변식

```ts
{
  name: string;
  vertices: { lat: number; lng: number }[];
  slopes: (number | null)[];   // 미입력은 null
}
```

불변식은 하나다.

```
slopes.length === Math.max(0, vertices.length - 1)
```

이것이 `slopeRoute.ts`의 계약이고 단위 테스트의 중심이다.

### 5.4 편집기 동작

`SlopeRouteMap`은 geoman을 폴리라인 그리기만 켠 채로 띄운다. 나머지 도구
(폴리곤, 마커, 원, 사각형, 잘라내기)는 모두 끈다. `PolygonEditor`가 하는 것과
같은 방식이고, 그 파일에서 `drawPolyline: false`로 꺼둔 옵션을 켜는 것이다.

`PolygonEditor`처럼 경로는 **하나만** 허용한다. `pm:create`가 오면 그린 레이어를
받아두고 `disableDraw`와 `Toolbar.setButtonDisabled`로 그리기 버튼을 잠근다.
편집기를 기존 경로로 열 때도 처음부터 잠근 채 시작한다. 다시 그리려면
"경로 지우고 다시 그리기"로 레이어와 입력값을 함께 비우고 버튼을 되살린다.
이 흐름이 없으면 폴리라인을 여러 개 그렸을 때 무엇을 저장할지가 정의되지 않는다.

#### 5.4.1 그리기가 끝나면 꼭짓점 개수를 고정한다

**꼭짓점 추가와 삭제를 허용하지 않는다.** geoman 옵션 두 개로 막는다.

- `hideMiddleMarkers: true` — 변의 중간점 핸들을 없애 꼭짓점 삽입을 막는다
- `preventMarkerRemoval: true` — 꼭짓점 삭제를 막는다

**위치 조정은 드래그로 얼마든지 할 수 있다.** 꼭짓점 하나를 끌거나 선 전체를
옮기는 것은 개수와 순서를 바꾸지 않는다. 형상 자체가 잘못됐으면 "지우고 다시
그리기"로 처음부터 그린다. 꼭짓점 2~5개짜리 경로에서 다시 그리는 비용은 클릭
몇 번이다.

이 제약의 대가로 **구간과 입력값의 대응이 그리기 직후에 확정되고 그 뒤로 절대
어긋나지 않는다.** `slopes.length`는 `pm:create` 이후 변하지 않으므로 값을 옮겨
붙이는 로직이 아예 없다. 값이 엉뚱한 구간에 붙는 사고의 여지도 함께 사라진다.

**이벤트는 "뭔가 바뀌었다"는 신호로만 쓰고, 좌표는 항상 레이어에서 다시 읽는다.**
어떤 이벤트가 왔는지로 무슨 편집이었는지 추론하지 않는다.

- 변경 신호를 받으면 `layer.getLatLngs()`로 좌표 전체를 다시 읽는다
- `slopes`는 건드리지 않는다
- **모든 구간의 `distance`를 다시 계산한다**

거리를 반드시 다시 계산하는 이유는, 선 전체 이동이 화면에서는 평행이동이어도
위도·경도가 바뀌기 때문이다. 경도 1도의 실제 길이는 위도에 따라 달라지므로
haversine 거리가 보존되지 않는다. 5.1절이 "`distance`는 저장 좌표에서 계산한다"고
못박은 이상, 거리는 들고 다니는 값이 아니라 좌표에서 매번 유도하는 값이어야 한다.

**`pm:vertexadded`는 구독하지 않는다.** geoman은 이 이벤트를 그리는 중에도 클릭
할 때마다 발생시키며(`_fireVertexAdded(marker, void 0, latlng, "Draw")`), 그때
`indexPath`는 `undefined`다. 또 이 이벤트는 지도가 아니라 레이어에 발생한다
(타입 선언 파일도 `DRAW MODE EVENTS ON LAYER ONLY`라고 적어 두었다). 꼭짓점
삽입을 막은 이상 구독할 이유가 없다.

`pm:edit`도 삽입·삭제 때 세부 이벤트보다 **먼저** 발생하므로 둘을 같이 구독하면
같은 변경이 두 번 처리된다. 좌표를 레이어에서 다시 읽는 방식은 몇 번 호출되든
같은 결과가 나오므로 이 문제를 받지 않는다.

방어적으로, `slopes.length !== vertices.length - 1`이면 저장을 막고 다시 그리기를
안내한다. 위 설계대로면 일어나지 않지만, 어긋난 상태로 저장되는 것보다 낫다.

#### 5.4.2 실시간 색상 미리보기

geoman 편집 레이어(얇은 실선) 아래에 구간별 색상 폴리라인을 별도 `FeatureGroup`
으로 그린다. 입력값이 바뀔 때마다 `slopeColor()`로 다시 칠해서 저장 전에 공개
지도와 같은 색을 확인할 수 있게 한다. geoman이 만드는 것은 폴리라인 하나라
구간마다 다른 색을 줄 수 없으므로 별도 레이어가 필요하다. 구간이 몇 개 없어
변경 때마다 통째로 재생성해도 무방하다.

**미리보기 레이어는 반드시 편집에서 배제한다.**

- `pmIgnore: true` — 없으면 geoman이 미리보기 선까지 편집 대상으로 잡아서,
  전역 편집 모드에서 색칠용 선에 꼭짓점 핸들이 붙는다
- `interactive: false` — 없으면 미리보기 선이 위에 깔려 편집 선으로 가야 할
  클릭을 가로챈다
- `map.createPane("slopePreview")`로 전용 pane을 만들고 `z-index`를 Leaflet 기본
  `overlayPane`(400)보다 낮은 350으로 준다. "아래에 그린다"를 말로만 두면 실제
  순서가 보장되지 않는다

`src/lib/neighborLayer.ts`가 배경 건물 레이어에 `interactive: false`를 주는 것과
같은 이유다.

#### 5.4.3 편집기는 `ssr: false`로 동적 로딩한다

`SlopeRouteMap`은 `leaflet`을 정적으로 import한다. 서버에서 실행되면 `window`가
없어 터진다. 그래서 페이지는 `PolygonEditor`와 똑같이 감싼다.

`src/app/admin/buildings/new/page.tsx:15`가 `dynamic(() => import(...), { ssr: false })`
를 쓰는 것과 같다. `src/lib/neighborLayer.ts`의 파일 주석도 같은 제약을 설명한다.
새 두 페이지 모두 이 방식으로 편집기를 불러온다.

### 5.5 검증

**저장을 막는 조건**

- 이름이 비어 있다
- 꼭짓점이 2개 미만이다
- 값이 입력되지 않은 구간이 있다
- 값이 유한한 수가 아니다 (`NaN`, `Infinity`). jsonb로 가면 `null`이 되어
  구간이 조용히 미입력 상태로 저장된다
- 값이 음수이거나 100을 초과한다
- 길이가 0m인 구간이 있다. 같은 자리를 두 번 클릭하면 생기며, 지도에 보이지도
  않고 경사를 정의할 수도 없다. 저장 전에 중복 꼭짓점을 걸러낸다

**상한을 100%에 두는 이유.** 초안은 30%였는데, 그 숫자는 `processRawPoints`가
**믿을 수 없는 GPS 고도를 노이즈로 버리는** 휴리스틱에서 가져온 것이다. 현장에서
직접 잰 값에는 그 근거가 없다. 30%를 넘는 경사로가 실재한다면 그것이야말로 이
지도가 반드시 실어야 할 정보인데, 상한으로 막으면 **가장 위험한 구간만 기록되지
않는다.**

100%는 경사로 기준이 아니라 **입력값의 상식 범위**다. 45도를 넘는 면은 보행
노면이 아니라 계단이나 벽이고, 이 테이블이 다루는 대상이 아니다. 이 선을 넘는
입력은 측정이 아니라 입력 사고로 본다.

**경고만 하고 저장은 허용하는 조건**

- 8.33%를 넘으면 "법적 기준(1/12) 초과"를 표시한다. 실제로 존재하는 경사로이므로
  오류가 아니라 정보다
- 30%를 넘으면 "이 값이 맞나요? 30%를 넘는 보행 경사로는 매우 드뭅니다"를
  강하게 표시한다. `7.2`를 `72`로 잘못 친 오타를 잡는 장치가 상한 대신 여기다.
  경고일 뿐 저장은 막지 않는다

### 5.6 목록 페이지 변경

`src/app/admin/dashboard/slopes/page.tsx`에 다음을 더한다.

- "경로 직접 그리기" 버튼. `/admin/slopes/new`로 이동한다
- `gpx_file === null`인 행에 "직접 입력" 배지와 "수정" 버튼을 노출하고
  **다운로드 버튼은 숨긴다.** `buildGpx()`가 고도를 그대로 문자열 보간하기 때문에
  수기 경로를 내려받으면 고도가 `null`로 찍힌 GPX가 나온다
- GPX 행은 조회·다운로드·삭제만 남긴다. 곧 폐기되므로 손대지 않는다
- **GPX 업로드는 v1에서 막는다.** 업로드 영역을 없애고 "GPX 등록은 종료됐어요.
  경로는 직접 그려서 등록해주세요"만 남긴다

업로드를 v1에서 닫는 이유는, 열어두면 **폐기 대상이 계속 늘어나기 때문**이다.
7절이 "기존 10개를 지운다"고 고정된 수를 말하는 동안 11번째 GPX 행이 생기면
정리가 끝나지 않는다. 애초에 3장에서 이 파이프라인을 못 믿겠다고 결론 낸 이상,
새 GPX를 더 받을 이유가 없다.

`/admin/slopes/[id]`는 수기 경로만 연다. GPX 경로 id로 접근하면 안내 후 목록으로
돌려보낸다. GPX 행을 편집 가능하게 만들면 측정 원본이 훼손된다.

### 5.7 에러 처리

기존 관례를 따른다.

- 저장 실패는 `Toast`(error)로 알리고 **그린 경로를 날리지 않는다.** 폼 상태를
  유지해 재시도할 수 있게 한다
- 삭제는 `ConfirmModal`을 거친다. 목록 페이지에 이미 있는 패턴이다
- 저장하지 않은 상태로 벗어나려 하면 건물 상세 화면과 같은 "저장하지 않은
  변경사항이 있어요" 경고를 띄운다

- **선을 완성한 뒤 변 중간에 꼭짓점을 끼울 수 없고, 꼭짓점을 지울 수도 없다**
  (5.4.1). 중간점 핸들이 아예 없는지 확인한다
- **꼭짓점을 드래그하면 입력값은 그대로 남고 구간 거리 표시만 바뀐다**
- 선을 하나 그린 뒤에는 폴리라인 그리기 버튼이 잠기고, "지우고 다시 그리기"로만
  풀린다. 다시 그리면 입력값도 함께 비워진다
- 값을 입력한 상태로 페이지를 벗어나려 하면 미저장 경고가 뜬다 (5.7절이 약속한
  동작)
- 수정 페이지에서 기존 수기 경로를 열면 구간 값이 채워진 채로 뜨고, 값을 고쳐
  저장하면 반영된다
- 목록에서 "경로 직접 그리기"로 편집기에 진입한다
- 시드한 수기 경로 행에 "직접 입력" 배지가 뜨고 다운로드 버튼이 없다
- **GPX 행의 id로 `/admin/slopes/[id]`에 가면 편집기가 열리지 않고 목록으로
  돌아간다** (5.6절이 약속한 동작)
- **비로그인 상태로 `/admin/slopes/new`와 `/admin/slopes/[id]` 둘 다 `/admin`으로
  리다이렉트된다** (5.2.1절이 약속한 동작)
- **저장이 실패해도 그린 경로와 입력값이 남아 있다** (5.7절이 약속한 동작).
  `mockBackend` 뒤에 `page.route`를 얹어 POST만 500으로 돌려 확인한다
- **저장한 수기 경로가 공개 지도의 경사도 오버레이에 실제로 그려진다.** 이 설계
  전체가 "저장 포맷을 `SlopeLayer`가 그대로 읽는다"에 걸려 있으므로 그 가정을
  끝단에서 한 번 확인한다

`mockBackend.ts`의 `slopes` 픽스처에 `gpx_file: null`이고 `slope`를 실은 행을
하나 추가한다. 이 목은 POST/PATCH를 in-memory로 반영하므로 저장 payload를 그대로
검증할 수 있다.

## 7. 2단계 폐기 계획

**삭제 기준은 "기존 10개"가 아니라 `gpx_file IS NOT NULL`이다.** 개수를 세어
지우면 놓치는 행이 생긴다. v1에서 업로드를 막았으므로(5.6) 이 집합은 더 늘지
않지만, 조건으로 지우는 편이 안전하다.

순서는 이렇다.

1. `gpx_file IS NOT NULL`인 행을 GPX로 내려받아 저장소 밖에 보관한다. 3장의
   결론은 "이 값을 믿지 않는다"이지 "측정 기록을 없앤다"가 아니다
2. 같은 조건으로 삭제한다
3. `select count(*) ... where gpx_file is not null`이 0인지 확인한다
4. 아래 정리를 별도 커밋으로 넣는다. 순서를 바꾸면 살아 있는 데이터가 안 그려진다

- `src/types/domain.ts` — `SlopePoint`에서 `ele`를 없애고, 첫 포인트를 제외하면
  항상 있는 `slope`·`distance`의 선택 속성 표기를 정리한다
- `src/components/map/SlopeLayer.tsx` — `processRawPoints`, `medianFilter`,
  레이어 내부 `haversine`, 이중 포맷 감지 분기 제거. 현재 119줄 중 계산 로직
  약 70줄이 사라지고 폴리라인 렌더링만 남는다
- `src/app/admin/dashboard/slopes/page.tsx` — v1에서 남겨둔 업로드 종료 안내와
  `buildGpx`·`downloadGpx`, 그리고 `gpx_file` 분기 제거. 모든 행이 수기 경로다
- `e2e/admin-buildings-slopes.spec.ts` — GPX 업로드/거부/다운로드 테스트와
  GPX 행 관련 분기 테스트 제거
- 남아 있는 수기 행의 `ele: null` 키는 **정리하지 않는다.** 읽는 코드가 없으면
  무해하고 jsonb 일괄 UPDATE는 순수 비용이다

## 8. 범위에서 제외한 것

- **구간 일괄 적용** — 구간이 1~4개라 필요 없다 (4.4)
- **공개 지도 팝업의 측정/수기 출처 표기** — GPX가 곧 사라지므로 구분할 대상이
  없어진다. `/api/slopes`의 `select`에 `gpx_file`을 더할 이유도 함께 사라진다
- **기존 `ramp` 시설 마커와의 연결** — 시설은 점 데이터, 경사도 경로는 선
  데이터로 성격이 다르다. 공존이 자연스럽고 연결은 별도 과제다
- **보행로 네트워크와 경로 탐색** — `docs/future-development/accessible-routing.md`의
  범위다 (3.5)
- **긴 보행로 수기 입력** — 실측 비용 때문에 성립하지 않는다 (4.4)

## 9. 검토자가 오인하기 쉬운 기존 동작

- `/admin/slopes/*`는 관리자 대시보드 레이아웃 **바깥**이다. 사이드바의 "경사도"
  탭이 강조되지 않는 정도가 아니라 **사이드바와 인증 검사 자체를 상속받지
  않는다.** `/admin/buildings/*`가 페이지마다 인증을 따로 확인하는 이유이며,
  이번 두 페이지도 같다 (5.2.1). 사이드바가 없는 것은 기존 편집기 화면과 동일한
  동작이므로 고치지 않는다
- **인증 확인은 로그인 여부까지고 관리자 역할은 보지 않는다.** 5.2.1절의 페이지
  검사도 `supabase.auth.getUser()`로 로그인만 본다. `slope_segments`의 RLS 역시
  `authenticated` 전체에 쓰기를 허용하므로, 일반 로그인 계정이 경사도 경로를
  만들고 고치고 지울 수 있다. 이것은 이번 설계가 넓히는 것이 아니라 관리자
  화면 전체의 기존 상태이며 `docs/TODO_list/auth/require-admin-role-check.md`에
  별도 과제로 잡혀 있다. 그 과제가 해결되면 이 두 페이지도 함께 적용받는다
- 공개 지도의 경사도 오버레이는 기본값이 꺼짐이다. 3장의 잘못된 데이터가 노출되는
  범위는 토글을 켠 사용자로 한정된다. 문제의 심각도를 낮추지는 않지만 전환을
  급하게 밀어붙일 이유는 아니다
