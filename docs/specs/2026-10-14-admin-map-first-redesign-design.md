## 1. 범위와 PR 나눔

PR마다 main에서 브랜치를 따고, 앞 PR이 병합된 뒤 다음을 시작한다. 각 PR은 그 화면의 모바일까지 담는다.
계획 문서는 PR마다 그 PR을 시작할 때 쓴다 — 뒤 PR의 계획은 앞 PR이 실제로 만든 컴포넌트에 기댄다.

| PR  | 범위                                                                                               |
| --- | -------------------------------------------------------------------------------------------------- |
| ①   | 이 사양과 핸드오버 원문, 토큰(3.6), 셸(3.1), 지도 작업 화면 공통 단위(3.2~3.5), **독립 시설**(4장) |
| ②   | **명소**(5장)                                                                                      |
| ③   | **경사도**(6장) — 판정 색, 보기·편집 패널, 옛 편집 라우트 리다이렉트                               |
| ④   | **제보함**(7장) — 상태별 보드와 검토 드로어                                                        |

건물 탭의 레이아웃은 범위 밖이다. 다만 토큰을 바꾸므로(3.6) 건물 화면의 주 버튼 색은 ①에서 같이 크림슨이 된다.

## 2. 핸드오버와 달라지는 결정

### 2.1 경사 판정 색

| 판정               | 핸드오버  | 이 설계   |
| ------------------ | --------- | --------- |
| ok (1/12 이하)     | `#3E7A46` | `#1B9E77` |
| over (1/12 초과)   | `#C27A12` | `#E6AB02` |
| extreme (30% 초과) | `#A31C12` | `#A50F15` |

핸드오버 3색은 OKLab ΔE×100, Machado 2009 색각 이상 시뮬레이션(2026-10-06 설계 4장과 같은 방법)으로 초록↔주황이
제1색약에서 7.7, 초록↔빨강이 제2색약에서 6.8이다. 2026-10-06 설계 11.1이 쓴 기준 8에 못 미친다. 초록과 빨강의 밝기가
비슷해 색약 시야에서 같은 갈색이 된다.

새 3색은 휠체어 경사 지도에서 흔한 초록·노랑·빨강 신호등 관례를 지키되, 초록은 밝고 푸르게, 빨강은 어둡게 밀어
밝기 차이로 갈리게 했다. 초록·겨자는 ColorBrewer Dark2, 빨강은 ColorBrewer Reds의 색이다. 같은 방법으로 세 쌍의
색각 이상 최소 13.8, 정상 시각 최소 24.2다. 색약 시야에서 회색·노랑·검정으로 갈린다.

기각한 대안:

- **파랑·주황·진홍(`#0465AF`·`#C27A12`·`#A31C12`).** 색각 이상 최소 17.2로 가장 잘 갈리지만 신호등 관례가 아니다.
- **Okabe-Ito(`#009E73`·`#E69F00`·`#D55E00`).** 주황과 주홍이 가까워 정상 시각 차이가 15.6이다.
- **공개 지도의 연속 색(`slopeColorFromDeg`)을 그대로.** 관리자 화면은 구간마다 판정 3단계를 읽는 화면이라
  (목록 배지·프로파일 막대·칩) 연속 색보다 단계 색이 맞다. 공개 지도는 연속 색을 유지한다.

대비 한계: 밝은 지도 바탕(`#F2F2F0`)에서 겨자 1.8:1, 어두운 지도 바탕(`#2B2B2B`로 가정)에서 빨강 1.8:1이다. 지도
위에서는 선택 경로의 구간 번호와 상세 패널의 구간 표·판정 배지(글자)가 보완한다. 2026-10-06 설계 4장이 공개
지도에 대해 같은 한계를 팝업 수치로 보완한 것과 같은 방식이다.

색은 라이트·다크가 같다. 시설 유형 색(`facilityColor`)처럼 데이터 색으로 다룬다.

### 2.2 조회 — 전체를 받아 클라이언트에서 거른다

핸드오버는 칩 개수를 별도 개수 쿼리(`head: true`)로 세라고 한다. 이 설계는 탭마다 행 전체를 한 번 받고, 검색·칩·
정렬·페이지 나누기·칩 개수를 클라이언트에서 한다.

- 칩 조건이 PostgREST로 표현되지 않는다. `번역 필요`는 `facilityNeedsTranslation`(`translation_status`가
  `translated`가 아니면 필요, 맞으면 원문이 있는 필드마다 영문·중문을 보는 계산)이고, 경사 판정은 `segments` JSON 안
  구간 값이다. 개수 쿼리로 하려면 RPC를 새로 만들어야 한다.
- 2026-10-14 운영 행 수(anon 키 조회): 독립 시설 3, 명소 4, 경사도 경로 39. 지도에는 어차피 거른 결과 전체를
  그려야 한다(3.3).
- 행 수가 수백을 넘으면 서버 페이지로 되돌린다. 그때 칩 조건은 RPC로 옮긴다.

### 2.3 명소 번역은 직접 고칠 수 있게 둔다

프로토타입의 번역 카드는 영문·중문 이름을 보여주기만 한다. 지금 명소 폼은 영문·중문 이름·설명 4칸을 직접 고칠
수 있고, 자동번역이 틀리면 이것이 유일한 수정 경로다. 카드는 핸드오버대로 값을 보여주고, `직접 고치기`를 펼치면
4칸 입력이 나온다.

### 2.4 다크의 크림슨 채움은 `#CC2936`

핸드오버는 다크 모드를 "기존 토큰을 따른다"고 한다. 다크의 `--ku-crimson-700`은 `#E66C62`이고 흰 글자와의 대비가
3.1:1이라 채움 버튼의 글자가 AA(4.5:1)에 못 미친다. 라이트 값 `#8C0000`을 그대로 쓰면 흰 글자는 9.9:1이지만 다크
표면(`--ku-surface` `#211D1A`)과의 대비가 1.7:1이라 버튼이 바탕에 묻힌다.

다크는 같은 크림슨 계열(색상 355°)을 밝고 선명하게 한 `#CC2936`으로 채운다. 흰 글자 5.3:1, 표면과 3.1:1(WCAG
1.4.11의 비텍스트 3:1), 배경(`--ku-bg`)과 3.5:1이다. 한 단계 어두운 `#C42634`은 표면과 2.9:1이다. hover는 라이트처럼
어둡게 가서 `#B0202E`(흰 글자 6.8:1)다.

다크에서 이 값은 위험 채움(`#DC2626`, 흰 글자 4.8:1)과 밝기가 가깝다. ①에서 두 채움이 한 줄에 서는 곳은 상세 패널
하단의 인라인 삭제 확인이고, 확인 문장과 버튼 문구(`삭제`·`저장`)가 갈라 준다.

공개 지도의 채움 버튼(`.ku-button--primary`)은 범위 밖이라 라이트·다크 모두 `#8C0000` 그대로다. 다크에서 관리자와
값이 다르다.

### 2.5 모바일 상세의 미리보기는 같은 지도다

핸드오버 모바일 상세의 미리보기(시설 지도 190px, 경사도 230px)는 지도를 하나 더 띄우지 않는다. 상세 화면을 지도
위쪽 그 높이만큼 비우고 덮어, 위쪽 띠로 작업 화면의 지도가 보인다. 그 띠를 눌러 위치를 바꾼다. 명소의 사진 미리보기는
지도가 아니므로 상세 화면 안에 그린다.

### 2.6 경사도 편집은 지도를 바꿔 끼운다

`경로 편집`을 누르면 작업 화면의 지도 자리에 기존 편집 지도(`SlopeRouteMap`)를 띄운다. 중심과 줌은 이어받는다.
다른 경로를 흐리게 까는 것(2026-10-06 설계 12장), 현재 위치에서 열기(5.4), 건물 스냅(5.5)이 이미 그 안에 있다.

기각한 대안: 보기·편집을 react-leaflet 지도 하나로 합치기. geoman 편집 상태와 react-leaflet 레이어 수명을 한
인스턴스에서 맞춰야 하고, 검증된 편집기 동작(꼭짓점 수 고정, 미리보기 pane 순서)을 다시 만들어야 한다. 지도를
바꿔 끼우면 타일을 한 번 다시 받는 것이 비용의 전부다.

### 2.7 도구 바의 `이어 그리기`는 `그리기`로 읽는다

프로토타입의 편집 도구 바(`✎ 이어 그리기` · `◇ 꼭짓점 편집` · `⌫ 지우기`)는 모양만 있고 동작이 없다. 이미 그린 선에
꼭짓점을 이어 붙이면 꼭짓점 수가 바뀌고, 편집기는 그때 입력한 구간 값을 모두 비운다(2026-08-30 설계 5.4.1의 꼭짓점
수 고정). 현장 실측값이 사라지므로 이어 그리기는 두지 않는다. 6.4의 도구 바가 대신한다.

### 2.8 동시성 체크는 지금 있는 곳만

핸드오버는 "낙관적 동시성 체크를 유지"하라고 한다. 이 리디자인이 옮기는 폼 저장 중 그 체크가 있는 것은 경사도
저장(`updated_at` 조건)이다. 시설·명소 폼 저장에는 없고, 이 설계도 더하지 않는다
(`docs/TODO_list/admin/facility-concurrent-edit.md` 그대로). 폼 밖의 조건부 쓰기 — 서버 번역 저장의 원문 조건,
등록 요청 상태 변경의 상태 조건 — 는 API가 하므로 화면을 바꿔도 그대로다.

### 2.9 `더 보기`는 세 열 모두

핸드오버는 처리 완료 열에만 `더 보기`를 둔다. 신규·확인 중 열도 한 페이지(`ADMIN_PAGE_SIZE`)를 넘을 수 있어 세 열
모두에 둔다(7.1).

### 2.10 마커 안쪽은 약자가 아니라 아이콘

핸드오버 안에서 두 절이 다르다. "지도 마커" 절은 시설 마커 가운데에 유형 약자(엘/화/경/주/점)를 쓰고, "Assets"
절은 그 약자가 자리 표시이며 기존 아이콘을 쓰라고 한다. Assets를 따른다(3.5).

### 2.11 피드백의 보낸 화면 주소는 같은 사이트일 때만 링크

핸드오버는 피드백 드로어에 `page_url` 링크를 둔다. 이 값은 익명 사용자가 보낸 것이고, 서버는 `http:`·`https:`만
확인한다(`src/lib/feedback.ts`). 아무 도메인이나 링크로 걸면 관리자에게 외부 주소를 누르게 하는 통로가 된다.
주소 원문은 그대로 보이고(핸드오버의 mono 12px), 이 사이트와 출처가 같을 때만 링크로 건다(7.4).

### 2.12 토스트는 관리자 화면에서만 모양을 바꾼다

핸드오버는 기존 `Toast`를 아래 가운데·`#1C1917`·2.2초로 쓰라고 한다. `Toast`는 공개 지도도 쓰고, 공개 지도 아래쪽에는
필터·지도 표기·모바일 시트가 있다. 컴포넌트는 하나로 두고(알림 역할·닫기·타이머가 한 곳에 있게) 모양만
`.ku-admin-shell` 안에서 바꾼다. 공개 지도는 지금 모양 그대로다.

- 색은 토큰을 반전한다 — 바탕 `--ku-text-1`, 글자 `--ku-surface`. 라이트는 핸드오버대로 `#1C1917`에 흰 글자이고,
  다크는 밝은 바탕에 어두운 글자다. `#1C1917`을 다크에 그대로 두면 다크 배경에 묻힌다.
- 핸드오버는 종류마다 색을 나누지 않는다. 성공·경고·오류는 아이콘 모양으로 가르고, 오류는 지금처럼 `role="alert"`다.
- 표시 시간은 지금의 3초다. 관리자 문구에 긴 경고(번역 실패 안내 등)가 있어 2.2초는 읽기에 짧다.
- 셸 밖인 옛 경사도 편집 라우트(`/admin/slopes/new`·`[id]`)는 6.5의 리다이렉트로 바뀔 때까지 지금 모양이다.

## 3. 공통 구조

### 3.1 셸

- 헤더 높이·버튼·nav 활성·배지는 핸드오버 "공통 셸"대로 바꾼다. 배지 배경은 크림슨 채움(2.4)이다 — 그 값을
  라이트·다크 모두 가진 토큰은 3.6의 `--ku-primary`뿐이라 그것을 쓴다.
- 지도 작업 화면은 `height: calc(100dvh - 헤더)`로 잡는다. 셸 전체를 고정 높이 flex로 바꾸면 스크롤 주체가 창에서
  안쪽 요소로 바뀌어, 범위 밖인 건물 화면의 스크롤 동작(sticky 헤더 등)까지 같이 바뀐다. 모바일은 아래 nav와
  safe area까지 뺀다.
- `.ku-admin-content > div { background … !important }`는 셸(`.ku-admin-shell`)이 같은 배경을 이미 줘서 지운다.
  `.ku-admin-content` 아래 입력·버튼 전역 덮어쓰기는 지도 위 패널의 배경·반경·포커스 테두리를 덮어쓰므로 지도
  작업 화면(`.ku-map-workspace`)을 범위에서 뺀다. 2026-10-14에 따져 보니 건물 화면이 기대는 것은 카드 버튼의
  반경(`button.ku-admin-overview-item`, `.ku-admin-mobile-card`)뿐이라 그 값을 각 클래스로 옮겼다. 남는 의존은
  아직 옮기지 않은 명소·경사도·제보함 화면(명소 폼·이모지 피커 입력의 색, 각 화면 버튼의 반경)이고, 마지막 탭을
  옮기는 PR(④)이 규칙을 지운다.

### 3.2 공통 단위

조회는 탭이 한다 — 테이블·조인·파생값(캠퍼스, 경로 요약)이 탭마다 다르다. 공통 단위는 Supabase 테이블이나 칩
의미를 모른다. `adminList.ts`의 `matchesAdminSearch`·`sortAdminItems`가 이미 접근자를 받는 순수 함수라 그 모양을
따른다. 제보함은 서버 페이지와 열별 이어 붙이기라 `useAdminCollection`을 쓰지 않는다.

`next/dynamic(ssr:false)`로 불러온 지도는 ref를 부모에 넘기지 않는다(`SlopeRouteMap`의 `onResetReady` 주석).
명령형 함수는 **객체 하나**로 묶어 콜백으로 등록하고(`onCommandsReady(commands)`), 지도가 정리될 때 먼저
`onCommandsReady(null)`을 부른다. 정리된 지도에 명령이 가지 않게 한다.

- 목록은 20개씩(`ADMIN_PAGE_SIZE`) 나누고, **지도에는 거른 결과 전체**를 그린다. 지금 페이지에 없는 마커를 누르면
  목록을 그 항목이 있는 페이지로 넘기고 선택한다.
- 정렬 select는 지금의 `최근 수정순 / 오래 수정순 / 이름순`이다.

### 3.4 선택과 URL

**URL과 상태.** 작업 화면 상태는 넷이다.

| 상태        | URL                | 쓰는 탭 |
| ----------- | ------------------ | ------- |
| 닫힘        | 아래 파라미터 없음 | 셋 다   |
| 보기        | `?id={id}`         | 셋 다   |
| 새로 만들기 | `?new=1`           | 셋 다   |
| 편집        | `?id={id}&edit=1`  | 경사도  |

- 우선순위: `new=1`이 있으면 `id`·`edit`을 무시한다. `edit=1`은 `id`와 함께일 때만, 경사도에서만 뜻이 있고 그 밖에는
  무시한다. 6.5의 리다이렉트는 원래 쿼리를 목적지에 넘기므로(Next `redirects()`) 겹친 조합이 실제로 들어올 수 있다.
- `workspaceUrl`은 자기 파라미터(`id`·`new`·`edit`)만 쓰고 지운다. 모르는 파라미터는 남긴다.
- 바꿀 때는 `history.replaceState`(지금 제보함의 `?tab=` 방식). `useSearchParams`는 Suspense 경계를 요구해 쓰지 않는다
  (제보함 페이지 주석과 같은 이유).
- 존재 검사는 **첫 조회가 성공한 뒤**에 한다. 조회 전의 빈 목록으로 판정하면 맞는 링크도 없는 항목이 된다. 없는
  `?id=`(삭제됐거나 틀린 id)면 선택을 풀고 토스트로 알린다.

**선택.**

- 같은 항목을 다시 누르면 선택을 푼다(데스크톱만).
- 저장 중에는 선택을 바꾸지 않는다 — 행·마커 클릭과 닫기를 막는다. 저장 완료 처리는 저장한 항목이 아직 선택돼
  있을 때만 패널 상태를 바꾼다. 늦게 끝난 저장이 다른 항목의 패널을 닫지 않게 한다.

**저장 안 한 변경.** dirty 여부는 각 탭의 상세 패널(초안 상태의 주인)이 계산하고, `UnsavedChangesGuard`에 등록만
한다. 이동은 전부 가드를 거친다 — 확인 전에는 선택·페이지·URL 어느 것도 바꾸지 않고, 승인되면 한 번에 적용한다.

| 이동                                                                          | 처리                                            |
| ----------------------------------------------------------------------------- | ----------------------------------------------- |
| 다른 항목 선택, 닫기, 새로 만들기, 칩·검색·정렬·페이지 변경, 경사도 편집 취소 | `ConfirmModal`                                  |
| 헤더 nav·로고·`지도 보기`·계정 메뉴                                           | `ConfirmModal`. 레이아웃의 링크가 가드를 거친다 |
| 브라우저 뒤로가기                                                             | `ConfirmModal`. 아래 방식                       |
| 새로고침·탭 닫기                                                              | `beforeunload`(브라우저 기본 경고)              |

확인 창 문구는 지금 편집기의 나가기 확인과 같다 — `저장하지 않은 변경사항이 있어요` / `지금 나가면 입력한 값이
사라져요` / `나가기`.

뒤로가기: dirty가 되면 같은 주소로 기록을 하나 쌓는다(`history.pushState`). 뒤로가기를 누르면 그 기록만 빠지고
화면은 그대로이므로, 그때 확인 창을 띄운다. `나가기`면 실제로 한 번 더 뒤로 가고, 취소면 기록을 다시 쌓는다.
저장하거나 dirty가 풀려도 쌓은 기록은 걷어내지 않는다. 작업 화면은 popstate 때 URL을 다시 읽어 상태를 맞추므로, 그
기록에서 뒤로가기를 누르면 직전 기록의 상태로 돌아간다(같은 선택이면 화면이 그대로인 뒤로가기가 한 번 생긴다).
Next 16 App Router가 `window.history.pushState`를 라우터와 맞추는지 구현 때 확인한다(10장).

### 3.5 지도

- 마커는 `L.divIcon`이다. 시설 마커 안쪽은 공개 지도와 같은 아이콘 함수(`facilityIconSvg`)를 쓰고, 한 글자 약자는
  쓰지 않는다(2.10). 명소는 `landmarkEmoji`.
- 선택된 마커는 커지고 링과 이름 툴팁이 붙는다(크기·색은 핸드오버). 마커 클릭 ↔ 행 클릭은 같은 선택이다.
- 선택하면 그 항목으로 `panTo`/`fitBounds` 하되, 목록 패널과 열린 상세 패널을 피하는 padding을 준다(값은 핸드오버).
- 줌 버튼은 Leaflet 기본 위치가 아니라 목록 패널 오른쪽 위다.
- 위치 편집(시설·명소): 상세 패널이 열려 있으면 빈 곳 클릭이 초안 핀을 옮기고, 선택된 마커는 끌 수 있다.
  `저장`을 눌러야 반영된다. 새로 만들기에서는 첫 클릭이 핀을 찍는다.
- 저장 중에는 위치 편집을 잠근다(지도 클릭·끌기·`현 위치로 찍기`). `현 위치로 찍기` 응답이 저장을 시작한 뒤나 선택이
  바뀐 뒤에 오면 버린다. 저장 요청에 실린 좌표와 화면의 핀이 달라지지 않게 한다.

### 4.2 상세 패널

`FacilityFormModal`을 패널로 옮긴다. 모달은 건물 상세가 계속 쓰므로 남기고, **저장(삽입·수정 → 번역 → revalidate)을
공유 함수로 뺀다.** 두 화면의 저장 경로가 갈라지지 않게 한다.

- 공유 함수는 시설 직접 저장 두 곳(모달·패널)만 쓴다. 등록 요청 승인은 자기 API 흐름이라 넣지 않는다.
- 결과를 돌려준다 — `{ facilityId, translated, revalidated }` 또는 저장 실패. 토스트 문구와 닫기는 화면이 정한다.
  지금 모달의 동작(DB 저장 실패는 오류, 번역 실패는 저장됨+경고, revalidate 실패는 조용히 넘김)을 두 화면이 같은
  결과로 판단하게 한다.
- 설치 세그먼트: 누르면 바로 저장하고 토스트를 띄운다(지금 `handleToggleInstalled`). 그래서 패널의 폼 `저장`은
  `is_installed`를 싣지 않는다 — 지금 모달 payload는 폼에서 읽은 값을 싣는데, 패널에서 그대로 두면 즉시 저장한
  설치 상태를 폼 저장이 처음 읽은 값으로 되돌린다. 모달(건물 상세)은 설치 체크박스가 폼 안에 있으므로 지금대로 싣는다.
- 번역 상태: 필요하면 `재번역`이 붙은 알약, 아니면 완료 문구. 재번역은 지금 `FacilityTranslationControl`의 동작이다.
- 폼: `FacilityFields`에 위치 칸을 끄는 옵션을 더한다(7.3도 쓴다). 위치는 3.5대로 큰 지도에서 바꾸고, 좌표와 캠퍼스
  판정(`inferCampusFromPoint`) 문구만 보인다. `현 위치로 찍기`는 위치 옆 보조 버튼으로 둔다.
- 미디어: 사진은 `FacilityPhotoManager`, 동영상은 `FacilityVideoModal`을 연다. 둘 다 지금 컴포넌트를 쓴다.
- 삭제: 인라인 확인 뒤 `deleteFacility`. `ConfirmModal`을 띄우지 않는다.
- 새로 만들기(`＋ 시설 추가`): 빈 패널을 열고, 지도 첫 클릭이 위치다. 저장 전에는 사진·동영상 칸을 비활성으로 둔다 —
  둘 다 시설 id가 있어야 올릴 수 있다.

  허용오차가 한 곳에 남는다.
- 편집 패널 구간 카드의 번호 원(판정 색 채움)은 글자를 ok·over 위에서 `#1C1917`(5.2:1·8.5:1), extreme 위에서
  흰색(7.8:1)으로 쓴다. 흰 글자로 통일하면 초록 위 3.4:1, 겨자 위 2.1:1이 된다. 지도 위 구간 번호표는 핸드오버대로
  지금의 `.ku-slope-segment-label`(흰 바탕·검은 테두리) 그대로다.

### 6.2 목록

| 칩             | 조건                          |
| -------------- | ----------------------------- |
| 전체           | —                             |
| 1/12 초과 포함 | over 또는 extreme 구간이 있음 |
| 확인 필요      | extreme 구간이 있음           |

- 행: 이름 + 판정 배지(핸드오버 우선순위), 구간 거리 비례 프로파일 막대(판정 색), `{구간 수}개 구간 · {총 거리}m ·
최대 {x.x}° · {수정일}`.
- `readRoutePoints`가 읽지 못하는 행(저장 형식이 깨진 경로)은 `형식 오류` 배지로 보이고, 상세는 지금 리다이렉트
  안내 문구(`저장 형식이 깨진 경로라 열 수 없어요. 지우고 다시 그려주세요`)와 삭제만 둔다.
- 지도: 구간마다 판정 색 선. 하나를 선택하면 나머지는 흐리게, 선택 경로에는 구간 번호.

### 6.3 보기 패널

헤더(이름·메타) + `삭제`(인라인 확인) + `경로 편집`, 구간 표(구간·거리·경사 `{x.x}° · {y.y}%`·판정).

### 6.4 편집

- `SlopeRouteEditor`의 상태·검증·dirty 계산을 훅(`useSlopeRouteDraft`)으로 뺀다. 편집 패널이 그 훅을 쓰고, 지도
  자리에 `SlopeRouteMap`을 띄운다(2.6).
- 지도 바꿔 끼우기: `AdminMapWorkspace`가 보관한 viewport를 `SlopeRouteMap`의 `initialViewport`로 넘긴다. 지금
  `SlopeRouteMap`은 마운트 때 줌 18로 열고 기존 경로면 `fitBounds`, 새 경로면 현재 위치로 옮긴다. `initialViewport`가
  있으면 기존 경로의 `fitBounds`는 하지 않는다(보기 상태에서 이미 그 경로로 맞춰 둔 화면을 이어받는다). 새 경로의
  현재 위치 이동(2026-10-06 설계 5.4)은 지금대로 한다. 편집을 마치면 편집 지도의 viewport를 돌려받아 보기 지도가
  이어받는다. `key`는 경로 id(새 경로는 `new`) — 지금 수정 페이지가 `key={params.id}`로 막는 문제(초기 props를 마운트
  때만 읽음)와 같다.
- geoman 기본 툴바는 숨기고, 지도 위 가운데 도구 바에서 같은 동작을 부른다. `SlopeRouteMap`은 명령 객체를
  `onCommandsReady`로 등록한다(3.2).

  | 도구              | 동작                                          |
  | ----------------- | --------------------------------------------- |
  | `✎ 그리기`        | 선이 없을 때만. 지금 `drawPolyline`           |
  | `◇ 꼭짓점 편집`   | 기본 상태. 꼭짓점 끌기(지금 `line.pm.enable`) |
  | `✥ 통째로 옮기기` | 지금 `dragMode`                               |
  | `건물에 붙이기`   | 지금 스냅 토글                                |
  | `⌫ 지우기`        | 확인 뒤 지금 `resetLine`                      |

  선을 그리는 동안에는 geoman이 툴바 옆에 붙이던 액션(`끝내기 / 마지막 꼭지점 제거 / 취소`, 2026-10-06 설계 5.6)도
  툴바와 함께 숨으므로, 도구 바가 그리는 동안 이 셋을 대신 보인다.

- 패널: 저장 상태 알약, 구간 수·총 거리, 단위 세그먼트(°/%, 지금처럼 기억), 경로 이름, 구간 카드(입력·환산값·경고 문구는
  `SlopeSegmentList` 그대로), 하단 `취소`·`저장`. 저장은 지금처럼 `updated_at` 조건을 걸고, 0행이면 지금 문구로 알린다.
- 새 경로(`＋ 경로 그리기`)는 `?new=1`로 편집 상태에서 연다.
- 편집 지도의 미리보기·다른 경로 색도 판정 3색으로 바꾼다. 2026-10-06 설계 11.1과 12장의 색 규칙을 대체하므로, 그
  문서 머리 표에 행을 더한다.

### 6.5 옛 라우트

`next.config.mjs`의 `redirects()`로 둔다. 순서가 중요하다 — `new`가 `:id`에 먼저 잡히지 않게 위에 둔다.
둘 다 `permanent: false`(307)다. `true`(308)는 브라우저가 캐시해 서버에서 되돌릴 수 없는데, 리디자인을 되돌릴
가능성이 남아 있는 동안은 옛 주소를 호환 진입점으로 둔다.

- `/admin/slopes/new` → `/admin/dashboard/slopes?new=1`
- `/admin/slopes/:id` → `/admin/dashboard/slopes?id=:id&edit=1`

원래 쿼리가 목적지에 붙어 겹친 조합이 될 수 있다. 우선순위는 3.4가 정한다.

목록의 `?redirected=missing|invalid` 안내는 3.4의 없는 `?id=` 처리와 6.2의 형식 오류 표시가 대신한다.

## 7. 제보함 (PR ④)

### 7.1 보드

- 종류 세그먼트 `전체 / 등록 요청 / 피드백`. 열은 신규·확인 중·처리 완료(핸드오버 매핑).
- 열마다 기존 API를 `status=new|reviewing|done`으로 부른다. `전체`는 두 API를 같은 상태로 불러 접수 시각순으로 합친다.
- 열은 첫 페이지(`ADMIN_PAGE_SIZE`)만 보이고 `더 보기`가 다음 페이지를 이어 붙인다. 세 열 모두 같다(2.9).
- 상태를 바꾸면 보드 전체를 다시 받고 `inboxCountsChanged`를 보낸다(지금과 같다). 다시 받으면 이어 붙인 페이지를
  버리고 첫 페이지부터 시작한다.
- 응답 순서: 보드 조회마다 세대 번호를 올리고, 응답의 세대가 지금과 다르면 버린다. 늦게 온 `더 보기` 응답이 다시
  받은 열에 붙어 중복되거나, 늦게 온 재조회가 이어 붙인 페이지를 덮지 않게 한다. 지금 `useInboxList`가 effect 정리의
  `cancelled`로 하는 일을 이어 붙이기까지 넓힌 것이다. 같은 항목 id가 두 번 오면 하나만 둔다.
- 부분 실패(`전체`에서 두 API 중 하나만 실패): 성공한 쪽은 보이고, 그 열 위에 `등록 요청을 불러오지 못했어요`(또는
  피드백) + `다시 시도`를 띄운다. 열 전체를 오류로 숨기지도, 성공한 절반을 완전한 목록처럼 보이지도 않는다.
- 건물 상세에서 오는 `?building=`은 `건물로 거름 ✕` 칩으로 유지한다. 그때 종류는 등록 요청으로 고정한다.

### 7.2 드로어

- 카드를 누르면 오른쪽 드로어. 배경을 누르거나 Esc로 닫는다(`useModalFocus`).
- 상태를 바꿔도 드로어는 열린 채다. 카드는 바뀐 열로 옮겨 간다.

### 7.3 등록 요청 드로어

`FacilityRequestReviewModal`의 로직(상세 조회, 사진 공개 선택, 상태 변경, 승인·거절, 409 처리, 남은 사진 정리)을 옮긴다.

- 왼쪽 `FacilityFields`(위치 칸 끔, 4.2), 오른쪽 위치 미니맵. 미니맵은 `FacilityMap`이고 건물 강조색으로 크림슨을
  넘긴다(3.6).
- `거절`은 하단 바가 인라인 확인으로 바뀐다. `ConfirmModal`을 겹쳐 띄우지 않는다.

### 7.4 피드백 드로어

`FeedbackDetailModal`을 옮긴다. 하단 상태 세그먼트는 누르면 바로 저장한다. `다음 항목 →`은 같은 열의 다음 카드다.

`보낸 화면`은 `page_url` 원문을 글자로 보인다. 링크는 그 주소의 출처가 이 사이트(`window.location.origin`)와 같을
때만 건다(2.11). 지금 모달은 아무 http(s) 주소나 `제보한 페이지`라는 문구 뒤에 링크로 건다.

### 7.5 모바일

세그먼트 `등록 요청 n / 피드백 n` + 상태 칩(지금 `INBOX_FILTERS`의 다섯 값) + 카드 목록 → 전체 화면 상세.

- Next 16의 `redirects()` 문법과 쿼리 문자열이 붙은 목적지 처리 — 로컬 `node_modules`가 없어
