## 1. 범위와 PR 나눔

PR마다 main에서 브랜치를 따고, 앞 PR이 병합된 뒤 다음을 시작한다. 각 PR은 그 화면의 모바일까지 담는다.
계획 문서는 PR마다 그 PR을 시작할 때 쓴다 — 뒤 PR의 계획은 앞 PR이 실제로 만든 컴포넌트에 기댄다.

| PR  | 범위                                                                                               |
| --- | -------------------------------------------------------------------------------------------------- |
| ①   | 이 사양과 핸드오버 원문, 토큰(3.6), 셸(3.1), 지도 작업 화면 공통 단위(3.2~3.5), **독립 시설**(4장) |
| ②   | **명소**(5장)                                                                                      |
| ③   | **경사도**(6장) — 판정 색, 보기·편집 패널, 옛 편집 라우트 리다이렉트                               |
| ④   | **제보함**(7장) — 상태별 보드와 검토 드로어                                                        |

## 2. 핸드오버와 달라지는 결정

### 2.1 경사 판정 색

| 판정               | 핸드오버  | 이 설계   |
| ------------------ | --------- | --------- |
| ok (1/12 이하)     | `#3E7A46` | `#1B9E77` |
| over (1/12 초과)   | `#C27A12` | `#E6AB02` |
| extreme (30% 초과) | `#A31C12` | `#A50F15` |

핸드오버 3색은 OKLab ΔE×100, Machado 2009 색각 이상 시뮬레이션(2026-10-06 설계 4장과 같은 방법)으로 초록↔주황이
제1색약에서 7.7, 초록↔빨강이 제2색약에서 6.8이다. 2026-10-06 설계 11.1이 쓴 기준 8에 못 미친다. 초록과 빨강의 밝기가
비슷해 색약 시야에서 같은 갈색이 된다.

새 3색은 휠체어 경사 지도에서 흔한 초록·노랑·빨강 신호등 관례를 지키되, 초록은 밝고 푸르게, 빨강은 어둡게 밀어
밝기 차이로 갈리게 했다. 초록·겨자는 ColorBrewer Dark2, 빨강은 ColorBrewer Reds의 색이다. 같은 방법으로 세 쌍의
색각 이상 최소 13.8, 정상 시각 최소 24.2다. 색약 시야에서 회색·노랑·검정으로 갈린다.

기각한 대안:

- **파랑·주황·진홍(`#0465AF`·`#C27A12`·`#A31C12`).** 색각 이상 최소 17.2로 가장 잘 갈리지만 신호등 관례가 아니다.
- **Okabe-Ito(`#009E73`·`#E69F00`·`#D55E00`).** 주황과 주홍이 가까워 정상 시각 차이가 15.6이다.
- **공개 지도의 연속 색(`slopeColorFromDeg`)을 그대로.** 관리자 화면은 구간마다 판정 3단계를 읽는 화면이라
  (목록 배지·프로파일 막대·칩) 연속 색보다 단계 색이 맞다. 공개 지도는 연속 색을 유지한다.

대비 한계: 밝은 지도 바탕(`#F2F2F0`)에서 겨자 1.8:1, 어두운 지도 바탕(`#2B2B2B`로 가정)에서 빨강 1.8:1이다. 지도
위에서는 선택 경로의 구간 번호와 상세 패널의 구간 표·판정 배지(글자)가 보완한다. 2026-10-06 설계 4장이 공개
지도에 대해 같은 한계를 팝업 수치로 보완한 것과 같은 방식이다.

색은 라이트·다크가 같다. 시설 유형 색(`facilityColor`)처럼 데이터 색으로 다룬다.

### 2.2 조회 — 전체를 받아 클라이언트에서 거른다

핸드오버는 칩 개수를 별도 개수 쿼리(`head: true`)로 세라고 한다. 이 설계는 탭마다 행 전체를 한 번 받고, 검색·칩·
정렬·페이지 나누기·칩 개수를 클라이언트에서 한다.

- 칩 조건이 PostgREST로 표현되지 않는다. `번역 필요`는 `facilityNeedsTranslation`(`translation_status`가
  `translated`가 아니면 필요, 맞으면 원문이 있는 필드마다 영문·중문을 보는 계산)이고, 경사 판정은 `segments` JSON 안
  구간 값이다. 개수 쿼리로 하려면 RPC를 새로 만들어야 한다.
- 2026-10-14 운영 행 수(anon 키 조회): 독립 시설 3, 명소 4, 경사도 경로 39. 지도에는 어차피 거른 결과 전체를
  그려야 한다(3.3).
- 행 수가 수백을 넘으면 서버 페이지로 되돌린다. 그때 칩 조건은 RPC로 옮긴다.

### 2.3 명소 번역은 직접 고칠 수 있게 둔다

프로토타입의 번역 카드는 영문·중문 이름을 보여주기만 한다. 지금 명소 폼은 영문·중문 이름·설명 4칸을 직접 고칠
수 있고, 자동번역이 틀리면 이것이 유일한 수정 경로다. 카드는 핸드오버대로 값을 보여주고, `직접 고치기`를 펼치면
4칸 입력이 나온다.

### 2.4 다크의 크림슨 채움은 `#CC2936`

핸드오버는 다크 모드를 "기존 토큰을 따른다"고 한다. 다크의 `--ku-crimson-700`은 `#E66C62`이고 흰 글자와의 대비가
3.1:1이라 채움 버튼의 글자가 AA(4.5:1)에 못 미친다. 라이트 값 `#8C0000`을 그대로 쓰면 흰 글자는 9.9:1이지만 다크
표면(`--ku-surface` `#211D1A`)과의 대비가 1.7:1이라 버튼이 바탕에 묻힌다.

다크는 같은 크림슨 계열(색상 355°)을 밝고 선명하게 한 `#CC2936`으로 채운다. 흰 글자 5.3:1, 표면과 3.1:1(WCAG
1.4.11의 비텍스트 3:1), 배경(`--ku-bg`)과 3.5:1이다. 한 단계 어두운 `#C42634`은 표면과 2.9:1이다. hover는 라이트처럼
어둡게 가서 `#B0202E`(흰 글자 6.8:1)다.

다크에서 이 값은 위험 채움(`#DC2626`, 흰 글자 4.8:1)과 밝기가 가깝다. ①에서 두 채움이 한 줄에 서는 곳은 상세 패널
하단의 인라인 삭제 확인이고, 확인 문장과 버튼 문구(`삭제`·`저장`)가 갈라 준다.

공개 지도의 채움 버튼(`.ku-button--primary`)은 범위 밖이라 라이트·다크 모두 `#8C0000` 그대로다. 다크에서 관리자와
값이 다르다.

### 2.5 모바일 상세의 미리보기는 같은 지도다

핸드오버 모바일 상세의 미리보기(시설 지도 190px, 경사도 230px)는 지도를 하나 더 띄우지 않는다. 상세 화면을 지도
위쪽 그 높이만큼 비우고 덮어, 위쪽 띠로 작업 화면의 지도가 보인다. 그 띠를 눌러 위치를 바꾼다. 명소의 사진 미리보기는
지도가 아니므로 상세 화면 안에 그린다. 그래서 명소 상세에는 띠가 없고, 위치 칸의 `지도에서 위치 고르기`가 상세를 접어
지도와 하단 확인 바(`이 위치로` / `취소`)를 보인다.

경사도는 편집 상태에서 띠가 편집 지도라 꼭짓점을 띠에서 바로 끈다. 도구 바가 필요한 편집은 명소처럼 상세를 접은 전체
지도에서 한다(6.6). 보기 패널(`?id=`로 바로 들어오거나 형식 오류 경로)의 띠는 보기 지도다.

### 2.6 경사도 편집은 지도를 바꿔 끼운다

`경로 편집`을 누르면 작업 화면의 지도 자리에 기존 편집 지도(`SlopeRouteMap`)를 띄운다. 중심과 줌은 이어받는다.
다른 경로를 흐리게 까는 것(2026-10-06 설계 12장), 현재 위치에서 열기(5.4), 건물 스냅(5.5)이 이미 그 안에 있다.

기각한 대안: 보기·편집을 react-leaflet 지도 하나로 합치기. geoman 편집 상태와 react-leaflet 레이어 수명을 한
인스턴스에서 맞춰야 하고, 검증된 편집기 동작(꼭짓점 수 고정, 미리보기 pane 순서)을 다시 만들어야 한다. 지도를
바꿔 끼우면 타일을 한 번 다시 받는 것이 비용의 전부다.

### 2.7 도구 바의 `이어 그리기`는 `그리기`로 읽는다

프로토타입의 편집 도구 바(`✎ 이어 그리기` · `◇ 꼭짓점 편집` · `⌫ 지우기`)는 모양만 있고 동작이 없다. 이미 그린 선에
꼭짓점을 이어 붙이면 꼭짓점 수가 바뀌고, 편집기는 그때 입력한 구간 값을 모두 비운다(2026-08-30 설계 5.4.1의 꼭짓점
수 고정). 현장 실측값이 사라지므로 이어 그리기는 두지 않는다. 6.4의 도구 바가 대신한다.

### 2.8 동시성 체크는 지금 있는 곳만

핸드오버는 "낙관적 동시성 체크를 유지"하라고 한다. 이 리디자인이 옮기는 폼 저장 중 그 체크가 있는 것은 경사도
저장(`updated_at` 조건)이다. 시설·명소 폼 저장에는 없고, 이 설계도 더하지 않는다
(`docs/TODO_list/admin/facility-concurrent-edit.md` 그대로). 폼 밖의 조건부 쓰기 — 서버 번역 저장의 원문 조건,
등록 요청 상태 변경의 상태 조건 — 는 API가 하므로 화면을 바꿔도 그대로다.

### 2.9 `더 보기`는 세 열 모두

핸드오버는 처리 완료 열에만 `더 보기`를 둔다. 신규·확인 중 열도 한 페이지(`ADMIN_PAGE_SIZE`)를 넘을 수 있어 세 열
모두에 둔다(7.1).

### 2.10 마커 안쪽은 약자가 아니라 아이콘

핸드오버 안에서 두 절이 다르다. "지도 마커" 절은 시설 마커 가운데에 유형 약자(엘/화/경/주/점)를 쓰고, "Assets"
절은 그 약자가 자리 표시이며 기존 아이콘을 쓰라고 한다. Assets를 따른다(3.5).

### 2.11 피드백의 보낸 화면 주소는 같은 사이트일 때만 링크

핸드오버는 피드백 드로어에 `page_url` 링크를 둔다. 이 값은 익명 사용자가 보낸 것이고, 서버는 `http:`·`https:`만
확인한다(`src/lib/feedback.ts`). 아무 도메인이나 링크로 걸면 관리자에게 외부 주소를 누르게 하는 통로가 된다.
주소 원문은 그대로 보이고(핸드오버의 mono 12px), 이 사이트와 출처가 같을 때만 링크로 건다(7.4).

### 2.12 토스트는 관리자 화면에서만 모양을 바꾼다

핸드오버는 기존 `Toast`를 아래 가운데·`#1C1917`·2.2초로 쓰라고 한다. `Toast`는 공개 지도도 쓰고, 공개 지도 아래쪽에는
필터·지도 표기·모바일 시트가 있다. 컴포넌트는 하나로 두고(알림 역할·닫기·타이머가 한 곳에 있게) 모양만
`.ku-admin-shell` 안에서 바꾼다. 공개 지도는 지금 모양 그대로다.

- 색은 토큰을 반전한다 — 바탕 `--ku-text-1`, 글자 `--ku-surface`. 라이트는 핸드오버대로 `#1C1917`에 흰 글자이고,
  다크는 밝은 바탕에 어두운 글자다. `#1C1917`을 다크에 그대로 두면 다크 배경에 묻힌다.
- 핸드오버는 종류마다 색을 나누지 않는다. 성공·경고·오류는 아이콘 모양으로 가르고, 오류는 지금처럼 `role="alert"`다.
- 표시 시간은 지금의 3초다. 관리자 문구에 긴 경고(번역 실패 안내 등)가 있어 2.2초는 읽기에 짧다.

조회와 행 만들기는 탭이 한다 — 테이블·조인·파생값(캠퍼스, 경로 요약)이 탭마다 다르다. 탭이 `useWorkspaceLoad`에
조회 함수를 넘기면, 요청 번호·떠난 뒤 버리기·실패 표시·`?id=` 존재 검사·첫 성공 페이지 맞추기는 훅이 한다(행 상태는
`useAdminCollection`이 `setPage`를 주므로 탭이 가진다). 공통 단위는 Supabase 테이블이나 칩 의미를 모른다. `adminList.ts`의 `matchesAdminSearch`·`sortAdminItems`가 이미 접근자를 받는 순수 함수라 그 모양을
따른다. 제보함은 서버 페이지와 열별 이어 붙이기라 `useAdminCollection`을 쓰지 않는다.

`next/dynamic(ssr:false)`로 불러온 지도는 ref를 부모에 넘기지 않는다(`workspace/types.ts`의 `WorkspaceMapSlotProps`
주석). 명령형 함수는 **객체 하나**로 묶어 콜백으로 등록하고(`onCommandsReady(commands)`), 지도가 정리될 때 먼저
`onCommandsReady(null)`을 부른다. 정리된 지도에 명령이 가지 않게 한다.

2026-10-15 — `focus` 명령은 실제로 옮겼는지를 돌려주고, 작업 화면은 옮겼을 때만 그 focus key를 적는다. 지도를 바꿔
끼우는 커밋(2.6)에서는 렌더 때 받은 명령이 막 정리된 지도의 것이라 버려진다. key를 먼저 적으면 새 지도가 명령을
등록해도 옮기지 않아, 편집 주소로 바로 들어오거나 편집 중 다른 경로를 고를 때 지도가 그 경로로 가지 않았다.

2026-10-15 — 작업 화면은 지도의 viewport를 `moveend`에서만 받는다. 지도가 focus로 옮기는 애니메이션 중에 바꿔 끼우면
새 지도는 옮기기 전 화면으로 열리는데, 같은 key라 다시 맞추지 않아 경로가 패널 밑이나 화면 밖에 남았다. 그래서 명령은
마지막 focus로 아직 옮기는 중인지(`moving`)도 알린다. 작업 화면은 같은 key를 앞 지도가 다 옮기기 전에 바꿔 끼웠으면 새
지도에서 다시 맞추고, 다 옮긴 뒤면 맞추지 않는다 — 그 뒤 손으로 옮긴 화면을 그대로 이어받는다(2.6). 두 지도의 명령은
`focusMap.ts`의 `bindWorkspaceMapCommands` 하나가 만든다. 정리(`remove()`)가 진행 중인 팬을 멈추며 내는 `moveend`는 다
옮긴 것으로 치지 않는다.

### 3.4 선택과 URL

**URL과 상태.** 작업 화면 상태는 넷이다.

| 상태        | URL                | 쓰는 탭 |
| ----------- | ------------------ | ------- |
| 닫힘        | 아래 파라미터 없음 | 셋 다   |
| 보기        | `?id={id}`         | 셋 다   |
| 새로 만들기 | `?new=1`           | 셋 다   |
| 편집        | `?id={id}&edit=1`  | 경사도  |

- 우선순위: `new=1`이 있으면 `id`·`edit`을 무시한다. `edit=1`은 `id`와 함께일 때만, 경사도에서만 뜻이 있고 그 밖에는
  무시한다. 6.5의 리다이렉트는 원래 쿼리를 목적지에 넘기므로(Next `redirects()`) 겹친 조합이 실제로 들어올 수 있다.
- `workspaceUrl`은 자기 파라미터(`id`·`new`·`edit`)만 쓰고 지운다. 모르는 파라미터는 남긴다.
- 바꿀 때는 `history.replaceState`(지금 제보함의 `?tab=` 방식). `useSearchParams`는 Suspense 경계를 요구해 쓰지 않는다
  (제보함 페이지 주석과 같은 이유).
- 존재 검사는 **첫 조회가 성공한 뒤**에 한다. 조회 전의 빈 목록으로 판정하면 맞는 링크도 없는 항목이 된다. 없는
  `?id=`(삭제됐거나 틀린 id)면 선택을 풀고 토스트로 알린다.

2026-10-15 — **저장·삭제 뒤 토스트 순서.** 성공 토스트를 먼저 띄우고 그다음에 목록을 다시 받는다. 토스트 상태는 하나라
순서가 거꾸로면 다시 받기가 실패해 띄운 `… 목록을 새로 불러오지 못했어요`를 성공 토스트가 곧바로 덮는다. 저장은 됐는데
화면의 목록이 낡았다는 사실이 사라진다. 이 순서면 다시 받기 실패의 오류 토스트가 마지막에 남는다. 세 탭의 저장·삭제와
명소 사진 업로드·삭제, 독립 시설의 설치 상태·재번역이 같은 순서다. 사진 업로드 실패 경고처럼 저장 결과로 이미 정해진
토스트는 다시 받기 전에 한 번만 띄운다.

**선택.**

- 같은 항목을 다시 누르면 선택을 푼다(데스크톱만).
- 저장 중에는 선택을 바꾸지 않는다 — 행·마커 클릭과 닫기를 막는다. 저장 완료 처리는 저장한 항목이 아직 선택돼
  있을 때만 패널 상태를 바꾼다. 늦게 끝난 저장이 다른 항목의 패널을 닫지 않게 한다.
- 삭제 중에는 선택을 잠그지 않는다. 그래서 삭제 완료 처리도 지운 항목이 아직 선택돼 있을 때만 선택을 풀고, 목록은
  어느 쪽이든 다시 받는다. 기다리는 사이 연 다른 항목이나 새로 만들기 패널을 닫지 않게 한다.

**저장 안 한 변경.** dirty 여부는 각 탭의 상세 패널(초안 상태의 주인)이 계산하고, `UnsavedChangesGuard`에 등록만
한다. 이동은 전부 가드를 거친다 — 확인 전에는 선택·페이지·URL 어느 것도 바꾸지 않고, 승인되면 한 번에 적용한다.

| 이동                                                                          | 처리                                            |
| ----------------------------------------------------------------------------- | ----------------------------------------------- |
| 다른 항목 선택, 닫기, 새로 만들기, 칩·검색·정렬·페이지 변경, 경사도 편집 취소 | `ConfirmModal`                                  |
| 헤더 nav·로고·`지도 보기`·계정 메뉴                                           | `ConfirmModal`. 레이아웃의 링크가 가드를 거친다 |
| 브라우저 뒤로가기                                                             | `ConfirmModal`. 아래 방식                       |
| 새로고침·탭 닫기                                                              | `beforeunload`(브라우저 기본 경고)              |

헤더 링크는 `Link`의 `onNavigate`에서 막는다(Next 15.3부터). 수정키 클릭(새 탭)·외부 링크에는 불리지 않아
브라우저 기본 동작이 그대로 간다. 지금 페이지를 가리키는 헤더 링크는 선택이 열려 있으면 Next로 옮기지 않고 그 화면의
닫기로 넘긴다(`requestWorkspaceClose`). 같은 페이지로 가는 Next 이동은 popstate를 내지 않아 작업 화면이 바뀐 URL을
모르고, URL만 바뀐 채 선택이 열려 남는다(2026-10-14 확인). 화면의 닫기로 넘기므로 저장 중 잠금과 가드도 `✕`와 똑같이
거친다.

확인 창 문구는 지금 편집기의 나가기 확인과 같다 — `저장하지 않은 변경사항이 있어요` / `지금 나가면 입력한 값이
사라져요` / `나가기`.

뒤로가기: dirty가 되면 같은 주소로 표식을 단 기록을 하나 쌓는다(`history.pushState`). 뒤로가기를 누르면 그 기록만
빠지고 화면은 그대로이므로, 그때 확인 창을 띄운다. `나가기`면 실제로 한 번 더 뒤로 가고, 취소면 기록을 다시 쌓는다.
저장하거나 dirty가 풀려도 쌓은 기록은 걷어내지 않는다. 작업 화면은 popstate 때 URL을 다시 읽어 상태를 맞추므로, 그
기록에서 뒤로가기를 누르면 직전 기록의 상태로 돌아간다(같은 선택이면 화면이 그대로인 뒤로가기가 한 번 생긴다).

- 다음에 dirty가 될 때 아직 그 기록 위에 있으면(그 뒤로 기록을 오가지 않았고 표식이 남아 있으면) 새로 쌓지 않고
  다시 쓴다. 고칠 때마다 같은 주소 기록이 하나씩 쌓이면 `나가기`의 뒤로가기가 같은 화면에 내려 아무 일도 없고,
  `beforeunload` 경고도 꺼진 채 남는다. 선택을 바꾸는 `replaceState`와 새 이동은 표식을 지우므로 그때는 새로 쌓는다.
- 기록을 오간 뒤에는 아래 기록이 같은 화면인지 알 수 없어 새로 쌓는다. 그래서 `나가기`가 같은 주소 기록에 내리면
  화면이 바뀔 때까지 더 뒤로 간다. 뒤로 갈 때마다 잠시(약 1초) 기다려 popstate도 `beforeunload`도 오지 않으면
  뒤로 갈 기록이 없던 것으로 보고 머물며 기록을 다시 쌓는다. Navigation API `canGoBack`은 쓰지 않는다 — 같은 출처
  기록만 세서, Slack·메일처럼 다른 사이트에서 같은 탭으로 들어온 경우에도 false다(2026-10-14 확인). bfcache로
  돌아오면(`pageshow`의 `persisted`) 떠나던 상태를 풀고 dirty면 기록을 다시 쌓는다.
- 확인 창은 쌓은 기록에서 같은 주소로 한 칸 뒤로 왔을 때만 띄운다. 여러 칸을 한 번에 갔거나 확인 창을 띄운 채 또
  뒤로 가면 이미 다른 기록이라 막지 못하므로 확인 창을 거둔다. dirty가 풀려도(저장, 패널이 사라짐) 띄운 확인 창을
  거둔다.
- 표식은 Next가 기록을 오갈 때 보존하고(`completeTraverseNavigation`의 `preserveCustomHistoryState`), 새 이동은 자기
  상태로 쌓는다(v16.2.4 `segment-cache/navigation.js`, 2026-10-14 확인).

**진행 중인 작업(2026-10-15).** 가드는 묻는 이유를 둘 안다. 저장 안 한 변경(dirty)과, 화면이 끝내야 할 클라이언트 일이
도는 동안(busy)이다. 승인 뒤 번역 호출처럼 떠나면 빠지는 일이 있어서다. 제공자는 두 키 집합을 따로 들고
`blocked = dirty || busy`가 위의 모든 동작(기록 쌓기, `beforeunload` 경고, 뒤로가기 확인, `guard`, 헤더 링크 가로채기,
떠 있는 확인 창 거두기)을 몬다. busy는 `useBusyNavigation(busy)`로 등록하고 dirty와 같게 언마운트하면 풀린다.
busy일 때의 문구는 `처리 중인 작업이 있어요` / `지금 나가면 진행 중인 작업이 끝나지 않을 수 있어요` / `나가기`다.
창이 열리는 순간 busy면 busy 문구, 아니면 저장 안 한 변경 문구를 쓰고(둘 다면 busy가 이긴다) 열린 동안 바뀌지 않는다.
등록하는 곳: 등록 요청 드로어(승인·거절·상태·정리 진행 중), 피드백 드로어(상태 변경 중), 독립 시설 상세(저장 뒤 번역과
재번역 중), 명소 상세(저장 중).

Next 16.2.4는 사용자가 부른 `pushState`·`replaceState`를 라우터와 맞춘다. 지금 기록의 라우터 상태를 새 기록에
복사하고, 그 기록에서 뒤로가기를 하면 같은 트리로 복원해 페이지를 다시 마운트하지도 다시 받지도 않는다(v16.2.4
`app-router.tsx`의 패치된 `pushState`와 `onPopState`, `restore-reducer.ts`, 2026-10-14 확인).

### 3.5 지도

- 마커는 `L.divIcon`이다. 시설 마커 안쪽은 공개 지도와 같은 아이콘 함수(`facilityIconSvg`)를 쓰고, 한 글자 약자는

  알리지 않게 한다. 패널이 바뀌어 버린 응답은 지도도 옮기지 않는다.

  선택 마커의 이름 툴팁 아래에 놓인다.
- 2026-10-15 — 이름표는 박스 없이 글자에 바탕색 테두리만 둔다(공개 지도 `.ku-building-label`과 같은 모양). 같은 주변

`FacilityFormModal`을 패널로 옮긴다. 모달은 건물 상세가 계속 쓰므로 남기고, **저장(삽입·수정 → 번역 → revalidate)을

  결과로 판단하게 한다.
- 설치 세그먼트: 누르면 바로 저장하고 토스트를 띄운다(지금 `handleToggleInstalled`). 그래서 패널의 폼 `저장`은

  설치 상태를 폼 저장이 처음 읽은 값으로 되돌린다. 모달(건물 상세)은 설치 체크박스가 폼 안에 있으므로 지금대로 싣는다.
- 번역 상태: 필요하면 `재번역`이 붙은 알약, 아니면 완료 문구. 재번역은 지금 `FacilityTranslationControl`의 동작이다.

- 프로파일 막대는 `aria-hidden`이다. 같은 판정을 배지가 글자로 말한다.
- 칩 개수는 시설·명소처럼 전체 행 기준이다. 형식 오류 행은 두 칩 어디에도 들지 않는다.
- `readRoutePoints`가 읽지 못하는 행(저장 형식이 깨진 경로)은 `형식 오류` 배지로 보이고, 메타는 수정일만, 지도에는
  그리지 않는다. 상세는 옛 리다이렉트 안내와 같은 문구(`저장 형식이 깨진 경로라 열 수 없어요. 지우고 다시 그려주세요`)와
  삭제만 둔다. 편집 주소(`?id=&edit=1`)로 들어오면 첫 조회 뒤 보기(`?id=`)로 바꾼다 — 편집기가 읽지 못한다.
  2026-10-15 — 꼭짓점으로 경계를 만들 수 없는 경로도 요약(`summarizeSlopeRoute`)이 `형식 오류`로 돌린다. 지금은
  `readRoutePoints`가 두 점 미만을 먼저 걸러 오지 않지만, 그 불변식이 바뀌어도 경계 없는 경로가 지도 focus까지 가지 않는다.
- 2026-10-15 — 판정 → 배지 색 짝은 `slopeWorkspace.ts`의 `SLOPE_GRADE_TONES` 하나다. 목록 행 배지(`slopeRouteBadge`)와
  보기 패널의 구간 표 배지가 같이 쓴다. 공개 지도는 판정 색 배지를 쓰지 않아 관리자 쪽 파일에 둔다.
- 없는 `?id=`는 3.4대로 열지 않고 URL에서 지운 뒤 경고 토스트로 알린다. 문구는 페이지의 `NOT_FOUND_MESSAGE`이고
  명소와 같은 꼴이다.
- 지도: 구간마다 판정 색 선. 하나를 선택하면 나머지는 흐리게, 선택 경로에는 구간 번호.
- 범례 항목은 핸드오버가 정하지 않아(1장은 범례 바의 모양만 정한다) 판정 3색과 그 경계(1/12, 30%)를 읽는다(페이지의
  `LEGEND`).

### 6.3 보기 패널

헤더(이름·메타) + `경로 편집`, 구간 표(구간·거리·경사 `{x.x}° · {y.y}%`·판정). 저장 버튼은 없다.

- 삭제는 `DetailPanel`의 인라인 확인이다. 데스크톱은 하단 바에 둔다 — 핸드오버는 헤더에 두지만 인라인 확인은 하단 바에
  있어 시설·명소와 자리를 맞춘다. 모바일은 `DetailPanel`이 본문 맨 아래에 그린다(핸드오버 8장). 삭제 호출과 토스트는
  페이지의 `deleteRoute` 하나를 보기 패널과 모바일 편집 패널(6.6)이 같이 쓴다.

### 6.4 편집

- `SlopeRouteEditor`의 상태·검증·dirty 계산을 훅(`useSlopeRouteDraft`)으로 옮기고 컴포넌트는 지운다. 편집 패널이 그
  훅을 쓰고, 지도 자리에 `SlopeRouteMap`을 띄운다(2.6).
- 편집 패널과 편집 지도는 형제라 페이지를 거쳐 패널의 초안(`SlopeEditDraft`)과 지도의 편집기 손잡이
  (`SlopeEditorHandle`)를 주고받는다. owner가 지금 편집 상태와 다르면 낡은 것으로 버린다 — 명소의 `DetailDraftPin`과
  같은 방식이다. 2026-10-15 — owner(`edit:{id}`·`edit:new`)는 페이지만 만들어 패널과 지도에 props로 넘긴다. 패널은
  사라질 때 초안을 `null`로 거둔다 — 같은 경로를 다시 열면 owner가 같아, 새 패널이 첫 초안을 내놓기 전 한 렌더 동안 앞
  패널의 초안(구간 값·잠금)이 편집 지도로 갔다.
- 지도 바꿔 끼우기: `AdminMapWorkspace`가 보관한 viewport를 `SlopeRouteMap`의 `initialViewport`로 넘긴다. 편집 지도는
  그 화면으로 열고 기존 경로라도 스스로 선에 맞추지 않는다(보기 상태에서 그 경로로 맞춘 화면을 이어받는다). 맞추는 것은
  작업 화면의 focus다 — 편집 주소로 바로 들어오거나 보기 지도가 그 경로로 옮기던 중에 바꿔 끼우면 그것이 맞춘다(3.2).
  그래서 편집 지도도 `onCommandsReady`로 보기 지도와 같은 명령(`bindWorkspaceMapCommands`)을 등록한다. 새 경로의 현재
  위치 이동(2026-10-06 설계 5.4)은 지금대로 한다. 편집을 마치면 편집 지도의 viewport를 돌려받아 보기 지도가 이어받는다.
  `key`는 편집 상태마다 다르다(페이지의 `editOwner`) — 옛 수정 페이지가 `key={params.id}`로 막던 문제(초기 props를
  마운트 때만 읽음)와 같다.
- geoman 툴바는 만들지 않는다(`addControls`를 부르지 않는다). 편집 패널이 지도의 형제로 도구 바(`SlopeEditToolbar`)를
  그리고, 버튼은 편집기 손잡이의 명령을 부른다. 지도 자리는 z-index 0 맥락이라 그 안에 그린 확인 창(`지우기`)은 패널

### 6.5 옛 라우트

`next.config.mjs`의 `redirects()`로 둔다. 순서가 중요하다 — `new`가 `:id`에 먼저 잡히지 않게 위에 둔다.
둘 다 `permanent: false`(307)다. `true`(308)는 브라우저가 캐시해 서버에서 되돌릴 수 없는데, 리디자인을 되돌릴
가능성이 남아 있는 동안은 옛 주소를 호환 진입점으로 둔다.

- `/admin/slopes/new` → `/admin/dashboard/slopes?new=1`
- `/admin/slopes/:id` → `/admin/dashboard/slopes?id=:id&edit=1`

원래 쿼리가 목적지에 붙어 겹친 조합이 될 수 있다. 우선순위는 3.4가 정한다.
Next 16.2.4는 요청 쿼리를 모두 목적지로 넘기고, 같은 키는 목적지 값(`id=:id`, `edit=1`)이 이긴다
(`shared/lib/router/utils/prepare-destination.js`의 `{ ...args.query, ...parsedDestination.query }`와
`next/dist/docs`의 `redirects.md`, 2026-10-14 확인). `permanent: false`는 307이다.

목록의 `?redirected=missing|invalid` 안내는 3.4의 없는 `?id=` 처리와 6.2의 형식 오류 표시가 대신한다.

옛 페이지는 대시보드 레이아웃 밖이라 인증을 스스로 확인했다(2026-08-30 설계 5.2.1). 페이지를 지웠으므로 옛 주소로 온
비로그인 사용자는 리다이렉트 뒤 대시보드 레이아웃이 `/admin`으로 보낸다.

  두지 않는다 — 지도 편집은 바로 초안에 들고, 패널의 `취소`가 초안 전체를 버린다. 그리는 동안에는 `완료`가 비활성이다 —
  띠에는 그리기를 끝내거나 취소할 도구 바가 없다.
- 전체 지도로 들어갈 때와 `완료`로 나올 때 각각 새 focus key로 지금 초안의 경계에 맞춘다(명소의 위치 고르기와 같은
  방식). 들어갈 때는 아래 확인 바와 위쪽 도구 바를 함께 비키고(`workspaceInsets`의 `pickingTop`, 값은
  `MOBILE_TOOLBAR_BOTTOM`과 그 주석), 나올 때는 띠에 맞춘다. 선이 없으면 옮기지 않는다.
- 띠로 돌아오면(전체 지도의 `완료`, 또는 데스크톱에서 `통째로 옮기기`를 고른 채 모바일 폭으로 좁아질 때) 꼭짓점 편집으로
  돌아간다. 띠에는 도구 바가 없어 지금 모드가 보이지 않고, 통째로 옮기기면 띠에서 끌 꼭짓점 핸들이 없다.
- 편집 패널에서 나가는 `‹ 목록으로`·`취소`와 저장 성공은 목록(닫힘)으로 간다. 행이 보기를 거치지 않으므로 상단 바의
  이름대로 돌아간다. 데스크톱(6.4)은 보기로 간다.
  - 기각: 저장 뒤 합친 상세에 남기. 같은 key라 패널이 다시 마운트되지 않아 저장 조건(`loadedAt`)이 낡는다. 행의
    `updated_at`으로 key를 바꾸면 다른 곳의 저장으로 목록을 다시 받기만 해도 쓰던 초안이 날아간다.
  - 기각: 보기로 가기. 행으로는 오지 않는 화면이고, 목록까지 두 번 눌러야 한다.
- 기존 경로의 편집 패널은 본문 맨 아래에 삭제를 둔다(6.3의 `deleteRoute`).

  받은 열에 붙어 중복되거나, 늦게 온 재조회가 이어 붙인 페이지를 덮지 않게 한다. 지금 `useInboxList`가 effect 정리의
  `cancelled`로 하는 일을 이어 붙이기까지 넓힌 것이다. 같은 항목 id가 두 번 오면 하나만 둔다.
- 부분 실패(`전체`에서 두 API 중 하나만 실패): 성공한 쪽은 보이고, 그 열 위에 `등록 요청을 불러오지 못했어요`(또는
  피드백) + `다시 시도`를 띄운다. 열 전체를 오류로 숨기지도, 성공한 절반을 완전한 목록처럼 보이지도 않는다.
- 건물 상세에서 오는 `?building=`은 `건물로 거름 ✕` 칩으로 유지한다. 그때 종류는 등록 요청으로 고정한다.

2026-10-15 — 구현하며 정한 것:

- **URL.** 종류는 지금의 `?tab=` 파라미터 이름을 그대로 쓴다(`requests` | `feedback`, 없으면 `전체`). 옛 `?tab=feedback`
  링크가 피드백을 연다. 바꿀 때 자기가 모르는 파라미터는 남긴다. 드로어 열림과 모바일 상태 칩은 URL에 두지 않는다.
- **조회.** 데스크톱은 세그먼트가 고른 종류만 부른다. 모바일은 세그먼트에 두 종류의 개수를 보여야 해서 고른 상태 칩으로
  두 API를 모두 부르고 고른 종류만 보인다.
- **중복의 키는 종류 + id.** "같은 항목 id"는 같은 종류 안의 같은 행이다. 등록 요청과 피드백은 다른 테이블이다.
- **같은 세대 안의 중복.** 세대에 더해 기대 페이지도 본다 — 다음 페이지 응답은 `더 보기`를 받는 중이고 마지막으로 받은
  페이지의 바로 다음일 때만 받는다. `더 보기`를 빠르게 두 번 눌러 같은 페이지가 두 번 와도 하나만 붙는다.
- **개수.** 열 헤더 개수는 보이는 소스를 모두 받았을 때만 그린다. 한 소스가 받는 중이거나 실패했으면 숫자를 비운다 —
  절반만 받은 합을 완전한 개수처럼 보이지 않는다. 캡션 `처리 전 {n}건`은 신규·확인 중 두 열 개수의 합이다(헤더 배지는
  `신규`만 센다).
- **카드의 설명.** 등록 요청 카드의 설명 두 줄을 그리려고 관리자 목록 API(`GET /api/facility-requests`) 항목에
  `description`을 더했다.

### 7.2 드로어

- 카드를 누르면 오른쪽 드로어. 배경을 누르거나 Esc로 닫는다(`useModalFocus`).
- 상태를 바꿔도 드로어는 열린 채다. 카드는 바뀐 열로 옮겨 간다.

2026-10-15 — 구현하며 정한 것:

- **드로어의 소유.** 열린 항목은 보드와 따로 페이지가 들고 있고, 연 순간 그 열의 카드 목록(이어 붙인 페이지 포함)을
  스냅샷으로 둔다. 보드를 다시 받아 카드가 다른 열로 가거나 빠져도 드로어는 닫히지 않는다. 드로어는 항목마다 새로
  그린다(앞 요청의 값이 남지 않는다).
- **층.** 드로어는 헤더 아래 제보함 영역을 덮는다. 배경(dim)은 패널의 형제 요소라 패널 안 클릭이 닫기로 번지지 않는다.
- **바쁜 동안**(승인·거절·상태 변경·정리 진행 중)은 ✕·배경·Esc·같은 화면 헤더 링크로 닫히지 않는다. 승인은 번역과
  revalidate까지 기다리므로 그 사이 닫히면 늦게 끝난 결과가 닫힌 드로어에 쓰인다.
- **Esc.** 인라인 거절 확인이 떠 있으면 Esc는 확인만 취소한다. 두 번째 Esc가 드로어를 닫는다.
- **저장 안 한 변경.** 사용자 결정. 처리 전 등록 요청에서 값·사진 선택이 처음 읽은 값과 다르면 가드에 dirty를 등록한다.
  ✕·배경·Esc·모바일 `‹`·같은 화면 헤더 링크·드로어 안 링크(건물, 만들어진 시설)는 가드를 거친다. `확인 중으로
표시`는 입력을 저장하지 않고 드로어도 닫지 않으므로 가드를 거치지 않는다. 바쁜 동안 다른 헤더 링크·뒤로가기로
  떠나려 하면 가드가 `처리 중인 작업이 있어요`로 묻는다(3.4의 2026-10-15 문단). 드로어 둘 다 바쁜 상태를 등록한다.
- **초점 복귀.** 상태를 바꾸면 연 카드가 다른 열로 가 돌아갈 곳이 없어진다. 그때는 보드 제목으로 돌아간다
  (`useModalFocus`의 `restoreFallbackRef`).
- **움직임.** 열고 닫는 트랜지션은 두지 않는다(핸드오버 Interactions의 "트랜지션 없음").

### 7.3 등록 요청 드로어

`FacilityRequestReviewModal`의 로직(상세 조회, 사진 공개 선택, 상태 변경, 승인·거절, 409 처리, 남은 사진 정리)을 옮긴다.

- 왼쪽 `FacilityFields`(위치 칸 끔, 4.2), 오른쪽 위치 미니맵. 미니맵은 `FacilityMap`이고 건물 강조색으로 크림슨을
  넘긴다(3.6).
- `거절`은 하단 바가 인라인 확인으로 바뀐다. `ConfirmModal`을 겹쳐 띄우지 않는다.
- 2026-10-15 — **승인·거절 뒤에도 드로어는 열린 채 처리 후 상태를 보인다.** 사용자 결정. 지금 모달은 승인·거절에
  성공하면 닫혔다. 7.2와 핸드오버 6절의 처리 후 바(`승인되어 시설로 등록됐어요` + `만들어진 시설 보기 →` /
  `거절된 요청이에요`, 남은 사진이 있으면 `남은 사진 정리`)를 따른다. 응답을 받으면 바로 끝 상태로 바꿔 값을 읽기
  전용으로 하고, 번역·revalidate·보드 다시 받기·상세 다시 읽기가 끝날 때까지 바쁜 상태를 유지한다. 뒤따르는 상세
  다시 읽기가 실패해도 닫지 않고 경고만 띄운다. 처리 후에 보이는 값은 요청 원본이다 — 관리자가 고친 값은 만들어진
  시설에 들어간다.
- 2026-10-15 — 위치 판정 문구는 셋이다. 요청 위치 그대로면 `제보자가 찍은 위치가 있어요`, 관리자가 지도에서 옮겼으면
  `지도에서 고른 위치예요`, 없으면 `위치 없음 · 지도에서 찍어 주세요`. 핸드오버는 앞의 하나와 마지막만 정한다.
- 2026-10-15 — `FacilityFields`는 독립 시설 패널처럼 `.ku-detail-form`으로 감싸 토큰 색을 받는다. `FacilityMap`은 높이를
  prop으로 받고(공개 요청 모달은 기본 250px 그대로) 위치 버튼에 class를 달아 드로어 안에서 토큰 색으로 덮는다.

### 7.4 피드백 드로어

`FeedbackDetailModal`을 옮긴다. 하단 상태 세그먼트는 누르면 바로 저장한다. `다음 항목 →`은 같은 열의 다음 카드다.

`보낸 화면`은 `page_url` 원문을 글자로 보인다. 링크는 그 주소의 출처가 이 사이트(`window.location.origin`)와 같을
때만 건다(2.11). 지금 모달은 아무 http(s) 주소나 `제보한 페이지`라는 문구 뒤에 링크로 건다.

2026-10-15 — 구현하며 정한 것:

- **`다음 항목 →`** 은 드로어를 연 열에서 지금 항목의 정렬 위치(접수 시각 내림차순 → 등록 요청 먼저 → id) 바로 뒤의
  카드다. 찾는 목록은 연 순간의 스냅샷(7.2)과 그 열의 지금 카드를 합친 것이다 — 상태를 바꾸면 보드가 첫 페이지로
  돌아가 이어 붙인 페이지가 사라지는데, 스냅샷이 있어 그 페이지의 다음 카드로도 간다. 종류는 가리지 않아 `전체`에서는
  등록 요청 드로어로 바뀔 수 있다. 다음이 없으면 버튼을 그리지 않는다. 데스크톱에만 있다(모바일 프로토타입에 없음).
- 상태를 저장하면 `신규로 되돌렸어요` / `확인 중으로 바꿨어요` / `처리 완료로 바꿨어요` 토스트를 띄운다(핸드오버 7절
  "PATCH + 토스트"). 지금 목록은 실패만 알렸다.

### 7.5 모바일

세그먼트 `등록 요청 n / 피드백 n` + 상태 칩(지금 `INBOX_FILTERS`의 다섯 값) + 카드 목록 → 전체 화면 상세.

2026-10-15 — **모바일 등록 요청 상세는 데스크톱과 같은 로직이다.** 사용자 결정. 프로토타입 모바일은 읽기 전용(값 카드 +
사진 가로줄, 지도·거절 확인 없음)이지만 7.3의 "로직을 옮긴다"를 따른다. 같은 드로어가 전체 화면이 되고 본문은 한 열(사진
→ 필드 → 지도 190px → 위치 판정)이다. 하단 바는 `거절`(1) / `승인하고 등록`(2)이고, `확인 중으로 표시`와 `사진 {k}/{n}장
공개`는 본문 위쪽으로 옮겼다. 상태 칩의 기본은 `처리 전`이다.

### 8.1 vitest

- 칩 조건과 개수(시설·명소·경사도)
- 항목 id로 그 항목이 있는 페이지 찾기(3.3)
- `slopeGradeFromDeg` — 1/12·30% 경계와 허용오차는 `slopeWarningFromDeg` 테스트와 같은 값
- 경로 요약 — 구간 수, 총 거리, 최대 경사, 판정별 구간 수
- 제보함 두 목록을 접수 시각순으로 합치기, 같은 id 하나만 두기, 낡은 세대 응답 버리기
- `workspaceUrl` — 넷 상태 읽고 쓰기, 우선순위(`new` > `id`, `edit`은 `id`와 함께 경사도에서만), 모르는 파라미터 보존
- 시설 저장 공유 함수의 결과(저장 실패 / 번역 실패 / revalidate 실패)
- 피드백 주소가 같은 출처인지 판정

### 8.2 Playwright — 무너지는 기존 단언

- 행의 `수정`·`삭제`·`동영상`·설치 토글 버튼을 찾는 시설·명소 시나리오 → 행 클릭 뒤 패널 버튼
- `명소를 서버 페이지 단위로 조회` → 전체 조회 + 클라이언트 페이지
- `/admin/slopes/new`·`/admin/slopes/[id]`로 들어가는 편집기 시나리오 → 리다이렉트를 거친 패널 편집
- 리다이렉트 사유 안내(`redirected=missing|invalid`) 시나리오 → 3.4·6.2의 새 표시
- 제보함 탭·상태 select·검토 모달 시나리오 → 보드·드로어

각 PR 계획에서 해당 spec 파일의 시나리오를 하나씩 대조해 목록을 확정한다.

### 8.3 Playwright — 새로

- 마커 클릭 ↔ 행 선택, 다른 페이지 마커 클릭 시 목록 이동
- 조회가 늦게 끝나도 `?id=` 링크가 그 항목을 연다
- 저장 안 한 변경이 있을 때 확인 — 다른 항목 선택, 헤더 nav 링크, 브라우저 뒤로가기
- 설치 상태를 바꾼 뒤 이름을 고쳐 저장해도 설치 상태가 남는다
- 위치를 지도 클릭으로 옮기고 저장
- 옛 경사도 라우트 리다이렉트(307), 겹친 쿼리의 우선순위
- 제보함 `전체`에서 한쪽 API만 실패하면 성공한 쪽과 안내가 함께 보인다
- 다크 모드 크림슨 채움 대비(`admin-dark.spec.ts`에 더함)

2026-10-15 — 작업 화면 세 spec과 제보함 spec이 같이 쓰는 화면 헬퍼(저장 안 한 변경 확인 창, `beforeunload` 판정,
관리자 메뉴, 상세 패널 region, Supabase 500 응답)는 `e2e/support/adminWorkspace.ts`에 둔다. 확인 창 제목이나 판정
방식이 바뀌면 그 파일 하나만 고친다. 탭마다 이름이 다른 목록 패널(`listPanel`)과 그에 기대는 `listRow`는 각 spec에 둔다.

2026-10-15 — 작업 화면 세 spec은 같은 실패 경로 시나리오를 갖춘다. 삭제 실패는 반환된 메시지를 오류 토스트로 알리고 행을
남긴다. 삭제를 기다리다 다른 탭으로 떠나도 끝난 삭제가 그 탭의 주소·패널·입력을 건드리지 않는다. 첫 목록 조회가 실패한
`?id=` 링크도 `다시 시도`가 그 항목의 페이지와 패널을 연다(2페이지 항목). 첫 조회를 기다리다 떠나도 늦게 끝난 조회가 그 탭을
건드리지 않는다. 저장·삭제 뒤 다시 받기가 실패하면 불러오기 오류가 마지막 토스트로 남는다. 경사도는 모바일 편집 패널의
삭제가 목록으로 돌아가 연 다른 경로를 닫지 않는지도 본다(삭제 버튼이 보기 패널이 아니라 편집 패널에 있다).
