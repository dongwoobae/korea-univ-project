# 시설 종류 관리 설계

2026-10-26

## 이 문서의 목적

관리자가 시설 종류(`facility_types`)를 화면에서 추가·수정·삭제하고 순서를 바꾸게 한다. 2026-10-26 사용자 요청이고, 멘토링 설계
(`docs/specs/2026-10-25-mentoring-feedback-design.md`) 1장의 PR ②-2, 12장 닫힌 질문 3이 이 문서를 가리킨다.

지금까지 종류의 아이콘·색은 코드에 있었다(`2026-08-13-public-map-lucide-icons-design.md`, 근거는 "유형이 5종 고정이라 스키마·관리자
개편 비용 대비 이득 없음"). 관리자가 종류를 더하면 그 전제가 깨진다. 장애학생 휴게실을 더할 때도 코드를 고쳐야 했다(멘토링 설계 4.2).

결정 표기: **[사용자]**는 사용자가 정한 것, **[판단]**은 Claude가 정하고 사용자에게 알린 것이다.

## 1. 데이터 (②-2a)

### 1.1 칸

`facility_types`에 두 칸을 더한다(`sort_order`는 멘토링 설계 4.2에서 이미 들어갔다).

| 칸      | 정의                                                                  | 뜻                                        |
| ------- | --------------------------------------------------------------------- | ----------------------------------------- |
| `icon`  | `text not null default 'accessibility'`                               | 아이콘 목록(1.3)의 키. lucide 이름 꼴     |
| `color` | `text not null default '#666666'`, `check (color ~ '^#[0-9A-F]{6}$')` | 마커·칩의 바탕색. 흰 아이콘·글자를 얹는다 |

- 기본값이 있어 이름만 넣는 기존 코드·DB 테스트(`admin_write_policies.test.sql`·`activity_log_triggers.test.sql`의 `facility_types`
  삽입)가 그대로 돈다.
- **[판단]** `icon`에는 목록 검사를 두지 않는다. 목록은 코드에 있어, DB 검사를 두면 아이콘 하나를 더할 때마다 마이그레이션이 든다.
  목록에 없는 키는 화면이 대체 아이콘으로 그린다(2.2).
- `color`는 대문자 `#RRGGBB`만 받는다. 화면은 색 목록(1.3)에서만 고르게 한다.

### 1.2 채우기

마이그레이션이 지금 종류를 채운다. 화면이 바뀌지 않도록 지금 코드 값(`mapIcons.ts`·`theme.ts`) 그대로 옮긴다.

| ---------------- | ---------------- | --------- |
| `restroom`       | `toilet`         | `#2F7A4F` |
| `ramp`           | `trending-up`    | `#B25617` |
| `parking`        | `square-parking` | `#6D4AB0` |
| `elevator`       | `elevator`       | `#2D5FB0` |
| `student_lounge` | `sofa`           | `#0F766E` |
| `braille`        | `grip-vertical`  | `#8A6A00` |

- `automatic_door`(코드가 몰랐던 종류)는 기본값(`accessibility`, `#666666`)을 받는다. 마커는 지금도 `#666`이고, 필터 칩만 대체
  팔레트의 보라 `#6D28D9`에서 회색으로 바뀐다. 주차 보라 `#6D4AB0`와 비슷하던 문제도 같이 사라진다.
- `braille`은 운영 표에 없다. 행이 없으면 `update`가 아무것도 하지 않는다.
- 채우기는 종류마다 "시설 종류 수정" 기록을 남긴다. **[판단]** 여섯 줄 안팎이라 트리거를 끄지 않는다 — 아이콘·색이 정해진 기록이 남는
  것이 맞다. 활동 기록 표시 이름표(`activityLabels.ts`의 `COLUMN_LABELS`)에 `color` → "색"을 더한다(`icon` → "아이콘"은 이미 있다).

### 1.4 지우는 것

`FacilityCode` 타입(`src/types/domain.ts`), `facilityColor`(`src/lib/theme.ts`), `FALLBACK_PALETTE`와 목록 위치로 색을 고르던
`getFacilityColor`(`facilityColors.ts`), 코드로 아이콘 키를 고르던 `FACILITY_ICON_KEY`(`mapIcons.ts`). 아이콘·색은 모두 DB 값이
정한다. 이 셋을 시험하던 단위 테스트(`facilityColors.test.ts`, `mapIcons.test.ts`의 `facilityIconKey`)는 목록과 훅을 시험하도록 바꾼다.

### 1.5 새 종류의 `code` (②-2b)

**[판단]** 관리자가 정하지 않는다. 화면이 `type_` + 무작위 소문자·숫자 8자로 만든다. 만든 뒤에는 바꾸지 않는다 — 시설
(`building_facilities.facility_code`, 외래 키)과 등록 요청(`facility_requests.facility_code`, 외래 키 없는 문자열)이 이 값으로 종류를
가리킨다. 기본 키라 겹치면 DB가 거부하고, 화면은 새 값으로 한 번 더 시도한다.

## 2. 공용 훅과 그리는 곳 (②-2a)

### 2.1 `useFacilityTypes()`

새 파일 `src/lib/facilityTypesStore.ts`(`slopeBandsStore.ts`와 같은 `useSyncExternalStore` 모양). 모듈 하나가 종류 목록을 받아 둔다.

- 조회: `facility_types`를 `select("*")`, `sort_order, code` 순. 여러 컴포넌트가 동시에 불러도 요청은 하나다.
- 돌려주는 것: 종류 목록, 상태(`loading` | `ready` | `error`), `loaded`(한 번이라도 받았는지 — 빈 자리(받기 전)와 대체 아이콘(받은 뒤
  모르는 코드)을 가른다). 코드로 아이콘·색을 찾는 것은 카탈로그의 `facilityStyleOf(types, code)` → `{ icon, color }`, 컴포넌트에서는
  `useFacilityStyle(code)`.
- `facilityStyleOf`는 목록에 없거나 아직 받지 못한 코드에 대체값(`accessibility`, `#666666`)을 준다. 아이콘 키가 목록(1.3)에 없거나 색
  형식이 틀리거나 칸이 없는 행(2.4)도 그 칸만 대체값이다.
- `reloadFacilityTypes()`: 다시 받는다. 받기 실패 뒤 다시 시도와 ②-2b 관리 화면의 쓰기 뒤에 부른다. **다시 받는 동안에도 직전 목록을
  그대로 쓴다** — 비우면 모든 아이콘이 잠깐 대체 아이콘으로 바뀐다. 다시 받기가 실패하면 직전 목록을 두고 상태만 `error`로 둔다. 먼저
  시작한 받기가 나중에 끝나면 그 결과는 버린다. 받기가 끝나면 성공 여부(`true`·`false`)로 풀리는 약속을 돌려준다 — 관리 화면(3.2)이
  다시 받은 뒤에 화면을 맞춘다. 그사이 더 늦게 시작한 받기에 밀려난 받기는 그 최신 받기의 결과로 풀린다.
- **처음 받기 전**(직전 목록이 없을 때) `<FacilityTypeIcon>`은 같은 크기의 빈 자리를 그린다. 대체 아이콘은 목록을 받은 뒤에도 모르는
  코드일 때만 쓴다 — 받기 전에 휠체어가 번쩍이지 않게. 색을 쓰는 곳도 받기 전에는 `styleOf`의 대체 회색이 잠깐 보일 수 있다.
  공개 지도 마커는 필터 칩을 켜야 보이고 칩은 목록을 받은 뒤에 그려져 이 경우가 없다.
- **[판단]** 다른 관리자가 고친 것은 새로 고침해야 보인다. 종류는 드물게 바뀐다.
- 공개 지도와 관리자 화면 모두 브라우저 Supabase 클라이언트로 읽는다(공개 읽기 정책 `public read facility_types`가 있다).

### 2.2 바꿀 곳

- 종류 조회 다섯 곳 → 훅: 공개 지도 `useMapData.ts`(지금의 실패·"다시 시도" 흐름을 훅의 상태·다시 불러오기로 잇는다. 지금은 목록을
  받을 때마다 필터 선택을 모두 끈다 — 다시 받아도 남은 코드의 선택은 유지한다), 등록 요청
  모달 `FacilityRequestModal.tsx`, 관리자 건물 상세 `admin/buildings/[id]/page.tsx`, 독립 시설 탭 `admin/dashboard/facilities/page.tsx`,
  제보함 `admin/dashboard/inbox/page.tsx`. 등록 요청 API 두 곳(`eq("code", …)`로 한 행 확인)은 그대로다.
- `<FacilityTypeIcon code>`: 겉모습을 그대로 두고 안에서 훅으로 아이콘을 찾는다. JSX로 쓰는 곳(공개 시설 목록·지도 안 목록·필터
  칩, 관리자 건물 상세 시설 카드·시설 목록 행·상세·동영상 모달·제보함)은 손대지 않는다.
- 색을 쓰는 곳 → `facilityStyleOf(types, code).color`: 공개 필터 칩(`FilterPanel.tsx`), 관리자 시설 목록 행(`FacilityListRow.tsx`)·상세
  (`FacilityDetailPanel.tsx`)·제보함 드로어(`FacilityRequestDrawer.tsx`)·시설 탭의 종류 표시(`facilities/page.tsx`).
- 마커 HTML을 만드는 두 곳 — 공개 `FacilityMarkers.tsx`, 관리자 `FacilityWorkspaceMap.tsx` — 은 컴포넌트에서 받은 스타일을 넘긴다.
- **위험:** 마커 divIcon 캐시 두 곳의 키에 아이콘이 없다. 공개 `FacilityMarkers.tsx`의 `cachedIcon`은 `facility|코드|시설id`, 관리자
  `FacilityWorkspaceMap.tsx`의 `markerIcon`은 `시설id|코드|색|선택`이다. 종류를 받기 전에 만든 대체 아이콘이나 아이콘만 바꾼 종류의 옛
  아이콘이 그 키로 남는다. 두 키 모두에 아이콘 키와 색을 넣는다.

### 2.3 결과

화면은 지금과 같다. 바뀌는 것은 자동문 필터 칩 하나(보라 → 회색, 마커와 같은 색)와, 관리자 화면에서 종류를 받기 전 아이콘 자리가
잠깐 비는 것(지금은 코드에서 바로 그린다)이다.

### 2.4 배포 사이

새 코드가 마이그레이션보다 먼저 뜨면 `select("*")`가 `icon`·`color` 없는 행을 돌려준다. 오류는 없고 모든 종류가 대체 아이콘으로
보이며, 그 목록을 받아 둔 화면은 새로 고침할 때까지 그대로다. **[사용자]** 상용 배포 전이라 받아들인다(멘토링 설계 "알아야 할
상황"). 막으려면 나중에 지울 임시 코드(칸이 없는 목록을 받아 두지 않기)가 필요해 넣지 않는다.

## 3. 관리 화면 (②-2b)

### 3.1 여는 곳

독립 시설 탭(`/admin/dashboard/facilities`) 목록 패널 아래 범례 줄에 "종류 관리" 버튼(모바일은 목록 시트를 펼친 아랫줄). 누르면 모달이
열린다. 종류를 한 번도 받지 못했으면 버튼이 꺼진다 — 이름 겹침 검사(3.3)가 받은 목록에 기댄다. 탭은 늘리지 않는다 — 탭 여섯 개가 태블릿
폭에서 넘치던 문제를 #53에서 막았다.

**[판단]** 2026-10-26 처음 적은 자리는 "＋ 시설 추가" 옆이었다. 모바일 시트 머리 줄에는 이름·개수·정렬·추가가 이미 한 줄로 있어 좁은
폭에서 넘칠 수 있다. 경사도 탭의 "범례 편집"과 같은 자리이고, 범례가 종류별 색이라 뜻도 맞다.

### 3.2 목록

`sort_order` 순으로 종류마다 한 줄: 아이콘(색 동그라미), 한국어 이름, 영어·중국어 이름(작게), 쓰는 시설 수, ▲▼, 수정, 삭제. 맨 위에
"＋ 종류 추가".

- 쓰는 시설 수와 검토 대기 요청 수는 모달을 열 때 새 관리자 라우트 `GET /api/facility-types/usage`로 받는다(응답
  `{ [code]: { facilities, pendingRequests } }`). `facility_requests`는 브라우저 클라이언트(`authenticated`)에 읽기 권한이 없어
  (`20261008000000_create_facility_requests.sql`이 회수) 서버가 `requireAdmin` 뒤 서비스 키로 센다. 시설 수도 같은 응답으로 받는다.
  실패하면 삭제 버튼을 모두 끄고 "사용 현황을 불러오지 못했어요"와 다시 시도 버튼을 보여 준다. 서버는 종류마다 개수만 묻는다
  (`count: exact, head`). 행을 받아 세면 PostgREST 최대 행 수에서 잘려 덜 센다.
- ▲▼는 사진 순서(멘토링 설계 3.2·3.4)와 같은 규칙이다: 누르면 화면을 먼저 바꾸고 바로 저장, 저장 중 모든 화살표 잠금
  (`aria-disabled`), 맨 앞·맨 끝만 `disabled`. 초점은 옮긴 줄의 같은 방향 화살표로 가고, 끝에 닿아 그 화살표가 꺼지면 같은 줄의 반대쪽
  화살표로 간다. 버튼 이름은 "<종류 이름> 위로 옮기기"·"<종류 이름> 아래로 옮기기"다(이름은 겹치지 않는다, 3.3).
- 종류 목록 다시 받기가 실패하면 모달 맨 위에 "종류 목록을 새로 불러오지 못했어요"와 다시 시도를 두고, 다시 받을 때까지 추가·수정·삭제·
  순서 바꾸기를 잠근다 — 낡은 목록으로 이름 겹침을 검사하거나 순서를 판정하지 않게.
- 맞바꾸기 RPC `swap_facility_type_order(p_first text, p_second text)`: 인자는 화면 순서(앞 종류, 뒤 종류).
  - **잠금을 먼저 잡고 읽는다.** 표 단위 advisory 잠금(`pg_advisory_xact_lock(hashtext('facility_types.sort_order'))`)을 잡은 뒤 두 행을
    `for update`로 읽어 판정한다. 잠금 없이 읽으면 겹치는 두 쌍(A·B와 B·C)을 동시에 바꿀 때 둘 다 옛 번호로 판정하고 써서 번호가
    겹친다. 사진 맞바꾸기(`swap_building_photo_order`)와 같은 구조다.
  - 앞 종류가 지금 뒤 종류의 바로 앞이 아니면(사이에 종류가 있거나 앞뒤가 뒤집힘) `PT409`, 종류가 없으면 `P0002`, 같은 종류면
    `22023`, 보이지만 고칠 권한이 없으면 `42501`.
  - 호출자 권한(`security invoker`)으로 돌아 기존 `admin write` 정책이 걸리고, 실행 권한은 `authenticated`에만 준다(`anon`·`public`·
    `service_role`에서 회수).
  - 화면: `PT409`·`P0002`면 목록을 다시 불러오고 "순서가 바뀌어 다시 불러왔어요", 그 밖은 화면을 되돌리고 오류 토스트. 되돌린 실패는
    활동 기록에 실패로 보고한다(작업 키 `facility_types.update`, 대상은 누른 종류의 `code`, HTTP 상태 포함) — 브라우저 쓰기 관문이
    `rpc/`를 건너뛰기 때문이다(사진 순서와 같은 이유, 멘토링 설계 3.4). 성공하면 `reloadFacilityTypes()`.
- **번호가 겹치지 않음을 DB가 보장한다.** ②-2b 마이그레이션이 `facility_types`에 `unique (sort_order) deferrable initially immediate`를
  더하고(맞바꾸기 한 문장이 중간 상태에서 걸리지 않게 문장 끝에 검사), identity 시퀀스를 지금 가장 큰 번호로 맞춘다(`setval`). 멘토링 ②
  마이그레이션이 identity가 채운 번호를 손으로 덮어써 시퀀스와 실제 번호의 관계가 보장되지 않기 때문이다(운영은 2026-10-26 기준
  1~5·7로 겹치지 않는다).

### 3.3 추가·수정 폼

모달 안에서 목록 대신 폼으로 바뀐다(뒤로 가기 버튼).

- 한국어 이름: 필수, 30자, 앞뒤 공백을 떼어 저장한다. 같은 이름이 이미 있으면 저장 전에 막는다.
- 영어·중국어 이름: 각 60자. "자동번역 채우기"는 `/api/translate`로 한국어를 번역해 **비어 있는 칸만** 채운다(명소 화면
  `landmarkSave.ts`의 `fill`과 같은 규칙). 실패하면 칸을 비운 채 경고 토스트를 띄우고 직접 적게 한다. 저장은 막지 않는다.
- **빈 칸은 `NULL`로 저장한다**(공백만 있어도). 화면들은 `label_en ?? label`처럼 `NULL`일 때만 한국어로 대체한다(`FilterPanel.tsx`의
  `facilityLabel`, `SidePanel.tsx`의 `getFacilityLabel`) — 빈 문자열이 들어가면 영어·중국어 화면에 이름이 빈 칩이 뜬다.
- 아이콘: 1.3의 30개를 격자로 보여 주고 이름을 붙인다. 고른 것은 눈에 구분된다.
- 색: 1.3의 10개 견본. 이름을 접근 가능한 이름으로 단다.
- 미리보기: 고른 아이콘·색으로 지도 마커 모양과 필터 칩 모양을 보여 준다.
- 저장: 추가는 `insert`(1.5의 `code`, `sort_order`는 비워 맨 뒤), 수정은 `update`(이름·아이콘·색). 성공하면
  `reloadFacilityTypes()` 후 목록으로 돌아가 토스트. 실패하면 폼을 그대로 두고 오류 토스트.
- 수정·삭제가 0행으로 끝나면(그사이 지워졌거나 권한이 없다 — RLS는 오류 없이 거른다) 실패로 알리고 목록과 사용 현황을 다시 받는다.
- 자동번역을 기다리는 동안 한국어 이름 칸을 잠근다. 요청한 뒤 이름을 바꾸면 옛 이름의 번역이 빈 칸에 들어간다.
- 실패 보고는 브라우저 쓰기 관문(`reportingFetch`)이 한다. 다만 관문(`supabaseWriteReporting.ts`의 `restWrite`)은 대상 키를 `?id=eq.`에서만
  읽어, `code`로 고르는 `facility_types`의 수정·삭제 실패는 대상이 빈다. `facility_types`는 `?code=eq.`를 대상 키로 읽게 고친다.
- **시설 쪽에 붙은 옛 이름.** 시설 조회는 종류 이름을 시설에 붙여 가져온다(`facility_types(code, label, …)` 임베드 — 공개
  `/api/facilities`, 시설 탭 목록 등). 공개 `/api/facilities`는 1시간 캐시(`revalidate = 3600`)라, 종류 이름을 고치거나 지운 뒤 그대로 두면
  공개 지도 시설 이름표에 옛 이름이 남는다. 수정·삭제가 성공하면 기존 `POST /api/revalidate-facilities`를 부르고(시설 저장과 같다), 모달을
  닫을 때 시설 탭이 자기 시설 목록을 다시 읽는다. 다른 관리자 화면은 그 화면을 다시 열 때 새 이름을 받는다.

### 3.4 삭제

- 쓰는 시설이 1곳이라도 있거나 검토 대기 요청(`new`·`reviewing`)이 1건이라도 있으면 삭제 버튼을 끄고 이유를 보여 준다("시설 N곳이
  이 종류를 써요", "검토 대기 요청 N건이 이 종류로 들어왔어요"). 끝난 요청(승인·거절)은 기록이라 막지 않는다.
- 지울 수 있으면 확인 창("종류를 삭제할까요?") 뒤 `delete`. 그사이 누가 시설을 붙였으면 외래 키가 막는다(`23503`) — 목록을 다시 불러와
  수를 보여 주고 알린다.
- 시설 탭의 유형 필터가 지운 종류를 고르고 있었으면 "모든 유형"으로 돌아간다.
- 대기 요청은 외래 키가 없어 DB가 막지 못한다. 수를 센 뒤 지우기 전 사이에 요청이 들어오면 그 요청의 종류가 사라진다 — 승인
  라우트가 종류가 없다고 거부하고(`approve/route.ts`의 `facility_types` 확인), 관리자는 드로어에서 종류를 바꿔 승인한다. 받아들인다.
- 삭제된 종류 코드를 가진 끝난 요청은 제보함 드로어에서 대체 아이콘과 이름 "시설"로 보인다(`FacilityRequestDrawer.tsx`의
  `typeLabel` 대체값). 받아들인다.

### 3.5 하지 않는 것

종류 숨기기, 다른 종류로 옮기며 삭제, `code` 직접 입력·변경, 아이콘·색 목록 자체를 화면에서 고치기, 다른 관리자의 변경을 실시간으로
받기, 끌어서 순서 바꾸기.

### 4.1 ②-2a

- pgTAP: 두 칸과 기본값, 색 형식 검사(`red`·`#fff`·소문자 거부), 빈 DB에도 있는 `restroom`·`student_lounge`(멘토링 ② 마이그레이션이

  불러도 요청이 하나인지.

- 병합 뒤: 방문자 키로 종류의 `icon`·`color`를 읽어 1.2 표와 맞춘다. 사용자가 공개 지도에서 아이콘·색이 전과 같은지(자동문 칩만 회색)

### 4.2 ②-2b

- pgTAP: 맞바꾸기 RPC — 이웃 맞바꾸기, 이웃 아님·뒤집힘 `PT409`, 없는 종류 `P0002`, 같은 종류 `22023`, 관리자 목록 밖 계정 거부,

  한 세션인 pgTAP으로 볼 수 없어 리뷰가 잠금 순서(잠금 → `for update` 읽기 → 판정)를 코드로 본다.
- 단위(vitest): `/api/facility-types/usage` — 관리자 아님 403, 코드별 시설 수·대기 요청 수(`new`·`reviewing`만), DB 오류 500. 기존
  라우트 테스트(`inbox-counts/route.test.ts`)의 흉내 방식을 따른다.
- E2E 목 백엔드: 종류 목록을 상태로 옮겨 `insert`·`update`·`delete`(`?code=eq.`로 고른다)와 RPC를 흉내 낸다. 지금은 고정 상수라
  쓰기가 반영되지 않는다. 시설 행의 `facility_types` 임베드도 읽을 때마다 상태의 종류에서 만든다 — 지금은 픽스처·시설 생성 때 붙인
  객체가 그대로 남아 종류 이름을 바꿔도 반영되지 않는다(`projectEmbeds` 전에 만든다).
- E2E: 추가(자동번역·아이콘·색) 뒤 목록과 공개 필터에 나온다, 빈 영어 칸은 `NULL`로 저장된다, 이름 중복을 막는다, 쓰는 시설·대기
  요청이 있으면 삭제가 꺼진다, 지울 수 있는 종류를 지운다, 이름을 바꾸면 시설 탭 목록의 종류 이름이 바뀌고 `revalidate-facilities`가
  불린다, ▲▼(초점·잠금·실패 되돌림과 보고), 모바일 폭 44px 터치.
- 단위(vitest): `restWrite`가 `facility_types` 쓰기의 대상 키를 `?code=eq.`에서 읽는다.
- 병합 뒤: 사용자가 운영에서 시험 종류 하나를 만들었다가 지운다. 활동 기록에 "시설 종류 등록·수정·삭제"가 남는지 본다.

## 5. 버린 대안

- **시설을 읽을 때 종류의 아이콘·색을 같이 받기**(`facility_types(…, icon, color)` 임베드) — 시설 조회 네 곳과 목 픽스처를 고쳐야 하고,
  코드 문자열만 있는 제보함은 따로 종류 목록이 필요해 두 길이 섞인다.
- **코드 매핑을 남기고 DB 값이 있으면 덮어쓰기** — 아이콘이 두 군데서 정해져 "왜 이 색인지"를 매번 두 곳에서 찾게 된다.
- **이름만 관리하고 아이콘은 개발자가 코드에 붙이기** — 휴게실 때와 같은 일이 종류마다 반복된다.
- **아이콘만 고르고 색은 아이콘에 따라 자동** — 두 종류가 같은 아이콘을 고르면 색도 같아진다.
- **`icon`에 DB 목록 검사** — 아이콘을 더할 때마다 마이그레이션이 든다.
- **헤더 일곱 번째 탭·"설정" 메뉴** — 탭은 태블릿 폭에서 다시 넘칠 수 있고, 설정 메뉴는 한 번 더 눌러야 한다.
- **쓰이는 종류를 숨기기·다른 종류로 옮기며 삭제** — 칸과 규칙이 늘거나, 실수 한 번에 많은 시설의 종류가 바뀐다.
