# requireAdmin이 로그인 여부만 보고 역할을 보지 않는다

`src/lib/requireAdmin.ts`는 이름과 달리 **관리자인지 확인하지 않는다.** Bearer
토큰을 꺼내 `authClient.auth.getUser(token)`이 사용자를 돌려주면 그대로 통과시킨다
(`requireAdmin.ts:33-39`). 역할·허용 목록·커스텀 claim을 보는 코드가 없다.

```ts
const { data, error } = await authClient.auth.getUser(token);
if (error || !data?.user) return unauthorized();
return { user: data.user };
```

즉 **인증된 아무 계정이나 관리자 API를 부를 수 있다.** 그리고 그 API들은
`SUPABASE_SERVICE_ROLE_KEY`로 만든 클라이언트를 쓴다 — RLS를 우회한다.
`facility-video-confirm` · `delete-facility-video` · `upload-building-photo` ·
`delete-landmark-photo` 등이 모두 같은 구조다.

지금 실제 피해가 없는 이유는 **가입 경로가 닫혀 있어 관리자 계정 외에 인증된
계정이 없기 때문**으로 보인다. 그건 코드가 보장하는 성질이 아니라 운영 상태다.
Supabase 프로젝트에서 이메일 가입을 켜거나, 공개 화면에 로그인이 생기거나,
누군가 계정을 하나 더 만드는 순간 전제가 무너진다.

## 왜 지금 값어치가 올라갔나

2026-08-06 3-lane 리뷰에서 이 항목은 **다른 취약점의 공격 문턱을 낮추는 증폭
요인**으로 드러났다. `facility-video-confirm`이 URL을 검증 없이 저장하던 문제와
엮이면 인증된 사용자가 R2 버킷의 임의 객체를 지울 수 있었다. 그 경로는
`b914f07`에서 막았지만, **막은 것은 결과이고 문턱은 그대로다.**

## 막힌 이유

**차단 사유 없음.** 미룬 이유는 범위였다 — 이번 브랜치(`facility-detail-modal`)는
시설 모달과 동영상 섹션 작업이고 `requireAdmin.ts`를 건드리지 않았다. 인증 통제를
같이 바꾸면 리뷰 단위가 흐려진다고 판단했다.

착수 전에 확인이 필요한 것은 **관리자를 무엇으로 식별할지 정해져 있지 않다는
점**이다. 현재 저장소에 관리자 목록·역할 컬럼·claim 설정이 보이지 않는다.
이걸 정하지 않으면 코드를 못 쓴다.

## 트리거

없음. 언제든 착수 가능하다.

다만 아래 중 하나라도 벌어지면 **선택이 아니라 필수**가 된다.

- Supabase에서 이메일/소셜 가입이 켜진다
- 공개 화면에 로그인 기능이 생긴다
- 관리자 계정이 2개 이상이 되고 권한을 나눠야 한다

## 착수 시 정할 것

- **관리자를 무엇으로 식별할지.** 선택지와 함의:
  - **환경변수에 이메일 화이트리스트** — 가장 빠르고 의존성이 없다. 대신 사람이
    늘면 배포를 해야 하고, 누가 관리자인지가 코드 밖에 있어 추적이 안 된다.
  - **Supabase user metadata의 커스텀 claim** — 콘솔에서 바꿀 수 있고 배포가 필요
    없다. 대신 claim을 누가 어떻게 부여하는지 절차가 필요하다.
  - **DB에 `admin_users` 테이블** — 이력과 감사 로그를 남기기 좋다. 대신 API마다
    조회가 한 번 더 붙고, 그 테이블 자체의 RLS를 또 정해야 한다.
- **범위.** `requireAdmin` 한 곳만 고치면 이를 쓰는 모든 라우트가 함께 닫힌다.
  쓰지 **않는** 경로가 있는지 먼저 훑어야 한다 — `git grep -n "requireAdmin"`으로
  현재 사용처를 확인하고, `src/app/api/` 아래에 이 가드가 없는 라우트가 있는지
  대조할 것.
- **관리자 화면 자체는 어떻게 할지.** 이 함수는 API 라우트용이다. 화면 쪽
  접근 통제(`/admin/**`)가 지금 무엇에 기대고 있는지 확인하고, 둘의 기준을
  맞출지 따로 둘지 정한다.
- **기존 세션을 끊을지.** 역할 검사를 켜면 claim이 없는 기존 로그인은 즉시 401이
  된다. 관리자 본인이 로그아웃되는 상황을 예상하고 순서를 잡아야 한다.
