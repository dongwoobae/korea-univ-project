# 관리자 계정을 화면에서 추가·삭제할 수 없다

관리자는 Supabase Auth의 이메일·비밀번호로 로그인한다(`src/app/admin/page.tsx`의
`signInWithPassword`). 계정을 만들고 지우는 화면은 없다. 지금은 개발자가 Supabase
콘솔에서 직접 만든다.

운영을 지속관리원에 넘길 때 **사람마다 계정을 따로 쓰라고 안내할 예정**이다. 그래야
변경 기록에 "누가 했는지"가 사람 단위로 남는다. 그러려면 비개발자도 계정을 만들 수
있어야 한다. 콘솔 접근 권한을 넘기는 것은 답이 아니다. 콘솔은 DB 전체를 만질 수 있다.

## 역할 분리가 처음 필요해지는 곳

변경 기록 자체는 역할 없이도 성립한다. 기록에 필요한 것은 "누구인지"이지 "무엇을 할
수 있는지"가 아니다. **계정을 만드는 화면은 다르다.** 계정을 만들 수 있는 사람은
관리자를 늘릴 수 있는 사람이다. 모든 관리자가 이 화면을 쓸 수 있으면, 나중에 권한을
제한한 관리자를 두더라도 그 사람이 자기 권한을 넓힌 계정을 하나 더 만들면 끝난다.

## 막힌 이유

차단 사유는 없다. 순서상 뒤로 미뤘다. 이 화면은 `admin_users` 허용 목록과
`is_admin()` 위에 얹힌다. 둘은 `supabase/migrations/20261019000000_create_activity_logs.sql`이 만든다.

## 트리거

- 지속관리원 이관 일정이 잡히면 **선택이 아니라 필수**가 된다.

## 착수 시 정할 것

- **역할을 어떻게 나눌지.**
  - `admin_users.role`(예: `owner` / `editor`), 계정 관리는 `owner`만: 나중에 다른
    권한을 더 나눌 때도 같은 칸을 쓴다.
  - `can_manage_accounts` 같은 불리언 하나: 지금 필요한 구분 하나만 표현한다. 두 번째
    구분이 생기면 칸이 또 늘어난다.
  - 나누지 않음: 가장 단순하다. 대신 위 "역할 분리가 처음 필요해지는 곳"의 문제를
    받아들이는 것이다.
  - 어느 쪽이든 **마지막 계정 관리자를 지우거나 강등하지 못하게** 막아야 한다.
- **계정을 어떻게 만들지.** 둘 다 service_role 키가 필요하다. 그래서 서버 API에서만
  할 수 있고, 그 API는 계정 관리 권한을 확인해야 한다.
  - 만드는 사람이 초기 비밀번호를 정해서 전달(`auth.admin.createUser`): 메일 발송이
    필요 없다. 대신 비밀번호를 어떤 경로로 전달할지, 첫 로그인 때 비밀번호 변경을
    강제할지 정해야 한다.
  - 초대 메일(`auth.admin.inviteUserByEmail`): 본인이 비밀번호를 정한다. Supabase의
    기본 메일 발송은 운영용이 아니라 제한이 크다. 커스텀 SMTP가 필요할 수 있으니
    착수할 때 Supabase 문서로 확인한다.
- **계정을 어떻게 내보낼지.** `admin_users` 행만 지우면 로그인은 되지만 관리자 기능은
  막힌다. Auth 사용자 자체를 지우거나 차단하면 로그인도 막힌다. 변경 기록은 행위자의
  이름을 기록할 때 복사해 두므로, 어느 쪽을 골라도 지난 기록은 읽힌다.
- **비밀번호 재설정.** 본인이 바꾸는 화면을 둘지, 계정 관리자가 재설정해 줄지 정한다.
- **기록.** `admin_users`는 감사 로그의 기록 대상이다
  (`docs/specs/2026-10-19-activity-log-design.md` 3.2). 화면에서 계정을 넣고 빼거나 역할 칸을
  더해도 같은 트리거가 잡는다. 계정 관리 API가 service_role로 쓴다면 행위자 헤더(같은 문서
  3.4)를 실어야 "누가 넣었나"가 사람 이름으로 남는다. 비밀번호 값은 어디에도 기록하지
  않는다.
- **비밀번호 정책.** 유출 비밀번호 차단은 Pro 플랜 전용이라 꺼져 있다
  (`supabase/migrations/20260514000000_security_fixes.sql` 끝의 주석). 최소 길이 같은
  Auth 설정을 착수할 때 확인한다.
