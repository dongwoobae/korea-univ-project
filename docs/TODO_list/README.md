# TODO_list — 아직 처리하지 못한 작업 지시서

**혼자 정해버리면 안 되는 것**을 문서당 하나씩 모아 둔다.

코드 리뷰나 구현 중에 두 종류의 항목이 계속 생긴다.

- **고칠 수는 있는데 고치는 순간 정책이 정해지는 것** — 어떤 값을 상한으로 둘지,
  실패했을 때 열지 닫을지처럼 코드만 보면 답이 안 나오는 것.
- **범위 밖이라 미뤘지만 근거를 남겨야 하는 것** — 지금 PR에서 다루지 않기로
  했으나, 왜 미뤘고 무엇이 충족되면 착수하는지가 사라지면 안 되는 것.

이 둘을 코드 주석이나 설계 문서 안에 묻으면 사람이 찾지 못한다. 그래서 별도
폴더로 분리하고, 각 문서를 **그대로 집어 들면 착수할 수 있는 작업 지시서** 형태로 쓴다.

## 규칙

1. **문서 하나 = 문제 하나.** 여러 건을 한 파일에 묶지 않는다.
2. **영역 폴더 아래에 둔다 — `<영역>/<주제>.md`.** 지금 있는 영역은
   `admin/`(관리자 화면과 그 UI) · `auth/`(인증·권한·API 접근 통제) ·
   `video/`(동영상 업로드·저장·삭제 파이프라인)이다. 이 목록은 고정이 아니다 —
   영역이 애매하면 내용이 사는 도메인을 따르고, 새 영역이 필요하면 폴더를 만든다.
   비면 폴더째 지운다.
3. **처리하면 파일을 삭제한다.** 폴더가 비면 대기 항목이 없다는 뜻이다.
   이력은 git이 갖고 있다 — `git log --diff-filter=D -- docs/TODO_list/`로
   언제 무엇이 닫혔는지 추적된다.
4. **삭제할 때 결론은 설계 문서로 옮긴다.** TODO 파일은 "아직 안 정한 것"을 담고,
   설계 문서(`docs/specs/`)는 "정한 것"을 담는다. 이 단계를 빼먹으면
   파일이 사라지면서 판단 근거도 같이 없어진다.
5. **여기에 목록을 만들지 않는다.** 색인을 두면 파일을 지울 때마다 색인도 고쳐야 하고,
   둘이 어긋나는 순간 어느 쪽이 진실인지 알 수 없게 된다. 무엇이 남았는지는
   `ls -R docs/TODO_list`가 답한다.

## 다른 문서와의 경계

[`docs/future-development/`](../future-development/)는 **별도 설계·데이터 구축·현장
검증이 필요한 대규모 후속 기능**을 담는다. 그 README가 스스로 "현재 구현의 단순한
미완료 항목이 아니라"고 못박고 있다. 경로 탐색처럼 프로젝트의 다음 단계에 해당하는
것은 그쪽이다.

**여기는 그 반대다.** 지금 코드에 이미 존재하는 결함이나 미결정 사항 중,
크기는 작지만 혼자 정하면 안 되거나 근거를 남겨야 하는 것이 온다.

`docs/specs/`의 `후속 과제` 절은 **그 설계의 범위를 긋기 위한 목록**이라
설계 문서 안에 남는다. 그중 값어치가 올라가 별도 착수 대상이 된 항목만 이 폴더로
옮겨 온다 — 옮길 때 어느 스펙에서 왔는지 `출처`에 적는다.

## 문서 형식

제목 아래 다음 네 가지를 둔다.

- **막힌 이유** — 왜 지금 못 하는지. 추측이 아니라 실측 근거로.
  차단 사유가 없고 순서상 뒤로 미룬 것뿐이면 **그렇게 적는다** — 없는 장애물을
  지어내면 다음 사람이 있지도 않은 조건을 기다린다.
- **트리거** — 무엇이 충족되면 착수 가능한지.
- **착수 시 정할 것** — 선택지와 각각의 함의.
- **출처** — 어디서 나왔는지와 날짜.

## 주의

여기 적힌 건 **아직 결정이 아니다.** 구현할 때 이 문서를 그대로 따르지 말고,
그 시점의 코드로 전제를 다시 확인할 것. 특히 인용한 파일·줄과 "막힌 이유"의
실측치는 작성 시점 기준이라 이미 바뀌었을 수 있다.
