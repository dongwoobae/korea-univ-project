# 작업 화면 페이지마다 같은 조회·존재 검사·다시 시도 코드가 복제돼 있다

독립 시설·명소·경사도 페이지(`src/app/admin/dashboard/{facilities,landmarks,slopes}/page.tsx`)가 목록 조회 둘레의 같은
일을 각자 한다.

- 첫 조회가 끝난 뒤에만 `?id=`의 존재를 검사하고, 없으면 URL에서 지우며 경고 토스트를 띄운다(설계 3.4)
- 첫 성공에서만 그 항목이 있는 페이지로 맞춘다
- 떠난 뒤 끝난 조회·삭제가 다른 화면의 주소를 건드리지 않게 `disposedRef`와 요청 번호로 버린다
- `retry`는 목록을 받기 전에만 `loading`으로 간다

이유를 적은 주석도 세 파일에 거의 글자 그대로 있다(2026-10-15 `rg -F "존재 검사는 조회가 끝난 뒤에만 한다"`,
`"떠난 뒤에 끝난 조회가"`, `"목록을 받은 뒤에 \"loading\"으로 가면"`이 세 페이지에 각각 한 줄씩 걸린다). 하나를 고칠 때
다른 둘을 빠뜨리면 탭마다 동작이 갈린다.

## 막힌 이유

**차단 사유 없음.** 탭마다 테이블·조인·파생값이 달라(설계 3.2 "조회는 탭이 한다") 공통 훅의 경계를 정하지 않은 채 각
PR이 앞 탭을 본떠 썼다.

## 트리거

- 제보함(PR ④)이 같은 흐름을 넷째로 쓰기 전. 다만 제보함은 서버 페이지라(설계 3.2) 이 흐름을 그대로 쓰지 않을 수 있다
- 셋 중 하나의 조회·존재 검사 동작을 바꿀 때

## 착수 시 정할 것

- **훅의 경계.** 조회 함수(행 만들기 포함)는 탭이 넘기고, 요청 번호·`disposedRef`·첫 성공 판정·존재 검사·페이지 맞추기·
  `retry`를 훅이 가질지. 삭제 뒤 다시 받기와 저장 뒤 다시 받기가 겹칠 때의 처리도 세 페이지에서 같은지 먼저 맞춰 본다.
- **설계에 둘 자리.** 설계 3.2 공통 단위 표에 훅을 더하고, 세 페이지의 주석은 그 훅으로 옮긴다.
- **확인 방법.** 세 작업 화면 spec이 그대로 통과해야 한다.
