# 경사도 작업 화면 spec에 명소·독립 시설에는 있는 실패 경로 시나리오가 없다

`e2e/admin-slopes-workspace.spec.ts`는 명소·독립 시설 spec의 정상 경로와 저장 쪽 실패는 따라 적었지만, 아래 경로는
경사도에 시나리오가 없다. 코드는 같은 방식으로 막고 있다(`src/app/admin/dashboard/slopes/page.tsx`의 `deleteRoute`·
`handleDeleted`·`loadRoutes`·`disposedRef`). 고장 나도 테스트가 알리지 않는다.

| 경로                                            | 다른 탭에 있는 대응 시나리오                                                                    |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| 삭제가 실패하면 오류로 알리고 행을 남긴다       | 명소 `삭제가 실패하면 반환된 메시지를 오류로 알리고 행을 남긴다`                                |
| 삭제를 기다리다 다른 화면으로 떠난 뒤 끝난 삭제 | 명소 `삭제를 기다리다 다른 화면으로 떠나도 끝난 삭제가 그 화면의 선택과 입력을 건드리지 않는다` |
| 2페이지 항목의 `?id=`가 첫 조회 실패 뒤 열림    | 독립 시설 `첫 조회가 실패한 ?id= 링크도 다시 시도가 그 항목의 페이지를 연다`                    |
| 다시 받기가 실패하면 토스트로 알린다            | 독립 시설 `받은 목록이 있으면 다시 시도의 목록 조회가 실패해도 패널이 멈추지 않는다`            |
| 모바일 편집 패널의 삭제가 늦게 끝남             | 없음 — 경사도의 모바일 삭제는 데스크톱(보기 패널)과 다른 패널에 있다(설계 6.6)                  |

## 막힌 이유

**차단 사유 없음.** ③의 범위를 새 화면과 옮긴 시나리오에 두고 뒤로 미뤘다.

## 트리거

- 경사도의 삭제·다시 받기 흐름(`deleteRoute`·`handleDeleted`·`loadRoutes`)을 바꿀 때
- 작업 화면 페이지의 조회 흐름을 공통 훅으로 뺄 때(`docs/TODO_list/admin/workspace-page-load-duplication.md`) — 그
  전에 세 탭의 같은 시나리오를 갖춰 두면 옮긴 뒤를 같은 기준으로 본다

## 착수 시 정할 것

- **목 응답.** 삭제 실패는 `slope_segments`의 `DELETE`를 500으로, 늦은 삭제는 응답을 붙잡아 두는 방식(명소 spec과 같다)으로.
- **모바일 늦은 삭제의 기대.** 삭제를 기다리는 동안 목록으로 돌아가거나 다른 행을 열었을 때, 끝난 삭제가 그 화면을
  닫지 않는지(`handleDeleted`의 선택 비교). 데스크톱 시나리오
  `삭제를 기다리는 사이 연 다른 경로의 상세는 삭제가 끝나도 남는다`와 같은 기대인지 정한다.
