# 시설 삭제가 중간에 실패하면 동영상만 사라진다

`deleteFacility`는 동영상을 **먼저** 지우고 시설 row를 나중에 지운다
(`src/lib/facilityDelete.ts:13-28`).

```ts
if (facility.video_url) {
  const res = await authedFetch("/api/delete-facility-video", { ... });
  if (!res.ok) return "동영상 삭제에 실패해 시설을 지우지 못했어요";
}
const { error } = await supabase.from("building_facilities").delete().eq("id", facility.id);
```

이 순서는 **의도된 것**이다. 함수 docstring이 "정리에 실패하면 고아 객체가 남지
않도록 row를 남겨두고 메시지를 반환한다"고 적고 있다. 첫 단계가 실패하는 경우는
잘 다뤄져 있다.

문제는 **반대 방향이다.** 첫 단계가 성공하고 두 번째가 실패하면:

- R2 객체는 이미 `DeleteObjectCommand`로 지워졌다 — 복구 수단이 없다
- `video_url`은 `null`이 됐다
- 시설 row는 그대로 남는다

사용자가 보는 것: 삭제가 실패했다는 메시지, 그런데 목록에는 시설이 남아 있고
**동영상만 없어져 있다.** 다시 삭제를 눌러도 동영상은 돌아오지 않는다.

두 번째 단계는 브라우저에서 anon 키로 나가는 `supabase.from(...).delete()`라
RLS 정책·네트워크 단절·경쟁 조건 어느 쪽으로도 실패할 수 있다. 첫 단계는
service-role 서버 라우트라 성공률이 다르다 — **성공률이 높은 쪽을 먼저 돌리고,
되돌릴 수 없는 쪽을 거기에 두었다.**

## 막힌 이유

**차단 사유 없음.** 범위 때문에 미뤘다 — `facilityDelete.ts`는
`facility-detail-modal` 브랜치가 건드리지 않은 선재 파일이다.

**실제 발생 사례는 없다.** 위 서술은 코드를 읽고 세운 것이고, 두 번째 단계가
실제로 얼마나 실패하는지(RLS가 지금 어떻게 걸려 있는지)는 확인하지 않았다.
착수하면 `building_facilities`의 DELETE 정책부터 확인할 것.

## 트리거

없음. 아래가 있으면 우선순위가 올라간다.

- `building_facilities`에 RLS DELETE 정책이 추가돼 브라우저 삭제가 조건부가 된다
- 실제로 "동영상만 사라졌다"는 사례가 나온다

## 착수 시 정할 것

- **어디까지 한 트랜잭션으로 묶을지.** 선택지:
  - **서버 라우트 하나로 합친다** — service-role로 row 삭제와 R2 정리를 한 곳에서
    한다. 순서를 DB 먼저로 뒤집고 R2 실패는 무시하거나 재시도 큐에 넣을 수 있다.
    가장 깨끗하지만 새 라우트가 생기고 클라이언트 호출부가 바뀐다.
  - **순서만 뒤집는다** — row를 먼저 지우고 R2를 나중에. 실패 시 고아 객체가
    남지만 **복구 불가능한 손실은 없다.** 변경이 작다. 대신 지금 docstring이
    말하는 "고아를 안 남긴다"는 성질을 포기하는 것이므로 문서도 같이 고쳐야 한다.
  - 그대로 두고 실패 메시지만 정확하게 — "동영상은 삭제됐지만 시설을 지우지
    못했어요"처럼. 손실은 그대로지만 사용자가 상태를 오해하지는 않는다.
- **고아 객체를 어떻게 볼지.** 위 두 번째 선택지를 고르면 고아가 정상 상태가 된다.
  같은 스펙의 `동영상 교체 시 R2에 남는 옛 객체 정리`와 묶어서 수거 절차를
  한 번에 정하는 편이 낫다 — 따로 정하면 규칙이 갈라진다.
- **되돌리기 지점.** 지금 `delete-facility-video`는 R2 삭제가 실패하면
  `video_url`을 되돌려 놓는다(보상 트랜잭션). 합치는 설계에서도 이 성질을
  유지할지 정한다.
