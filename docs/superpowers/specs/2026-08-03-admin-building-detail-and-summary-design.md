# 관리자 건물 화면 정리 설계 스펙

날짜: 2026-08-03
상태: 승인 대기

건물 편집 페이지와 건물 관리 목록에서 드러난 문제들을 한 번에 정리하고, 요약 카드에 목록 필터 기능을 붙인다. 서로 독립적이지만 모두 "관리자가 건물 데이터를 보는 화면"이라는 한 지점에 모여 있어 하나의 스펙으로 묶는다.

## 스코프

1. 건물 편집 페이지 — 폴리곤을 편집 전에도 보여준다
2. 건물 편집 페이지 — 동작하지 않는 섹션 내비를 걷어낸다
3. 건물 편집 페이지 — 삭제 버튼의 위치와 모양을 바로잡는다
4. 건물 관리 — 요약 카드가 전부 `—`인 문제와 모바일 목록 정렬 어긋남
5. 건물 관리 — 경고 카드를 눌러 해당 건물만 목록에 거른다

## 1. 폴리곤 프리뷰

### 문제

`/admin/buildings/[id]`의 폴리곤 카드는 편집 버튼을 누르기 전까지 `✅ 폴리곤 데이터 있음`이라는 문구만 보여준다. 폴리곤이 있다는 사실은 알 수 있지만 그것이 **맞게 그려졌는지**는 편집 모드에 들어가야만 확인할 수 있다.

### 설계

`src/components/BuildingPolygonPreview.tsx`를 새로 만들고 `dynamic(..., { ssr: false })`로 로드한다. Leaflet은 `window`에 의존하므로 `PolygonEditor`와 같은 방식이다.

| 항목      | 값                                                                          |
| --------- | --------------------------------------------------------------------------- |
| 높이      | 260px (편집기는 420px — 프리뷰는 확인용이므로 더 낮게)                      |
| 타일      | CARTO, `usePrefersDarkMode`로 라이트/다크 전환 (편집기와 동일)              |
| 이 건물   | 파란색 폴리곤 (`#2563EB`, weight 2, fillOpacity 0.3) — 편집기와 같은 스타일 |
| 주변 건물 | 회색(`#9ca3af`) + 이름 툴팁 — 편집기와 같은 그림                            |
| 뷰포트    | 중심점 + zoom 18 (아래 참조)                                                |
| 상호작용  | 전부 차단 (아래 참조)                                                       |

**뷰포트는 편집기와 같은 방식을 쓴다.** 편집기가 `setView(center, 18)`이므로 프리뷰만 `fitBounds`를 쓰면 편집 버튼을 누르는 순간 화면이 튄다. 건물 크기 편차 때문에 `fitBounds`가 더 나은 프레이밍을 주지만, 그 이득보다 두 화면이 어긋나는 손해가 크다. 프레이밍을 개선하려면 편집기와 프리뷰를 **함께** 바꿔야 하며, 그것은 이번 범위 밖이다.

**attribution 컨트롤은 표시되지 않는다.** `globals.css`가 `.leaflet-control-attribution { display: none; }`으로 전역에서 숨기고 있다. 프리뷰만 예외로 두지 않는다 — 관리자 화면의 다른 지도와 어긋나기 때문이다. 타일 저작권 표기는 공개 지도 화면이 별도 UI로 담당한다.

상호작용 차단은 두 층으로 한다. 지도 옵션(`dragging`, `scrollWheelZoom`, `doubleClickZoom`, `touchZoom`, `boxZoom`, `keyboard`, `zoomControl` 모두 off)과 레이어 옵션(`interactive: false`)을 함께 끈다. 지도 옵션만 끄면 폴리곤 자체는 여전히 마우스 이벤트를 잡아 커서가 바뀐다.

렌더 조건:

- `building.geojson`이 없으면 지도를 띄우지 않고 기존 `❌ 폴리곤 없음 — 편집으로 추가` 문구를 유지한다
- `editingPolygon`이 참이면 프리뷰 대신 `PolygonEditor`를 띄운다 (지도 두 개가 동시에 뜨지 않는다)

### 수명주기

`PolygonEditor`는 `initialGeojsonRef = useRef(geojson)`와 의존성 빈 `useEffect`로 초기 폴리곤을 **한 번만** 읽는다. 프리뷰가 이 패턴을 그대로 복사하면 폴리곤 저장 직후 화면이 갱신되지 않는다 — 저장 핸들러가 `setEditingPolygon(false)` 후 `fetchData()`를 부르는데, 프리뷰는 새 `geojson` prop을 무시하고 이전 폴리곤을 계속 그린다. "저장은 됐다는데 지도가 그대로"인 버그가 된다.

프리뷰는 `geojson`이 바뀌면 반드시 다시 그린다. 호출부에서 `key`로 재마운트를 강제하거나, 컴포넌트가 `geojson` 변경을 감지해 레이어를 교체한다. 어느 쪽이든 **언마운트 시 `map.remove()`를 호출한다** — 편집 토글을 반복할 때마다 지도 인스턴스가 쌓이면 타일 요청과 이벤트 핸들러가 함께 남는다.

### 조회 비용

이 변경으로 **상세 페이지를 열 때마다 전체 건물 폴리곤을 조회하게 된다.** 지금은 편집 버튼을 눌러야 나가던 쿼리다. 현재 쿼리에는 `limit`도 bounds 필터도 없어, 목록을 훑으며 건물 10개를 열면 전체 조회가 10번 반복된다.

건물 96개 규모에서는 감당 가능하므로 이번에는 쿼리 자체를 바꾸지 않는다. 다만 **주변 건물 조회 결과를 모듈 수준에서 캐시**해 같은 세션 안에서 상세 페이지를 여러 번 열어도 조회가 한 번만 나가게 한다. 폴리곤을 저장하면 캐시를 무효화한다.

건물 수가 수백 개로 늘면 bounds 기반 조회로 바꿔야 한다. 그 시점의 작업으로 남긴다.

### 공유 추출

주변 건물 조회·스타일 로직을 `src/lib/neighborBuildings.ts`로 뺀다. 소비자는 **셋**이다:

- `PolygonEditor` — 편집 대상을 제외한 나머지를 회색으로
- `BuildingPolygonPreview` — 같음
- `FacilityMap` — 제외 없이 전부 받아, 하나를 파란색으로 강조

세 곳이 이미 `select("id, name, geojson").eq("is_deleted", false).not("geojson", "is", null)`라는 **똑같은 쿼리**를 쓰고 회색값도 `#9ca3af`로 같다. 복사해두면 한쪽만 고쳐지는 사고가 난다.

계약은 세 소비자를 모두 담아야 한다. `excludeId`를 필수 인자로 받는 모양은 `FacilityMap`을 배제하므로 좁다. 조회와 스타일을 분리한다:

- `fetchNeighborBuildings()` — 필터 없이 조회하고 캐시한다. 반환은 `Feature[]`이며 각 feature의 `properties`에 `bid`와 `name`을 넣는다
- `NEIGHBOR_STYLE` — 회색 스타일 상수

제외와 강조는 각 소비자가 결과를 받아 처리한다. 소비자마다 다른 것을 공유 모듈에 밀어 넣지 않는다.

## 2. 섹션 내비 제거

### 문제

상단 섹션 내비(`사진 · 이름 · 소속 · 폴리곤 · 시설 · 삭제·복구`)는 같은 페이지 안의 앵커 스크롤이다. 데스크톱은 2열 레이아웃이라 내용이 한 화면에 거의 다 들어와 스크롤할 거리가 없고, 그래서 눌러도 아무 반응이 없는 것처럼 보인다. 원래 세로로 길어지는 모바일을 염두에 둔 장치였지만 실사용에서 값을 못 하고 있다.

### 설계

제거 대상:

- `DETAIL_SECTIONS` 상수, `activeSection` 상태, 이를 갱신하는 `IntersectionObserver` 이펙트
- `<nav className="ku-admin-detail-section-nav">` 블록 전체
- CSS의 `.ku-admin-detail-section-nav*` 규칙과 `scroll-margin-top` 규칙

**카드의 `id` 속성은 남긴다.** 앵커 대상으로는 쓸 데가 없어졌지만 E2E가 섹션 스코프 로케이터로 쓰고 있다(아래 참조). 지우면 내비와 무관한 테스트가 깨진다.

존치 대상:

- `저장하지 않은 변경 N개` 상태 칩. 이름·소속·폴리곤 중 저장 안 한 게 있는지 알려주는 실질적인 장치다. 내비 바가 사라지므로 헤더의 `지도 보기` 버튼 왼쪽으로 옮긴다.
- `.ku-admin-detail-save-status`는 헤더 배치에 맞게 재조정한다. 모바일에서 `position: absolute`로 내비 바 아래에 띄우던 규칙은 붙을 대상이 없어지므로 삭제한다.

### E2E 영향

`e2e/admin-buildings-slopes.spec.ts`의 두 테스트가 영향을 받는다.

"건물명 수정과 소프트 삭제·복원을 수행한다":

- 내비 존재·링크 6개 단언 → 삭제
- 시설 링크 클릭 후 `#building-facilities` URL 단언 → 삭제
- 이탈 경고 모달 취소 후 URL 단언 → 해시 없는 `/admin/buildings/1`로 바꾼다
- `#building-name` 로케이터 → `id`를 남기므로 그대로 둔다

"건물 사진의 파일별 성공·실패를 표시하고 실패만 재시도한다":

- `page.locator("#building-photos")`를 섹션 스코프로 쓴다. `id`를 남기므로 수정 불필요하다.

`저장하지 않은 변경 1개` 상태와 `저장 안 됨` 배지 단언은 그대로 유지한다. 이 둘이 이 테스트의 실제 회귀 방어선이다.

## 3. 삭제 버튼 위치·모양

### 문제

두 가지가 겹쳐 있다.

`admin-ui.css`의 `.ku-admin-detail-grid > div` 규칙이 그리드 **직계 자식 전부**에 카드 배경·테두리·radius를 강제한다. `building-danger` 래퍼는 카드가 아닌데 카드처럼 렌더된다.

같은 파일의 배치 규칙이 `nth-child(1)`부터 `(5)`까지만 있는데 JSX 자식은 6개다. 6번째인 danger는 배치 규칙이 없어 자동 배치로 왼쪽 열 맨 아래에 떨어진다.

### 설계

- `.ku-admin-detail-grid > div` 선택자를 `.ku-admin-detail-grid > .ku-admin-detail-card`로 좁힌다. danger 래퍼가 카드 스타일을 상속하지 않게 되는 근본 수정이다.
- **위치 기반 배치를 클래스 기반으로 바꾼다.** `nth-child(1)~(5)`를 각 카드의 의미 클래스(`--photos`, `--name`, `--college`, `--polygon`, `--facilities`)로 교체한다. 이번 사고의 원인이 DOM 순서를 레이아웃 API로 쓴 것이므로, 선택자 범위만 좁히고 두면 카드를 하나 더 추가할 때 같은 일이 반복된다. 비용은 2파일(`page.tsx`, `admin-ui.css`)이고 소비자는 이 화면 하나뿐이다.
- `.ku-admin-detail-danger`에 `grid-column: 1 / -1`을 명시한다. 두 열 아래 전체 폭에서 가운데 정렬된다.
- 버튼은 작게 줄인다: `font-size: 12px`, `padding: 6px 14px`, 얇은 danger 테두리만. 흰 배경 없이 페이지 배경 위에 그대로 놓는다.
- 복구 버튼도 같은 치수로 맞춘다. 삭제/복구는 같은 자리에서 토글되므로 크기가 다르면 전환할 때 레이아웃이 흔들린다.

## 4. 건물 관리 — 요약 카드와 모바일 목록

### 4-1. 요약 카드가 전부 `—`였던 이유

**마이그레이션이 운영 DB에 적용된 적이 없었다.** CI 실행 이력 실측 결과:

- `Apply Supabase migrations` 잡은 `def2536`(2026-07-23)에 추가된 이래 모든 런에서 `skipped`였다. 한 번도 성공한 적이 없다.
- 이 잡을 처음 통과했어야 할 푸시(run `29996096449`, 2026-07-23)는 Format(Prettier) 잡이 실패했다. `migrate`는 `needs: [migration-safety, lint, format, typecheck, test, e2e]`이므로 함께 skip됐다.
- 그 뒤의 푸시들은 `supabase/migrations`에 변경이 없어 `has_changes=false`가 되어 계속 skip됐다. 07-27·07-30 런이 초록불이라 적용된 것처럼 보였지만 실제로는 건너뛴 것이다.

**조치(운영) — 완료:** 2026-08-03 CI를 `workflow_dispatch`로 수동 실행(run `30800700137`)해 밀려 있던 두 개를 적용했다.

- `20260723000002_add_facility_translation_status.sql`
- `20260723000003_create_admin_building_summary.sql`

`translation_status` 컬럼도 함께 밀려 있었다. 즉 요약 함수가 존재했더라도 그 컬럼을 참조하는 `translation_needed_count` 집계에서 실패했을 것이다. 두 마이그레이션이 한 세트로 밀린 셈이다.

**조치(코드):** `fetchSummary`가 `summaryResult.error`를 확인하지 않는다. 그래서 RPC 실패와 "집계 결과가 비어 있음"이 화면에서 구분되지 않는다. 오류를 상태로 잡아 요약 영역에 실패했음을 드러낸다.

단, **오류 원문을 화면에 렌더링하지 않는다.** PostgREST 오류의 `message`·`details`·`hint`에는 함수 시그니처, relation·column 이름, schema cache 힌트가 담긴다. 화면에는 `요약을 불러오지 못했어요` 수준의 문구와 재시도 수단만 두고, 원문은 `console.error`로 보낸다.

**조치(CI):** 두 가지를 고친다.

첫째, **검증 스텝 자체가 깨져 있다.** run `30800700137`에서 마이그레이션 적용은 성공했으나 `Verify local and remote migration history` 스텝이 실패했다:

```
Connecting to remote database...
jq: parse error: Invalid numeric literal at line 3, column 9
```

`supabase migration list --output json`이 JSON 앞에 진행 메시지를 stdout으로 흘리는데 그 출력을 `jq`에 그대로 물린다. 이 스텝은 한 번도 통과한 적이 없다 — 잡이 계속 skip돼서 드러나지 않았을 뿐이다. CLI 출력 포맷에 의존하지 않는 방식으로 바꾼다: `supabase_migrations.schema_migrations` 테이블을 직접 조회해 로컬 파일 목록과 대조한다.

둘째, 이 검증이 `migrate` 잡 안에만 있다. 그 잡이 skip되면 검증도 함께 사라져 드리프트가 감지되지 않는다 — 이번 사고가 열흘 넘게 안 보인 이유가 이것이다. 별도 잡으로 분리해 마이그레이션 변경 여부와 무관하게 실행한다.

분리한 잡은 두 조건을 지켜야 한다. **그러지 않으면 고치려던 것보다 나쁜 것을 만든다.**

- **PR에서는 돌리지 않는다.** `push`와 `workflow_dispatch`로 한정한다. `ci.yml`은 `pull_request`에서도 도는데, 포크 PR에는 secrets가 주어지지 않아 DB URL 검사에서 `exit 1`이 난다. 항상 빨간불이 되면 드리프트 신호로서 무의미해지고, 이를 무마하려 `pull_request_target`으로 우회하는 압박이 생긴다.
- **마스킹을 그대로 복사한다.** 기존 잡은 URL 인코딩된 비밀번호와 완성 DB URL을 `::add-mask::`로 가린다. 원본 secret은 자동 마스킹되지만 `[YOUR-PASSWORD]` 치환 후의 인코딩된 파생 값은 별도 마스킹 없이는 로그에 그대로 남는다.

### 4-2. 모바일 목록 정렬 어긋남

`.ku-admin-mobile-card`는 `<button>` 요소인데 `globals.css`의 리셋에 `text-align` 항목이 없다. 브라우저 기본값 `text-align: center`를 상속받아 건물명이 가운데 정렬되고, 바로 아래 `.ku-admin-mobile-meta`는 `display: flex`라 항목들이 왼쪽에 붙는다. 두 줄의 기준선이 달라 목록 전체가 들쑥날쑥해 보인다.

`.ku-admin-mobile-card`에 `text-align: left`를 준다.

## 5. 경고 카드 클릭 → 목록 필터

### 목적

요약 카드가 "사진 없는 건물 12개"라고 알려주면 다음 행동은 그 12개를 찾는 것이다. 지금은 알려주기만 하고 찾는 일은 사용자 몫이라, 96개 목록을 눈으로 훑어야 한다.

경고 카드 5개를 누르면 아래 목록이 해당 건물만 남도록 한다.

- 시설 정보 없음
- 사진 없음
- 위치 없음
- 갱신일 오래됨
- 번역 필요

`등록된 시설`은 경고가 아니라 총계이므로 클릭 대상이 아니다.

### DB — `admin_building_flags` 뷰 신규

카드 숫자와 목록 개수가 어긋나지 않으려면 조건 정의가 **한 곳에만** 있어야 한다. 지금 정의는 `get_admin_building_summary()`의 SQL 안에 있다. 목록 필터를 TypeScript로 따로 구현하면 정의가 두 벌이 되어 시간이 지나면 갈라진다.

건물별 플래그를 주는 뷰를 만들고, 카드 숫자와 목록 필터가 **둘 다** 그 뷰를 본다.

| 컬럼                 | 내용                                                           |
| -------------------- | -------------------------------------------------------------- |
| `building_id`        | `buildings.id`                                                 |
| `missing_facility`   | 등록된 시설이 없다                                             |
| `missing_photo`      | 사진이 없다                                                    |
| `missing_location`   | `geojson`이 null이다                                           |
| `stale_update`       | `last_updated`가 null이거나 1년 이상 지났다                    |
| `translation_needed` | `translation_status <> 'translated'`인 시설을 하나 이상 갖는다 |

삭제된 건물(`is_deleted`)은 뷰에서 제외한다. 기존 함수의 `active_buildings` 정의와 같다.

**`security_invoker = on`으로 만든다.** 뷰는 기본적으로 소유자 권한으로 실행되어 RLS를 우회한다. 기존 함수가 `security invoker`인 것과 posture를 맞춘다. 권한도 함수와 같이 간다 — `revoke ... from public`, `grant select ... to authenticated`.

같은 마이그레이션에서 `get_admin_building_summary()`를 `create or replace`로 갱신해 4개 건물 단위 집계를 이 뷰에서 가져오게 한다. `registered_facility_count`는 시설 총계라 뷰 대상이 아니므로 그대로 둔다.

마이그레이션 적용 후 `supabase/database.types.ts`를 재생성한다.

### `번역 필요` 카드는 두 숫자를 함께 보여준다

`translation_needed_count`는 **시설 수**를 센다(카드 설명: "번역 대기 또는 실패 상태인 시설"). 나머지 경고 카드 4개는 건물 수다. 클릭 필터는 건물을 거르므로, 이대로 두면 카드가 `12개`인데 목록에 건물 7개가 나와 고장으로 읽힌다.

시설 수는 그 자체로 작업량을 알려주는 값이므로 버리지 않는다. **두 숫자를 카드에 함께 표시한다** — `시설 12개 · 건물 7개`. 클릭하면 건물 7개를 거른다.

- 기존 `translation_needed_count`(시설 수)는 그대로 둔다. 의미를 바꾸지 않으므로 이 지표를 읽던 곳이 깨지지 않는다.
- `translation_needed_building_count`를 함수에 추가한다. 뷰의 `translation_needed`가 참인 건물 수다.
- 이 카드만 두 숫자를 갖게 되어 다른 카드와 모양이 달라진다. 의도된 예외이며, 클릭 시 걸러지는 대상이 무엇인지 카드에서 바로 읽히는 편이 모양의 일관성보다 낫다.

`summaryItems`는 지금 카드 하나가 키 하나를 갖는 구조다. 이 카드는 두 값을 쓰므로 그 구조를 넓혀야 한다. 카드마다 "표시할 값을 어떻게 만들지"를 갖게 하고, 클릭 필터가 쓰는 플래그 키는 표시 값과 별개로 둔다.

### 화면 동작

- 경고 카드를 누르면 필터가 켜진다. 같은 카드를 다시 누르면 꺼진다. 필터는 한 번에 하나만 — 여러 조건을 겹치는 요구는 아직 없다.
- 켜진 카드는 눌린 상태로 보인다. `aria-pressed`로 상태를 알린다.
- 필터가 켜지면 페이지를 1로 되돌린다. 3페이지를 보던 중 필터를 켜면 결과가 1페이지뿐인데 3페이지에 머무는 일이 생긴다.
- 기존 검색어와 함께 걸린다. 검색과 필터는 AND다.
- `AdminListControls`의 `hasActiveFilters`·`onReset`이 이미 있으므로 필터 해제 경로는 그것을 쓴다. 지금은 검색어만 보고 있으므로 필터 상태도 함께 보도록 넓힌다.
- 필터 결과가 0건이면 기존 `검색 결과가 없습니다.` 대신 어떤 필터 때문인지 알 수 있는 문구를 낸다.

카드는 현재 `<div>`다. 클릭 대상이 되므로 `<button>`으로 바꾼다 — 키보드 접근과 포커스 표시가 따라온다. 이때 `text-align`을 명시한다. 4-2와 같은 원인으로 카드 안 텍스트가 가운데 정렬되기 때문이다.

### 목록 쿼리

기존 목록 쿼리는 `buildings`를 직접 조회한다. 필터가 켜지면 `admin_building_flags`에서 해당 플래그가 참인 `building_id`를 받아 `.in("id", ids)`로 좁힌다.

건물 96개 규모에서 id 배열은 작다. 수백 개로 늘어 URL 길이가 문제가 되면 뷰를 조인하는 방식으로 바꾼다. 그 시점의 작업으로 남긴다.

## 검증

- 폴리곤이 있는 건물과 없는 건물 양쪽에서 편집 페이지를 연다. 있으면 지도가 뜨고 없으면 기존 문구가 남는지, 편집 진입 시 지도가 하나만 뜨는지 확인한다.
- 편집 버튼을 눌렀을 때 지도 뷰포트가 튀지 않는지 확인한다.
- 폴리곤을 편집·저장한 뒤 프리뷰가 **새 폴리곤**을 그리는지 확인한다.
- 편집 진입·취소를 여러 번 반복한 뒤 지도 인스턴스가 쌓이지 않는지 확인한다.
- 상세 페이지를 연속으로 여러 개 열었을 때 주변 건물 조회가 반복되지 않는지 네트워크 탭에서 확인한다.
- 프리뷰 지도에서 드래그·휠·더블클릭이 모두 먹지 않는지, 폴리곤 위에서 커서가 바뀌지 않는지 확인한다.
- 이름을 수정한 채로 두고 헤더에 `저장하지 않은 변경 1개`가 뜨는지, 저장 후 사라지는지 확인한다.
- 삭제 버튼이 두 열 아래 가운데에, 흰 카드 배경 없이 놓이는지 확인한다.
- 모바일 폭(390px)에서 건물명과 메타 줄의 왼쪽 끝이 맞는지 확인한다.
- 요약 카드 6개에 실제 숫자가 뜨는지 확인한다.
- 경고 카드 5개를 각각 눌러 **목록 개수가 카드 숫자와 일치**하는지 확인한다. 이것이 뷰를 도입한 이유이므로 가장 중요한 검증이다. `번역 필요`는 두 숫자 중 **건물 쪽**과 일치해야 한다.
- 필터를 켠 채 검색어를 넣어 AND로 걸리는지, 필터를 끄면 원래 목록으로 돌아오는지 확인한다.
- 키보드만으로 카드를 눌러 필터를 켜고 끌 수 있는지 확인한다.
- 요약 RPC가 실패했을 때 화면에 오류 원문이 아니라 일반 문구가 뜨는지 확인한다.
- 기존 E2E 스위트를 돌려 위 변경으로 깨지는 것이 없는지 확인한다.

## 이번 범위 밖

- `PolygonEditor`의 편집 기능 자체는 건드리지 않는다. 프리뷰와 공유하는 주변 건물 로직만 모듈로 뺀다.
- 프리뷰·편집기의 뷰포트를 `fitBounds`로 개선하는 것. 두 화면을 함께 바꿔야 하므로 별건이다.
- 주변 건물 조회를 bounds 기반으로 좁히는 것. 캐시로 이번 규모는 감당되며, 건물 수가 수백 개가 될 때 다룬다.
- 목록 필터를 여러 조건 동시 적용으로 확장하는 것.
- `README.md`의 RLS 서술 정정. README는 관리 작업이 API Route의 service_role을 경유하고 `buildings` 쓰기가 service_role 전용이라고 적지만, 건물명 저장·소속 저장·소프트 삭제·시설 토글이 모두 브라우저에서 `supabase.from("buildings").update(...)`로 직접 나간다. 관리자 화면이 실제로 동작하므로 README 쪽이 사실과 다르다. 이 스펙과 무관한 선재 문제라 별도로 다룬다.
