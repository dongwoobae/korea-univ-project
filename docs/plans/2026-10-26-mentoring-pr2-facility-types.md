**Goal:** 시설 종류에 '장애학생 휴게실'(`student_lounge`, 소파 아이콘·청록)을 더하고, '장애인 화장실'을 '장애인용 화장실'로 바꾸고,

**Architecture:** 마이그레이션 하나가 `sort_order` 칸을 더해 지금 화면 순서로 채우고, 종류 두 행을 넣거나 고치고, 이름이 정확히 옛

정렬, 메타 설명을 바꾼다.

## Global Constraints

- 새 종류 값(설계 4.2): 코드 `student_lounge`, 한국어 `장애학생 휴게실`, 영어 `Lounge for Students with Disabilities`, 중국어

- `restroom`의 한국어 이름은 `장애인용 화장실`. 빈 DB에 새로 넣을 때 영어·중국어는 운영 값 `Accessible Restroom`·`无障碍卫生间`.
  이미 있으면 **한국어 이름만** 바꾼다.
- 시설 이름(`building_facilities.name`)이 **정확히** `장애인 화장실`인 행만 `장애인용 화장실`로 바꾼다. 영어·중국어 이름과 번역
  상태, 대기 중인 등록 요청은 건드리지 않는다. 나머지 운영 종류를 씨앗으로 채우지 않는다. `automatic_door` 아이콘은 범위 밖.
- `sort_order`는 `integer generated by default as identity`. 기존 행은 `restroom` 1 · `ramp` 2 · `parking` 3 · `elevator` 4 ·
  `automatic_door` 5, 채우는 동안 활동 기록 트리거(`log_facility_types_change`)를 끈다. 번호 없이 들어오는 행은 다음 번호.

## 이 계획이 정한 것

1. **활동 기록**: 순서 채우기 동안만 끈다(종류 다섯 줄 "순서" 노이즈). 화장실 이름·휴게실·시설 이름 바꾸기는 남긴다 — 운영에서 네 줄,
   행위자 "DB 직접 변경". 이름을 바꾼 시설 두 곳은 `updated_at`도 바뀌어 관리자 최근 수정순에서 앞으로 온다.
2. **시설 이름 바꾸기는 종류를 가리지 않고 이름만 본다**(설계 4.2 문구 그대로). 운영에서 두 곳 다 `restroom`이다.
3. **빈 DB 결과만 pgTAP으로 본다.** 운영 행의 순서 채우기, 이미 있던 `restroom`의 영어·중국어 지키기, 시설 이름 바꾸기는 마이그레이션
   때 한 번 도는 일이라 DB 테스트(빈 DB)에서 볼 수 없다. 병합 뒤 방문자 키로 확인한다. 버린 대안: `scripts/apply-db-test-schema.sh`에
   "이 마이그레이션 직전에 넣는 데이터" 장치를 두는 것 — 모든 마이그레이션이 쓰는 DB 테스트 절차를 바꾸고, 그 데이터가 `rollback` 밖이라
   다른 테스트 파일의 DB에 남는다. 운영에서 바뀌는 행은 정확히 읽을 수 있다(①-1 채우기와 같은 방식).
4. **`sort_order`를 identity로 두는 이유**: 번호 없이 넣는 기존 코드·테스트(`admin_write_policies.test.sql`·
   `activity_log_triggers.test.sql`의 `facility_types` 삽입)가 그대로 돌고 새 행이 맨 뒤에 붙는다. `by default`라 ②-2가 번호를 직접
   바꿀 수 있다. 버린 대안: 사진처럼 트리거로 마지막 번호 + 1(관리자가 동시에 종류를 더할 일이 드물어 잠금·트리거가 과하다), 빈 칸
   허용 + `nulls last`(새 행 자리가 정해지지 않는다), 기본값 0(동점이 생긴다).
5. **E2E는 정렬 요청 계약만 본다**: 공개 지도·관리자 시설 탭·건물 상세·제보함이 `facility_types`를 `order=sort_order.asc,code.asc`로
   읽는지. 목 백엔드는 종류를 고정 목록으로 돌려줘 정렬 결과는 흉내 내지 않는다. 등록 요청 모달은 여는 흐름이 길어 리뷰로 본다.
   아이콘·색은 단위 테스트와 기존 짝 검사·대비 검사가 잡는다.

## Review Focus

1. **순서 채우기**: `alter table … add column … generated by default as identity`가 기존 행을 채운 뒤 `update`가 다섯 코드에 1~5를 주고,
   그 사이만 `log_facility_types_change`가 꺼지는지. 휴게실 `insert`가 `sort_order`를 주지 않아 가장 큰 번호를 받는지. 번호는 6이
   아니라 7일 수 있다 — `restroom`의 `insert … on conflict`가 충돌을 알기 전에 identity 기본값을 계산해 시퀀스 하나를 쓴다. 순서에는
   상관없다.
2. **`on conflict`**: `restroom`은 `label`만, `student_lounge`는 세 이름 모두 덮는지(`excluded.`).
3. **시설 이름**: `where name = '장애인 화장실'`이 정확히 같음 비교인지. 다른 칸을 고치지 않는지.
4. **`Record<FacilityCode, …>` 네 곳**: `facilityColor`, `FACILITY_ICON_KEY`·`FACILITY_ICON_SVG`, `FACILITY_ICON`. 타입 검사가 앞의
   셋을, 짝 검사가 `FACILITY_ICON`을 강제한다.
5. **등록 요청 모달 정렬**: `FacilityRequestModal.tsx`의 조회에 `.order("sort_order").order("code")`가 들어갔는지(E2E가 보지 않는다).

  when 'restroom' then 1
  when 'ramp' then 2
  when 'parking' then 3
  when 'elevator' then 4
  when 'automatic_door' then 5
end
where code in ('restroom', 'ramp', 'parking', 'elevator', 'automatic_door');
alter table public.facility_types enable trigger log_facility_types_change;

on conflict (code) do update set label = excluded.label;

insert into public.facility_types (code, label, label_en, label_zh)
